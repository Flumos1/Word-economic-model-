# Навыки роли `archivist`

Дата: 2026-11-22. Каждый навык описан как **вход → шаги → выход → проверка**. Инструмент —
`tools/archivist.py`; ручная правка `entries/*.jsonl` запрещена (только `add` → `merge`).

## 1. Приём записи (intake)

**Вход:** знание от роли/проекта: текст, источник, дата, кому адресовано.

**Шаги:**
1. Определить `kind`: `method` (как делать), `source` (карточка источника/класса), `legal`
   (правовая рамка-указатель), `fact_pack` (сводка фактов), `template` (шаблон документа).
2. Определить `namespace`: `global`, `amfe`, `osint`, `legal`, `cases`, `lead`. Если проект не
   назван — `global` только для методов и шаблонов; факт идёт в свой проект.
3. Сформулировать одно утверждение: запись, на которую нельзя ответить «да/нет/не знаю», —
   это две записи.
4. Заполнить провенанс (навык 2), evidence (A/B/C и статус), лицензию и доступ (навык 7).
5. `add` → `merge` → `index`. Дефект: `add` возвращает exit 2 и **ничего не пишет**.

**Выход:** запись в `entries/`, строка в индексе, код `AR-NNNN`.

**Проверка:** `--check` exit 0; `search "<id>"` находит запись; в `notes` названы причина и
блокер, если `NOT_FETCHED`.

## 2. Провенанс

**Вход:** утверждение и его источник.

**Шаги:**
1. `provenance.origin` — https URL либо путь репозитория (для `INTERNAL_DOC` — только
   существующий путь).
2. `origin_type` — `OFFICIAL_LAW`, `OFFICIAL_STATISTICS`, `COMPANY_FILING`, `OPEN_WEB`,
   `INTERNAL_DOC`, `BOOK`, `DATASET`, `EXPERT_NOTE`.
3. `method` — `MANUAL_READ`, `DOCUMENTED_API`, `OFFICIAL_PORTAL`, `DERIVED`, `EXPERT_NOTE`.
4. `collected_by` — роль, `collected_at` — дата сбора (не позже `as_of`).
5. `retrieved_at` — только если данные реально получены; иначе `null` и `NOT_FETCHED`.
6. `sha256` — если есть артефакт, чья целостность важна.

**Выход:** провенанс, который можно проверить, не спрашивая автора.

**Проверка:** `INTERNAL_DOC` origin существует; URL без учётных данных; `VERIFIED` без
`retrieved_at` невозможен (код `verified_retrieved`).

## 3. Версионирование

**Вход:** исправление или обновление существующей записи.

**Шаги:**
1. Ничего не редактировать на месте: старая строка остаётся в файле.
2. Новая запись: `--supersedes AR-XXXX`, `version` = версия цели + 1 (инструмент посчитает сам).
3. Тот же `namespace` и `kind` — иначе валидатор отклонит (`supersedes_scope`).
4. У цели должно быть `archived=false`; цепочка не ветвится (`supersedes_fork`).
5. При замене обновить `as_of`, `review_due` (через `ttl_days`) и, если нужно, `evidence`.

**Выход:** цепочка `AR-0003 → AR-0021 (v2) → …`, видимая в `index.json` (`superseded_by`).

**Проверка:** `search --json` показывает `version` и `supersedes`; старые записи не исчезли.

## 4. Дедупликация

**Вход:** очередь `inbox/` и существующие записи.

**Шаги:**
1. Ключ дубля: `(namespace, kind, title)` после нормализации регистра и пробелов.
2. Тот же `id` дважды → пропуск при `merge`, ошибка при `--check`.
3. То же содержание в другом namespace — не дубль, а другая область применения: проверить,
   действительно ли знание другое.
4. `merge` не перезаписывает: дубли попадают в отчёт, а не в `entries/`.

**Выход:** отчёт «объединено N, дублей M» со списком id.

**Проверка:** `--check` без `duplicate_content`; повторный `merge` ничего не добавляет.

## 5. Тегирование

**Вход:** запись, тема, аудитория.

**Шаги:**
1. `tags`: 1–4 тега, нижний регистр, `[a-z0-9_-]`, без синонимов в одной записи
   (`osint` и `osint-scout` — разные сущности: первое тема, второе роль).
2. `audience`: роли из `x-roles` или `all`. Это не украшение: `pack --role` фильтрует по нему.
3. Не дублировать в тегах `kind` и `namespace` — они уже поля.
4. Новый тег — только если он переиспользуется: одноразовые теги ломают поиск.

**Выход:** запись, находимая `search --tag` и попадающая в пакет нужной роли.

**Проверка:** `search "" --tag <тег>` непуст; `pack --role <роль>` включает запись.

## 6. Свежесть и пересмотр (`review_due`)

**Вход:** `as_of`, `ttl_days`, дата `--today`.

**Шаги:**
1. `review_due = as_of + ttl_days`, пересчитывает код; расхождение — ошибка.
2. Классы: `fresh`, `due_soon` (≤ 30 дней), `stale` (просрочено), `UNKNOWN` (дата не передана).
3. `stale` не удаляется: пересмотр → новая версия или `archived`.
4. Правовые записи — `retention: LEGAL_HOLD`: их нельзя архивировать, пока дело не закрыто.
5. Каждый цикл: `index --today <дата>`, отчёт о просроченных Lead.

**Выход:** индекс со счётчиками свежести и списком `stale`.

**Проверка:** `index --today` назвал просроченные; `--check` не ловит `review_due_mismatch`.

## 7. Доступ и лицензия

**Вход:** происхождение записи и её аудитория.

**Шаги:**
1. `access`: `PUBLIC` (берут любые проекты), `PROJECT` (свой namespace + `global`),
   `RESTRICTED` (свой namespace и явное `--allow-restricted`).
2. `licence`: `OPEN`, `ATTRIBUTION`, `PUBLIC_DOMAIN`, `SUBSCRIPTION`, `LICENCE_REQUIRED`,
   `INTERNAL`, `NONE`.
3. `RESTRICTED` + открытая лицензия и `PUBLIC` + подписка — запрещённые комбинации.
4. `NONE` — только для `NOT_FETCHED`: «прав нет, использовать нельзя».
5. Сомнение в правах → `licence-auditor`, запись остаётся `PROJECT`/`INTERNAL`.

**Выход:** запись, которую можно законно передать в другой проект.

**Проверка:** `pack` другого проекта не содержит `PROJECT`-записей; `licence_notices` в пакете
перечисляет условия.

## 8. Сборка контекст-пакета

**Вход:** проект, тема, получатель (роль), дата, лимит.

**Шаги:**
1. `pack --project <ns> --topic "<тема>" --role <роль> --today <дата>`.
2. Видимость: свой namespace + `global` + `PUBLIC` из других проектов; `RESTRICTED` — только с
   разрешением.
3. Релевантность: совпадение темы по токенам; сортировка — совпадения, затем свежесть, затем id.
4. В пакет входят: лицензии и что можно делать, исключённые записи с причиной, пробелы.
5. `stale` исключается по умолчанию; `--include-stale` — осознанное решение.

**Выход:** `context_packs/<проект>--<тема>--<роль>.json|.md`.

**Проверка:** два запуска на одну дату дают одинаковые файлы; в пакете нет секретов; исключения
объяснены.

## 9. Передача (handoff)

**Вход:** пакет и вопрос получателя.

**Шаги:**
1. Передавать файл пакета, а не пересказ: пересказ теряет провенанс, лицензию и исключения.
2. В сообщении: проект, тема, роль, дата, сколько записей, какие пробелы, что запрещено делать
   с записями (лицензия).
3. Получатель не «дополняет» пакет по памяти: новое знание — новая запись, а не правка пакета.
4. После работы получатель возвращает: что использовал, чего не хватило (пробелы в архив).

**Выход:** пакет + короткое сопровождение.

**Проверка:** получатель может назвать `id`, `origin` и лицензию каждой использованной записи.

## 10. Хранение (retention)

**Вход:** характер знания.

**Шаги:**
1. `TTL` — факт-пак, живёт до `review_due`; по истечении — новая версия.
2. `PROJECT` — знание проекта, живёт до конца проекта.
3. `PERMANENT` — методы, шаблоны, карточки источников: не выводятся.
4. `LEGAL_HOLD` — правовые рамки и доказательства: `archived=true` запрещён.
5. Удаления нет вообще: только `archived=true` (история сохраняется).

**Выход:** политика хранения в каждой записи и в `index.md`.

**Проверка:** `--check` не ловит `legal_hold_archived`; `archived`-записи не попадают в пакеты.

## 11. Межпроектные namespace

**Вход:** проект-получатель и проект-владелец знания.

**Шаги:**
1. `global` — методы, стандарты, шаблоны: читают все, пишет архивариус.
2. `amfe`, `osint`, `legal`, `cases`, `lead` — знания проекта; чужие `PROJECT`-записи не видны.
3. Перенос знания в другой проект — не копирование файла, а `PUBLIC`-доступ или новая запись со
   своим namespace и ссылкой на оригинал.
4. Новый namespace добавляется в `schema.json` (`x-namespaces`) с владельцем и описанием;
   самовольные namespace валидатор отклоняет.
5. Пересечение тем решается тегами, а не дублированием записи в двух namespace.

**Выход:** чистая граница проектов и отсутствие «теневых копий».

**Проверка:** `pack` для проекта не содержит чужих `PROJECT`-записей; `--check` не ловит
`namespace_unknown`.

## 12. Кому какой контекст (готовые рецепты)

### OSINT (`osint-scout`)

```powershell
python tools/archivist.py pack --project osint --topic "законный сбор источники" `
    --role osint-scout --today 2026-11-22
```

Пакет даёт: границы сбора, классы источников, журнал коллекции. Перед сбором `osint-scout`
обязан прочитать исключения (`excluded`) — они объясняют, почему часть знаний недоступна.

### Legal (`legal-claim`)

```powershell
python tools/archivist.py pack --project legal --topic "доказательства давность" `
    --role legal-claim --today 2026-11-22
```

Пакет даёт: правовые рамки-указатели, шаблон доказательственной карточки, правило «норма только
из первоисточника». `NOT_FETCHED` здесь означает «юрист ещё не проверил», а не «нормы нет».

### Case (`case-writer`)

```powershell
python tools/archivist.py pack --project cases --topic "факт-пак" `
    --role case-writer --today 2026-11-22
```

Пакет даёт: факт-паки с evidence и границы переноса фактов в кейс: цифры без первоисточника в
кейс не переносятся.

### Lead

```powershell
python tools/archivist.py pack --project lead --topic "передача контекста ограничения" `
    --role lead --today 2026-11-22
```

Пакет даёт: правило handoff через пакет, ограничения среды (нет сети, нет лицензий, нет
`VERIFIED`) и открытые вопросы к Lead.
