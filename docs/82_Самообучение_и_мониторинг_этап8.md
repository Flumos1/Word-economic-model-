## 1. Что реализовано

| Модуль | Содержание |
| --- | --- |
| `versions.py` | версии моделей/весов с идентификатором, привязанным к хешу кода и снапшоту весов; append-only журнал с хеш-цепочкой (`VERSION`, `SWITCH`, `ROLLBACK`, `UPDATE`, `DECISION`, `NOTE`); откат к предыдущей версии |
| `metrics.py` | rolling MAE/RMSE/CRPS/Brier, EWMA-карта, CUSUM (Page), Page-Hinkley; HAC long-run sigma для автокоррелированных рядов |
| `drift.py` | дрейф данных (KS, PSI, сдвиг среднего, отношение дисперсий), дрейф концепта по ошибкам и по изменению связи «вход → цель» (Fisher z) |
| `decision.py` | решающее правило «кандидат против действующей версии» по замороженной логике C1/C2; `PROMOTE / HOLD / REJECT / INSUFFICIENT_DATA`; автоматический откат (`ROLLBACK`) |
| `contours.py` | быстрый контур (оценки состояния, скалярный фильтр Калмана), медленный контур (параметры/веса, обратно-квадратичные веса), шлюз допустимости наблюдений |
| `loop.py` | сквозной цикл: наблюдение → шлюз/контуры → дрейф → решение → журнал |

Ключевой принцип: слой мониторинга **не обучает модели**. Он решает, можно ли обновить/переключить
версию, и фиксирует это в аудите; сама модель поставляет прогнозы через свой слой.

## 2. Версионирование и журнал

- `ModelVersion` — неизменяемая версия: `version_id`, `model_id`, `code_hash`, `weights`
  (+`weights_hash`), `code_commit`, `data_vintage_hash`, `parent_version_id`, `metadata`.
- `version_id = <model_id>@<code_hash[:12]>+<weights_hash[:8]>`: версия однозначно привязана к коду
  и весам. Изменение кода или весов даёт новый id — «незаметно переписать» версию нельзя.
- Журнал (`VersionJournal`) — append-only с хеш-цепочкой: `prev_hash` + `entry_hash` каждой записи.
  Загрузка проверяет цепочку, поэтому правка/удаление строки обнаруживается (`VersionError`).
- Переключение (`SWITCH`) хранит `previous_active`, веса и число наблюдений; откат (`ROLLBACK`)
  возвращает на предыдущую версию и тоже записывается отдельной строкой. `DECISION` и `UPDATE`
  — аудит без смены действующей версии (решения об отказе, обновления медленного контура).
- Журнал можно вести в памяти (тесты, синтетика) или в JSONL-файле (рабочий режим). Формат —
  канонический JSON, LF.

## 3. Метрики и детекторы деградации

Формулы потерь совпадают с замороженным harness (это проверяется тестом):

- MAE = mean |y − ŷ|; RMSE = sqrt(mean (y − ŷ)²);
- CRPS = 2 × средний pinball по 19-квантильной сетке 5%…95% с шагом 5%;
- Brier = mean (p − 1[event])²; log score с обрезкой вероятностей в [0.01, 0.99].

Детекторы:

| Детектор | Что ловит | Калибровка |
| --- | --- | --- |
| EWMA-карта | медленный сдвиг среднего | `alpha=0.2`, порог 3–4σ по steady-state пределу; для автокорреляции σ берётся как HAC long-run sigma |
| CUSUM | устойчивый сдвиг среднего на `delta` σ | reference k = delta/2, решение h = 10 (≈ ARL₀ тысяч наблюдений) |
| Page-Hinkley | накопленное отклонение в выбранном направлении | статистика `(m_t − min m)/sqrt(t)` (брауновская шкала), порог 3.5 ≈ 1% ложных срабатываний на сотнях наблюдений |

`long_run_sigma` (HAC, Bartlett-kernel) обязательна для макро-рядов: без неё CUSUM/EWMA на AR(1)
дают ложные срабатывания на самой автокорреляции. Тесты проверяют оба свойства: **отсутствие
ложных срабатываний** на i.i.d. и AR(1) (по 20 фиксированным seed) и **обнаружение структурного
сдвига** в пределах нескольких десятков наблюдений. Дефолтные пороги — стартовая точка; в рабочем
режиме они калибруются под целевой ARL₀.

## 4. Дрейф данных и концепта

- **Дрейф данных**: на каждый признак — KS (p < 0.05), PSI (≥ 0.2), сдвиг среднего (Welch z).
  Признак считается сдвинутым, если согласуются ≥ 2 методов из 3 (`min_votes`); это снижает
  одиночные ложные срабатывания на коротких окнах.
- **Дрейф концепта по ошибкам**: KS + сдвиг среднего + отношение дисперсий ошибок между
  референсным и свежим окном (≥ 2 голоса).
- **Дрейф связи**: тест Фишера на изменение корреляции «вход → цель» с порогом `delta ≥ 0.3`.
- `DriftMonitor` хранит референсные окна; после контролируемого обновления референс
  перебазируется **явно** (`shift_reference`), а не автоматически — иначе дрейф «исчезал» бы сам.

## 5. Решающее правило и автоматический откат

`SwitchRule.evaluate(candidate_losses, active_losses, target, observations)` — чистая функция,
повторяющая логику допуска:

- **C1-логика**: относительная потеря (кандидат/действующая) ≤ порог из
  `protocols/nf_sim_thresholds.json` для каждой применимой потери;
- **C2-логика**: односторонний GW/DM (единственный инструмент — константа), HAC h−1,
  поправка HLN, p < 0.10, для каждой потери;
- переключение — только если оба условия выполнены для всех потерь и наблюдений
  ≥ `MIN_OBSERVATIONS = 12` (минимум C6 журнала будущих прогнозов);
- если кандидат значимо хуже (обратная односторонняя альтернатива p < 0.10 и относительная потеря
  > 1) — `REJECT`; если неразличим — `HOLD`; без наблюдений — `INSUFFICIENT_DATA`.

**Порог C1 для рабочего мониторинга.** NF-SIM-таблица заморожена для окон W1/W2, а forward-окно
журнала в исследовании не участвовало. Правило берёт **более строгий** из порогов W1/W2 для пары
(target, horizon, loss) — консервативный выбор, задокументированный в коде; для исследовательских
сравнений можно передать `threshold_override`. Вопрос порога для forward-окна — открытый пункт
протокола v5.

`RollbackController`: `consider()` продвигает кандидата только по `PROMOTE` и пишет `SWITCH`;
`auto_rollback_check()` сравнивает действующую версию с предшественницей и при её преимуществе
выполняет `ROLLBACK` на предшественницу. Повторный вызов при уже совершённом действии возвращает
`NOOP` и **не пишет** новых строк (идемпотентность). Откат без наблюдений не выполняется.

## 6. Быстрый и медленный контуры, запрет обновления без наблюдений

- `ObservationGate` — шлюз допустимости: обновления разрешены только для `REAL_TIME`
  (опционально — с обязательным `vintage_hash`); `PSEUDO_REAL_TIME`, `CONTAMINATED`, помеченные
  недопустимыми или нечисловые наблюдения отклоняются и считаются. Это исполнение docs/41 A04.
- `FastContour` — на каждое допустимое наблюдение обновляет оценки состояния (скалярный
  Калман). Недопустимые наблюдения не меняют состояние; пустой пакет → `updated=False`.
- `SlowContour` — параметры/веса только после `min_observations=12` допустимых наблюдений, через
  интерфейс `WeightUpdater` (синтетическая реализация `InverseMSEWeights`: веса ∝ 1/средняя
  потеря). Повторная подача того же пакета → `updated=False` («нет новых наблюдений»), веса не
  меняются; нулевые наблюдения → обновления нет.
- `ContourCoordinator` — маршрутизация: шлюз → быстрый контур → (периодически) медленный контур;
  обновления медленного контура пишутся в журнал (`UPDATE`, scope `SLOW_CONTOUR`).

## 7. Интеграция с harness и границы

- Формулы DM/GW-теста и порогов C1 в мониторинге **тождественны** замороженному
  `tools/evaluate.py`; это проверяется тестом «DM mirrors the frozen harness» на случайных рядах.
  `tools/evaluate.py` не изменялся.
- На стадии допуска работает harness C1–C6 (на исторических окнах); мониторинг этапа 8 работает
  на forward-потоке после допуска. Оба используют один и тот же язык потерь.
- **Границы:** рабочая (не синтетическая) модель ещё не допущена; forward-журнал пуст; порог C1
  для forward-окна формально не заморожен (используется более строгий W1/W2); детекторы
  дрейфа и ARL-пороги нужно калибровать на реальных остатках; медленный контур обучается только
  на допустимых наблюдениях и не может переписывать учётные тождества или замороженный протокол;
  смена версии не является решением о допуске — это follow-up эксплуатации, требующий отчётности
  (docs/41 §8).
- C4 (рецессионные месяцы) в мониторинг не переносится: это свойство исторического допуска, а не
  рабочего потока.

## 8. Запуск

```powershell
python -m unittest tests.test_monitoring -v
```

Тесты покрывают: детерминизм и привязку версий к коду/весам, хеш-цепочку и обнаружение подмены,
идемпотентность регистрации, переключение и откат (в т.ч. к явной версии), персистентность журнала,
rolling-метрики и точные формулы CRPS/Brier, EWMA/CUSUM/Page-Hinkley (обнаружение сдвига и
отсутствие ложных срабатываний на i.i.d. и AR(1)), дрейф данных/концепта/связи, пороги из
замороженной таблицы, совпадение DM-формулы с harness, `PROMOTE`/`HOLD`/`REJECT`/
`INSUFFICIENT_DATA`, автоматический откат, шлюз допустимости, оба контура, сквозной цикл
«промоушен → деградация → откат» с проверкой целостности журнала.
