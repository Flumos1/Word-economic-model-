# 224. Gated-источники: практический гид по законному доступу

Дата: 2026-11-22. Роль: `osint-scout`. Статус: **RESEARCH_ONLY, admission=false**, режим сети
**`OSINT_ONLY`** (`subscriptions = 0`). Это гид по **распознаванию** gated-источников и **запросу
доступа**, а не по их обходу. Правовая рамка — [docs/212](212_Агентная_сеть_market_intelligence.md),
плейбуки — [`gated_sources.md`](../agents/market_intelligence/playbooks/gated_sources.md) и
[`access_request.md`](../agents/market_intelligence/playbooks/access_request.md).

Главная мысль: «условно закрытый» — не значит «недоступный» и не значит «надо открыть». Это значит,
что у источника есть **законный путь**: подписка, institutional/academic license, FOIA/public
records, судебный реестр, закупочный портал, data room по NDA, API с ключом. Агент определяет класс,
оформляет запрос, а решает человек.

## 1. Пять классов за минуту

| Класс | Признак | Пример | Что делает агент |
|---|---|---|---|
| **G0** | открыто, без логина | годовой отчёт, пресс-релиз, публичный судебный реестр | читает, цитирует, ставит ссылку и дату |
| **G1** | бесплатная регистрация организации | закупочный портал, реестр, бесплатный API | проверяет ToS, логин берёт у человека |
| **G2** | платно или по договору | ценовая БД, терминал, платный отчёт, платный API | готовит access request, статус `REQUEST_PENDING` |
| **G3** | по NDA и правилам комнаты | data room сделки, due diligence | готовит access request, NDA подписывает человек |
| **G4** | доступа не существует | утёкшие базы, чужие аккаунты, инсайд | `NOT_AUTHORIZED` + `NOT_FETCHED`, не трогает |

Класс G — про **доступ**, класс S (`source_hierarchy.md`) — про **силу источника**: G0/G1 это
S1–S3, G2/G3 это S4, G4 это S5. Договор расширяет доступ, но grade не повышает: потолок
`osint-scout` остаётся `PARTIAL`, `VERIFIED` подписывает `evidence-qa`.

## 2. Дерево решения

```text
нашли источник
  ├─ открыт без логина?                         -> G0: robots/ToS -> собираем
  ├─ бесплатная регистрация по ToS?             -> G1: ToS -> логин у человека -> собираем
  ├─ платно / по договору / по license?         -> G2: access request -> REQUEST_PENDING
  ├─ data room по NDA?                          -> G3: access request -> NDA у человека
  └─ нет законного пути (слив, чужой аккаунт)?  -> G4: NOT_AUTHORIZED, не трогаем
```

Если класс неясен — считаем G2/G3 и **не собираем** до прояснения. Сомнение трактуется в пользу
ограничения, а не доступа.

## 3. По типам источников

### 3.1 Публичные реестры (G0/G1)

Регистрационные, разрешительные, судебные реестры обычно публичны, но правила цитирования и
персональные данные в них различаются по юрисдикции. Что делать: проверить ToS, брать только
корпоративные данные, не вытаскивать ФИО частных лиц, фиксировать URL и дату. Если реестр платный —
это G2, а не «реестр с хитростями».

### 3.2 Судебные реестры

Публичное решение суда — G0; картотека с платным доступом — G2. Персональные данные из решений не
переносим: нужны факты о компаниях и спорах, а не досье на людей. Цитата — <= 300 символов,
номер дела и дата обязательны.

### 3.3 Закупки и тендеры (G0/G1/G2)

Публичные тендерные публикации — G0/G1. Закрытая часть после аккредитации — G2: оформляется
access request, аккредитацию проходит человек. Данные о закупках используем как контекст TCO, а не
как «доказательство» связи компаний.

### 3.4 Санкционные списки и бенефициары (G0)

Санкционные списки регуляторов и публичные реестры бенефициаров — открытые источники. Ограничение
фиксируется как ограничение, а не как задача поиска обходного пути. Спорная юрисдикция — стоп и эскалация к
`director`, юридическую оценку даёт человек.

### 3.5 FOIA / public records

Это законная процедура запроса публичного документа у органа власти, а не доступ к закрытой базе.
Агент готовит черновик: орган, предмет, период, формат; отправляет человек. Отказ — `NOT_AUTHORIZED`,
а не повод искать «слив». Сроки ответа зависят от юрисдикции; в журнале фиксируем дату запроса и
решения.

### 3.6 Лицензированные API (G2)

Ключ выдаёт человек и хранит в секрет-сторе; в репозитории, отчёте и памяти агента ключа нет.
Проверяем: что разрешено договором (лимиты, производные, передача клиенту), до какой даты, можно ли
цитировать. Без договора API — `NOT_FETCHED` с блокером «нужна лицензия», даже если эндпоинт
отвечает.

### 3.7 Data room по NDA (G3)

Доступ открывает человек после NDA. Правила комнаты читаем до входа: что можно скачивать, что
цитировать, сколько хранить. Цитата — только с разрешения; полные документы в репозиторий не
попадают. Нарушение правил комнаты — стоп-сигнал, а не «мелкая формальность».

## 4. Access request: что писать

Шаблон — [`access_request.md`](../agents/market_intelligence/playbooks/access_request.md). Минимум:

1. **кто** — роль и владелец запроса, без имён и личных контактов;
2. **источник** — название, владелец, URL/идентификатор, класс G2/G3;
3. **правовое основание** — договор/NDA/license/FOIA/ToS: номер, дата, сторона;
4. **цель** — какой решение-релевантный подвопрос закрываем;
5. **срок** — с какой по какую дату, когда пересматриваем;
6. **что не копируем** — полные тексты, сырые выгрузки, персональные данные, лишнее из data room;
7. **как храним** — цитаты <= 300 символов и агрегаты; сырые данные вне git;
8. **ключи** — выдаёт человек, в запросе не указываются.

Маршрут: `osint-scout` → `director` → Lead/человек (юрист, закупки, подписант) → поставщик.
Агент не отправляет запрос, не подписывает договор и не принимает NDA.

## 5. Журнал доступа

Одна строка на gated-источник: `request_id`, `role`, `source`, `gated_class`, `legal_basis`,
`purpose`, `requested_at`, `decision`, `decided_at`, `expires_at`, `owner`. В журнале нет ключей,
токенов, логинов, персональных данных и содержимого data room. Изменение срока — новая строка;
старые не удаляются.

Зачем: журнал доказывает добросовестность и позволяет `evidence-qa` воспроизвести вывод. Без него
нельзя отличить «доступ был законным» от «доступ был».

## 6. `NOT_AUTHORIZED`: нормальный результат

Примеры:

```text
Gated: source="Price DB", class=G2, status=NOT_AUTHORIZED, reason="договора нет; поставщик
отказал 2026-11-25", blocker="нужна подписка", used=false
NOT_FETCHED: ценовой бенчмарк 2026 — доступа нет; открытая аннотация даёт только диапазон S3/B.
```

```text
Gated: source="Settlement data room", class=G3, status=NOT_AUTHORIZED, reason="NDA не подписан,
доступ не открыт", blocker="нужен NDA", used=false
NOT_FETCHED: детали сделки — только публичный пресс-релиз S2, остальное не проверено.
```

Запрещено: подставлять «похожие» числа из S3 и называть их данными G2, скрывать отказ, повторять
запрос в обход решения, просить коллегу «посмотреть под своим логином».

## 7. Что делает инструмент

```powershell
python tools/market_intel.py --check
python tools/market_intel.py --json          # gated: collect_now/request_only/never
python tools/market_intel.py --org
python tools/market_intel.py --access-request --source "Price DB" --gated-class G2 `
    --purpose "проверка CAPEX-бенчмарка" --legal-basis "NDA от 2026-11-20" --out .tmp/request.md
```

`--check` проверяет классы G0–G4, статусы, журнал, запрет обхода, `credentials.in_repo = false`,
наличие плейбуков и отсутствие credential-подобных значений. `--access-request` отказывает для G0
(запрос не нужен), G4 (нет законного пути) и неизвестного класса; в тексте запроса нет контактов,
ключей и обещаний допуска модели.

## 8. Чек-лист

Перед сбором:

- [ ] класс G0–G4 определён и записан;
- [ ] для G0/G1 проверены robots/ToS/лимиты;
- [ ] для G2/G3 есть договор/NDA или оформлен access request;
- [ ] для G4 — только `NOT_AUTHORIZED`;
- [ ] правовое основание и срок известны;
- [ ] ключи вне репозитория, персональных данных нет.

Перед сдачей:

- [ ] у каждой gated-строки есть класс, статус и запись в журнале;
- [ ] нет обхода paywall/авторизации/NDA/robots/лимитов;
- [ ] `NOT_AUTHORIZED` и `NOT_FETCHED` заполнены с причиной и блокером;
- [ ] цитаты в разрешённом объёме, полных текстов нет;
- [ ] в отчёте есть `mode: osint (OSINT_ONLY)` и строка «gated: проверено».
