## 3. Покрытие (из отчёта инструмента)

```
by status:  ADAPTER_READY 1, UNAVAILABLE 9, RESTRICTED 8, NOT_FETCHED 8
by target:  CPI 6, GDP 17, UNRATE 1, RECESSION 2
by licence: OPEN 11, OPEN_ATTRIBUTION 7, RESTRICTED 8 (UNVERIFIED 0)
by mapping: EXACT 3, PENDING 14, NONE 9
by freq.:   DAILY 1, WEEKLY 1, MONTHLY 8, QUARTERLY 10, SEMIANNUAL 4, IRREGULAR 2
ready targets: GDP = да; CPI, UNRATE, RECESSION = нет
```

Отсюда три честных вывода:

1. **Каталог широкий, оценка узкая.** 26 источников и 3 `EXACT`-мэппинга (SPF GDP, NY Fed,
   GDPNow); из них scorable только один — остальные два заблокированы архивом и лицензией.
2. **`UNRATE` — дыра протокола, а не реестра.** В v5 цели: T1 CPI, T2 GDP, T3 рецессия.
   Прогнозы безработицы (SPF, FOMC SEP, CBO, NABE, EC) каталогизированы, но скорить их не на что;
   добавление цели — изменение протокола, а не запись в реестр.
3. **`PENDING` (14 источников) — это решения, которые нельзя протащить через реестр.**
   Годовые, Q4/Q4, HICP/PCE и «условные» прогнозы (BoE) не равны квартальной annualized цели;
   чтобы их скорить, нужен зарегистрированный мэппинг, то есть смена цели. Реестр это фиксирует,
   а не замазывает.

## 4. Почему часть источников `NOT_FETCHED` (и почему это не «забыли»)

`NOT_FETCHED` — не ошибка и не лень: это состояние «лицензия позволяет, но данных в проекте нет,
и цитировать оттуда нечего». Причины по группам:

| Причина | Источники | Что нужно, чтобы сдвинуть |
|---|---|---|
| `MAPPING_PENDING` | FOMC SEP, CBO, BoE MPR | зарегистрировать мэппинг Q4/Q4 → квартальная annualized (или годовая) цель: это решение по протоколу, а не по реестру |
| `PUBLIC_ARCHIVE_NOT_FETCHED` | IMF WEO, OECD EO, World Bank GEP, EC ECFIN, ECB SPF | скачать публичный винтаж, записать условия в `licence_register.json`, зарегистрировать мэппинг (годовая сетка ≠ квартальная) |

`UNAVAILABLE` — тоже не «нет данных вообще», а конкретный блокер:

| Причина | Источники | Блокер |
|---|---|---|
| `ARCHIVE_NOT_LOCAL` | NY Fed | адаптер и схема архива готовы (`data/raw/ny_fed/nowcast.csv`), архива в репозитории нет |
| `NO_PROTOCOL_HORIZON_MAPPING` | SPF CPI (1yr/10yr), Cleveland | публикуется не y/y на t−1+h: пересчёт m/m→y/y или «ожидание на год» меняет цель |
| `NO_EVENT_PROBABILITY_MAPPING` | SPF Anxious Index | событие «падение реального GDP», а T3 — месяц NBER-рецессии: разные события |
| `NO_PROTOCOL_TARGET_MAPPING` | SPF UNRATE, NY Fed SCE, Michigan, Dallas, Kansas City | нет цели в протоколе либо это региональный/потребительский индекс, а не прогноз цели |

`RESTRICTED` — 8 источников, и это не «мы не смогли»: подписка (Blue Chip, Consensus, EIU),
членство (NABE), news-terms без архива (Reuters, WSJ), лицензия на исторический ряд
(Conference Board) и прямой запрет (GDPNow: «personal and educational use only»). Значения не
читаются даже при наличии локальной копии — это закреплено тестом v1-scorecard и повторено здесь
в правилах реестра.

## 6. Что это меняет в оценке

**Пока ничего.** Явно:

* `protocols/external_forecast_scorecard.json` не перегенерировался и не менялся; его
  `content_sha256 = 183a07caf412d091…` остаётся прежним;
* статус scorecard остаётся `PARTIAL` с причиной `SCORED_SOURCES_BELOW_CRITERION(1<3)`;
* C1–C6, стадии и допуск не затрагиваются: реестр — диагностический артефакт, не admission;
* ни одна цифра RMSE/MAE/bias/CRPS/Brier не появилась: для новых источников нет ни данных,
  ни разрешённых значений.

Что изменится, когда появится второй и третий scorable-источник:

1. `tools/external_forecast_scorecard.py` получит адаптер и `SOURCE_SPECS`-запись, реестр —
   `ADAPTER_READY` с непустым `data_path`;
2. scorecard перегенерируется, `status` станет `OK` при ≥3 источниках и ≥50 общих PIT-точках;
3. только тогда имеет смысл «внешние vs наши» (C6-журнал, R3-ансамбль) и API `/v1/external-forecasts`.

## 7. Как добавить источник (порядок, который не ломает честность)

1. **Запись в реестр.** Добавить объект в `sources` со статусом `NOT_FETCHED`,
   `adapter_state: "PLANNED"`, осмысленным `adapter` (например `imf_weo_csv`), `url`,
   `publication.vintage_policy` и `notes`. Валидатор не даст поставить `ADAPTER_READY` без
   адаптера, локального пути и записи в реестре лицензий.
2. **Лицензия.** Проверить условия на дату и добавить запись в `protocols/licence_register.json`
   (`OPEN` / `RESTRICTED` / `UNVERIFIED`). Если условия не проверены — `UNVERIFIED`, и тогда
   статус обязан быть `RESTRICTED`; значения не читаются.
3. **Адаптер.** В `tools/external_forecast_scorecard.py` — класс по образцу `SpfAdapter`:
   строгая схема локального файла, дата публикации на каждую строку, гейт `pit_gate`,
   отказ при `publication_date > origin`, никакой подстановки плотности/вероятности.
   Тесты — с инъекцией таблицы (`FixedTable…`), чтобы не зависеть от git-ignored данных.
4. **Данные.** Скачать публичный винтаж в `data/raw/<source>/…` (git-ignored), зафиксировать
   SHA-256 в `values_file`, добавить `data_path` в реестр.
5. **Флип статуса.** `NOT_FETCHED` → `ADAPTER_READY` только когда шаги 1–4 сделаны;
   `mapping` — `EXACT` только если величина совпадает с протокольной. Иначе сначала
   регистрируется мэппинг (протокол), и лишь потом статус.
6. **Прогон.** `python tools/external_scorecard_v2.py --check` (0), `python tools/external_forecast_scorecard.py`
   (перегенерация scorecard), `python tests/test_external_forecast_scorecard.py`,
   `python tests/test_external_scorecard_v2.py`, затем обновить docs/174 и этот документ.

Правило-предохранитель: **нельзя** получить `ADAPTER_READY` правкой одного поля. Нужны адаптер,
запись лицензии и локальный путь — три независимых объекта, каждый со своим тестом.

## 8. Воспроизведение и CI

```powershell
python tools/external_scorecard_v2.py --check                 # валидация + сводка, exit 0 (PARTIAL)
python tools/external_scorecard_v2.py --check --strict        # exit 3, пока ready < 3
python tools/external_scorecard_v2.py --json                  # полный отчёт в stdout
python tools/external_scorecard_v2.py --md --out <tmp>.md     # Markdown-отчёт
python tools/external_scorecard_v2.py --out <tmp>.json        # JSON-отчёт
python tests/test_external_scorecard_v2.py                    # 46 тестов, офлайн, ~0.25 с
```

Коды выхода: `0` — реестр валиден (даже если `PARTIAL`); `2` — реестр невалиден, артефакт не
пишется (fail-closed); `3` — `--strict` и покрытие ниже критерия. Детерминизм: инструмент не
читает часы и не пишет `generated_at`, два прогона дают побайтово одинаковый JSON/Markdown;
`content_sha256` покрывает отчёт целиком, кроме себя. Сети нет: в модуле нет
`urllib`/`requests`/`socket`/`http.client`, это отдельный тест.

## 9. Ограничения (что не проверено)

1. **Условия использования не перепроверялись в этом прогоне.** Инструмент офлайн, поэтому
   `licence.status` — это либо запись `licence_register.json` (7 источников), либо
   консервативное чтение публичных условий. Перед первой загрузкой данных условия проверяются
   и фиксируются датой в реестре лицензий; до этого источник остаётся `NOT_FETCHED`/`RESTRICTED`.
2. **URL — указатели, а не доказательство доступа.** Для части провайдеров дан корневой адрес
   (подписка/витрина), потому что конкретная страница отчёта меняется; это отмечено в `notes`.
3. **`PENDING`-мэппинги не реализованы** — это честно не сделано, а не «сделано приблизительно».
4. **Реестр не является scorecard.** Он не содержит ошибок и не заменяет
   `protocols/external_forecast_scorecard.json`.
5. **20+ — про каталог.** По критерию docs/173 (≥3 скорированных источника) прогресса нет;
   прогресс есть по критерию P-003 «20+ внешних источников в едином реестре».
