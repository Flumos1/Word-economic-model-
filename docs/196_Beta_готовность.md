# 196. Beta-готовность AMFE 2.0 (G6-prep): аудит

Дата аудита: 2026-11-20. Волна 26, трек «beta readiness». Инструмент —
[tools/beta_audit.py](../tools/beta_audit.py), тесты — [tests/test_beta_audit.py](../tests/test_beta_audit.py),
машиночитаемый отчёт — `build/beta_audit/report.json`, сводка — `build/beta_audit/report.md`.
Аудит **только читает** артефакты и документы; он не активирует предрегистрацию, не подписывает
документы и не меняет статусы.

## 1. Вердикт

**`BETA_NOT_READY` — beta 2.0 сейчас выпускать нельзя.** Не из-за качества продуктов (API v2, Client
Pack v2, FLAKS MVP и Simulator UI существуют и проходят тесты), а из-за трёх блокеров:

1. **G4 не пройден**: предрегистрация 0.3 в статусе `PROPOSED` (нужна активация владельцем-человеком);
2. **G4 не пройден**: независимая V2-оценка пакета docs/170 — **`NOT_CONFIRMED`** (docs/172);
3. **C6 не выполнен**: 0/12 разрешённых прогнозов и 1/4 различных периодов (`NOT_MET`).

Плюс шесть средних замечаний (не блокируют технически, но запрещают часть публичных claims):
неполный реестр источников (10 из 15 не `VERIFIED`), отсутствие человеческих подписей для G5/G6,
задокументированное исключение в политике «сырых данных» (EIA Brent series в git) и отсутствие
собранного beta-пакета.

## 4. Средние замечания (MEDIUM): что нельзя заявлять

1. **Источники**: 10 из 15 записей реестра — `CATALOGUED` (6) / `NOT_DOWNLOADED` (4);
   `VERIFIED` — 3, `ACCESS_VERIFIED` — 2 (итого 5 проверенных). Нельзя писать, что «все данные проверены».
2. **Подписи**: подписан только G4 (docs/160). Для G5 и G6 человеческих подписей нет.
3. **Сырые данные**: политика «сырые данные не в git» имеет задокументированное исключение — ряд
   EIA Brent (`data/oil/brent_monthly_eia.csv` + meta) закоммичен (public domain). Формулировка
   «в git нет сырых данных» была бы ложной; корректно: «единственное исключение — EIA Brent series
   с meta-файлом и записью в реестре лицензий».
4. **Beta-пакет**: `build/beta` отсутствует; релиз 2.0 не собран и не подписан.
5. **release_check**: на момент аудита — `CONDITIONAL`, 0 блокеров, 2 warning'а
   (`frozen.r2_gate_fact`, `reports.references_current`); это не блокер beta, но чеклист релиза не
   зелёный. README/docs/164 на 20.11 обновлены; G4-строка всё ещё требует активации prereg и
   перевыпуска V2 — это факт, а не устаревший текст; при следующем обновлении статуса
   docs/164 и README нужно синхронизировать повторно.

## 6. Что нужно для beta (порядок действий)

1. **Владелец**: решение по prereg 0.3 (docs/199) — активировать / оставить PROPOSED / выпустить
   0.4. Только человек; агент не активирует.
2. **G4**: перевыпуск пакета docs/170 с настоящими обязательными срезами и повторная независимая
   V2-проверка; после этого — активация prereg и пересборка оценки.
3. **C6**: продолжать недельный журнал до 12 разрешённых прогнозов и 4 различных периодов; это
   календарное ограничение, а не задача разработки.
4. **G5**: независимое ревью продуктового слоя (по образцу docs/160) + человеческая подпись.
5. **Beta-пакет**: собрать `build/beta`, зафиксировать состав, ограничения и статусы, подписать.
6. **Данные**: довести реестр источников до `VERIFIED` для тех, чьи числа попадут в клиентские
   материалы; зафиксировать политику по EIA-исключению.
7. **Документы**: после закрытия пунктов 1–6 обновить README/docs/164 и пересобрать этот аудит.

## 7. Ограничения аудита

- Это **чек-лист**, а не пересчёт моделей: числа G1–G5 берутся из артефактов и внешних ревью
  (docs/160, docs/168), экономическая валидность заново не выводится.
- Продуктовые тесты и `release_check` запускаются только по флагу; их результат — снимок рабочего
  дерева на момент аудита и может меняться при параллельных коммитах.
- Аудит не активирует prereg, не подписывает и не меняет статусы; решение о beta принимает человек.
- «Готовность» здесь — формальная (артефакты, статусы, подписи, блокеры), а не оценка
  коммерческого спроса или качества сценариев.

## 8. Воспроизведение

```powershell
# полный аудит (запускает продуктовые тест-сьюты; ~45 с)
python tools/beta_audit.py

# быстрый снимок без тестов и без release_check
python tools/beta_audit.py --no-tests --json

# с дополнительным прогоном release_check (read-only, во временную папку)
python tools/beta_audit.py --no-tests --release-check

# тесты самого аудита (23 теста: структура, false PASS, fail-closed, детерминизм, CLI)
python tests/test_beta_audit.py
```

Снимок волатилен: параллельные треки меняют docs/164, README и реестр источников; пересобирать
аудит перед каждым решением по beta.

Выход: `build/beta_audit/report.json` + `report.md`; коды: `0` — аудит выполнен (вердикт может быть
`BETA_NOT_READY`), `2` — fail-closed (обязательный вход отсутствует, ничего не пишется).
Детерминизм: дата аудита задаётся явно, часы не читаются; одинаковые входы дают одинаковый digest.

## 9. Итог

**Beta 2.0 не готова, и это не техническая проблема продуктов.** Продуктовый слой G5 существует и
проходит тесты; закрыты G1–G3. Осталось то, что нельзя ускорить разработкой: активация
предрегистрации (решение владельца), подтверждённая независимая V2 и календарное накопление C6.
До этого допустимые формулировки: «research-платформа с прототипами продуктов, G1–G3 закрыты,
G4 заблокирован, beta не готова». Недопустимые: «beta 2.0 готова», «модель допущена», «C6 пройден»,
«все данные проверены», «в git нет сырых данных».
