# 195. Двигатель предложений L-2/L-3 (G6-prep)

Дата: 2026-11-20. Волна 26 (G6-prep), задача `task-57`, пункт docs/173 P1 #14. Статус:
**прототип структурного/методологического обучения; человек утверждает, система не меняет
архитектуру и не присваивает допуск.** Файлы:
[src/amfe/learning/proposals.py](../src/amfe/learning/proposals.py),
[tools/proposal_engine.py](../tools/proposal_engine.py),
[tests/test_proposals.py](../tests/test_proposals.py) (17 тестов). Журнал:
`build/registry/proposals.jsonl` (генерируемый артефакт, в git не коммитится).

## 1. Что это и чего это не делает

L-1 (Q-функция, walk-forward, реестр моделей, docs/151) уже есть. L-2/L-3 — это **предложения**:
новые связи, режимы, методы/эксперименты. Двигатель:

* читает **фактические** артефакты проекта (без LLM, без сети);
* превращает сигналы в структурированные предложения (`PROPOSED`) с обоснованием и оценкой;
* пишет их в append-only журнал и останавливается.

Чего он **не делает**: не меняет код, протоколы, frozen-файлы, архитектуру модели; не переводит
предложения в `APPROVED`; не запускает предложенные эксперименты; не принимает решений за человека.

## 2. Схема предложения (`AMFE-PROPOSAL/1.0.0`)

Одно событие = каноническая JSON-строка (`sort_keys`, компактные разделители, LF, `event_id` =
SHA-256 содержимого). Действия: `REGISTER → APPROVE | REJECT → IMPLEMENT`.

| Поле | Тип | Смысл |
|---|---|---|
| `proposal_id` | hex16 | детерминированный id: sha256(kind, dedupe_key, title, evidence_sha256)[:16] |
| `kind` | enum | `NEW_LINK` / `NEW_REGIME` / `NEW_METHOD` / `DATA_GAP` |
| `title`, `rationale` | str | формулировка и обоснование |
| `evidence` | object | правило + значения сигналов + путь артефакта |
| `dedupe_key` | str | ключ дедупликации (`<rule>:<object>`), уникален в журнале |
| `expected_value` | object | `benefit` 1–5, `risk` 1–5, `value_score = benefit/(1+risk)`, `effort` S/M/L, `effort_weeks`, `risk_level` |
| `status` | enum | `PROPOSED / APPROVED / REJECTED / IMPLEMENTED` |
| `created_at` | date | дата события (передаётся, часы не читаются) |
| `human_approved_by/at` | str/date | подпись человека (только через APPROVE) |
| `rejected_by/at/reject_reason` | | отклонение человеком |
| `implemented_by/at` | | отметка реализации после APPROVED |
| `note` | str | версия набора правил |

`expected_value` — **эвристический прокси** ценности информации (H-008): польза/(1+риск), а не
полноценный расчёт EVOI. `value_score`: DATA_GAP = 1.5, C6/NEW_LINK = 1.5, C4/Q/coverage = 1.33.

## 3. Правила двигателя (rules v1.0.0, без LLM)

| Правило | Сигнал (артефакт) | Условие | Kind | EV (b/r/e) |
|---|---|---|---|---|
| `q_degradation` | learning registry JSONL (`build/registry/learning.jsonl`, опционально) | Q упал на `≥ 0.01` между версиями модели | `NEW_REGIME` для regime-моделей, иначе `NEW_METHOD` | 4/2/M |
| `c4_ambiguity` | `protocols/c4_analysis.json` | есть `structural_findings` со словом "fail" | `NEW_METHOD` | 4/2/M |
| `data_gap` | `protocols/source_registry.json` | статус источника `≠ VERIFIED` | `DATA_GAP` | 3/1/S |
| `c6_release_week` | `build/c6/c6_audit.jsonl` + `build/shadow/shadow_status.json` | последний WEEK_CHECK `registered=false` или `days_since_last_row > suspend_cadence_days` | `NEW_LINK` | 3/1/S |
| `coverage_gap` | `build/shadow/shadow_status.json` | `c6.coverage = null` (не измеряется) или `coverage_met=false` | `NEW_METHOD` | 4/2/M (null) / 5/2/S (вне допуска) |

Дедупликация: если `dedupe_key` уже есть в журнале (в любом статусе) — предложение не создаётся
повторно; повторный `--scan` даёт `created=0`. Fail-closed: отсутствие/битый `shadow`, `c4`,
`sources` — ошибка (exit 1); отсутствие learning registry — правило Q пропускается с примечанием;
битый JSONL — ошибка.

## 4. Человеческий гейт

* `build_proposal` всегда создаёт `PROPOSED`; `register` отказывает событиям не-REGISTER/не-PROPOSED;
  `APPROVE` невозможен без `--by "Имя Человека"`.
* `validate_human` отклоняет автоматические подписи (`automation`, `system`, `engine`, `bot`, `ai`,
  `auto`, `agent`, `proposal_engine`, `t3-admission`, `dsh`, `cron`, `pipeline`), пустые и слишком
  короткие имена.
* Переходы: `PROPOSED → APPROVED` (только человек), `PROPOSED → REJECTED` (человек + причина),
  `APPROVED → IMPLEMENTED` (человек). Повторный approve/reject и approve после reject — ошибка.
* `--approve/--reject/--implement` без `--by` → exit 1; причина отклонения обязательна.

## 6. CLI

```
python tools/proposal_engine.py --scan                  # по умолчанию; пишет в build/registry/proposals.jsonl
python tools/proposal_engine.py --scan --dry-run        # показать, не писать
python tools/proposal_engine.py --scan --json           # отчёт
python tools/proposal_engine.py --list [--status PROPOSED] [--kind DATA_GAP]
python tools/proposal_engine.py --approve <id> --by "Имя Фамилия" --at 2026-11-20
python tools/proposal_engine.py --reject  <id> --by "Имя Фамилия" --reason "дубликат"
python tools/proposal_engine.py --implement <id> --by "Имя Фамилия"
```

Пути сигналов переопределяются (`--shadow/--c6-audit/--c4/--sources/--learning`), журнал —
`--registry`. Код возврата: 0 — успех; 1 — ошибка (битый журнал/артефакт, нет `--by`, авто-имя,
недопустимый переход, отсутствующий id).

## 7. Как работать с предложениями

1. `--scan` раз в неделю/после обновления статусов; новые предложения — `PROPOSED`.
2. Человек читает `--list`, проверяет `evidence`, оценивает `expected_value` и решает.
3. `--approve` (или `--reject --reason`) — подпись человека фиксируется в журнале.
4. Реализация: изменения делает человек/трек; затем `--implement` фиксирует факт.
5. Журнал append-only: история не редактируется; отозвать можно только новым решением
   (reject только из PROPOSED; уже утверждённое — реализовать или зафиксировать отдельно).

## 9. Ограничения

1. **Правила — эвристики**, а не «AGI-самообучение»: пять пороговых правил; качество сигналов
   зависит от актуальности артефактов.
2. `expected_value` — прокси (benefit/(1+risk)), не EVOI-расчёт; числа 1–5 заданы вручную.
3. Q-правило пропускается, пока нет production learning registry; деградация Q сейчас не
   отслеживается этим двигателем.
4. DATA_GAP даёт по одному предложению на каждый не-VERIFIED источник (12 сейчас) — это шумно, но
   честно; группировка по приоритету — следующий шаг.
5. Дедупликация по `dedupe_key`: отклонённое предложение повторно не создаётся автоматически
   (нужно новое решение человека/новый ключ).
6. Человеческая подпись — строка в журнале, не криптографическая; identity/SSO нет.
7. Двигатель не реализует предложения и не запускает эксперименты; нет расписания/CI — запуск
   ручной или из внешнего CI.
8. Количество предложений зависит от текущих артефактов (13 на 2026-11-20; DATA_GAP = число
   не-VERIFIED источников и меняется при верификации другими треками). Тест не фиксирует
   конкретное число: ожидание DATA_GAP вычисляется из `protocols/source_registry.json`.
9. NEW_REGIME в демо = 0: правило срабатывает только на падении Q модели с "regime" в id.
