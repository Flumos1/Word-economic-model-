## 2. Критерии релиза

- **PASS** — все блокеры и предупреждения прошли, регрессия запускалась и зелёная. Только этот
  результат даёт `exit code 0`.
- **CONDITIONAL** — ни один блокер не упал, но регрессия пропущена или есть предупреждения
  (устаревшие ссылки отчёта, пустой forward-журнал, ожидаемое расхождение с замороженным фактом
  R3 и т.п.). `exit code 2`; релиз возможен только с явно записанными оговорками.
- **FAIL** — хотя бы один блокер упал (`exit code 1`): сломан frozen-пин, сырые данные в индексе,
  неполный/невалидный отчёт, битые ссылки README/дорожной карты, красная регрессия.

Научный статус (пройденные C1–C6, допущенные кандидаты, forward-окно) **не является** инженерным
блокером релиза платформы: чеклист требует, чтобы он был честно записан в отчётах и ограничениях.
Соответственно, «релиз 1.0» может быть выпущен как исследовательская платформа с `CANDIDATE`-статусом
кандидатов, но не как «модель, допущенная к применению».

## 5. Как запускать

```
python tools/release_check.py                            # полный чеклист + локальная регрессия
python tools/release_check.py --skip-tests=true          # только артефактные проверки (быстро)
python tools/release_check.py --date 2026-11-12 --out build/release_check.json
python tools/release_check.py --markdown-out build/release_check.md
```

Параметры: `--root` (корень репозитория), `--out` (JSON, по умолчанию
`protocols/release_check_report.json`), `--markdown-out`, `--skip-tests` (в форме
`--skip-tests` / `--skip-tests=false`), `--timeout` (на файл тестов, 900 с), `--date`
(фиксирует `generated_at` для воспроизводимости), `--no-json`.

Exit codes: `0` — PASS, `1` — FAIL, `2` — CONDITIONAL (и `2` для некорректного `--date`).
JSON-отчёт содержит: `report_id=AMFE-RELEASE-CHECK`, `generated_at`, `status`, `exit_code`,
`options`, `counts`, `blockers`, `warnings`, `skipped`, `checks[]` (id/group/severity/status/
detail/evidence), `known_limitations[]`, `markdown`, `executed_tests`.

- чтение реального рабочего дерева (отчёт строится на любом текущем состоянии — PASS/CONDITIONAL/FAIL);
- фикстура «согласованного» дерева (копия репозитория с временно выправленной композицией и
  дополненным журналом) — на ней все блокеры PASS, статус CONDITIONAL только из-за предупреждений;
- мутации на временной копии: изменение frozen-файла → FAIL; порча пина → FAIL; `data_class` в
  отчёте оценки → FAIL; `passed=false` в отчёте ворот → FAIL; удаление правил из `.gitignore` →
  FAIL; битая ссылка в README → FAIL; расширение плана без журнала → FAIL с перечнем рядов;
  «устаревшая ссылка» отчёта оценки → CONDITIONAL без блокеров; пустой корень → FAIL без падения;
- git-индекс с сырыми данными (временный репозиторий) → блокеры `repo.no_tracked_data` и
  `repo.no_raw_archives`;
- детерминизм быстрого прогона (`--skip-tests`, фиксированная дата), запись Markdown, кривая дата →
  exit 2, отсутствие сетевых импортов.

Команда: `python tests/test_release_check.py` → 22/22 OK (18.7 s). Повторный прогон самого
`release_check.py` по рабочему дереву занимает ~109 s (из них ~106 s — полная регрессия 45 файлов).

## 7. Ограничения метода

- Чеклист читает **рабочее дерево**, а не git-объект; на время параллельных незакоммиченных волн
  статус отражает незакоммиченное состояние. Перед тегированием релиза его нужно перезапустить на
  закоммиченном коммите (и приложить `protocols/release_check_report.json` к релизу).
- Регрессия проверяет ровно то, что лежит в `tests/`; время выполнения зависит от машины.
- Чеклист не оценивает научную обоснованность и не присваивает статусы кандидатов — только
  проверяет, что фроузены, отчёты и документация согласованы и честно описывают состояние.
- `reports.no_third_party_values` — эвристика (числовые массивы > 8 элементов); текстовые значения
  и небольшие массивы ею не ловятся, полнота обеспечивается лицензионным аудитом docs/84.
- Проверка ссылок ограничена README и docs/42; ссылки внутри остальных документов не аудируются.
- CI-интеграция чеклиста в рабочие процессы не входила в границы задачи (workflow не менялись);
  рекомендуется вызывать `python tools/release_check.py --skip-tests=true` в отдельном job и
  полный прогон — перед релизом.
