# 124. Поддержка продукта: еженедельный CI-контур, maintenance-guard и чек-листы

Версия 1.0.0 · 2026-11-14. Волна 7, трек поддержки (P2, 10–20% усилий). Задача: `task-13`.
Действующий протокол — **v5 FROZEN** (`protocols/evaluation_protocol_v5.json`, SHA-256 `41d6823e…`);
журнал — [registry/forecasts.jsonl](../registry/forecasts.jsonl) (append-only).

Новые файлы: [.github/workflows/weekly-bulletin.yml](../.github/workflows/weekly-bulletin.yml),
[tools/maintenance_check.py](../tools/maintenance_check.py),
[tests/test_maintenance_check.py](../tests/test_maintenance_check.py), этот документ.
Frozen-файлы, `protocols/**`, `registry/**`, `src/**` и существующие `tools/**` не меняются,
`build/` остаётся в `.gitignore`.

Режим поддержки — **не развитие продукта**. Задача контура: не дать P2 сломать еженедельную
публикацию и теневой трек. Новых оценок нет, критерии не пересчитываются, статусы не меняются,
внешней публикации и деплоя нет.

## 1. Что именно поддерживается

| Артефакт | Кто строит | Как часто | Куда попадает |
|---|---|---|---|
| `build/product/` (модель-карточка, JSON-фид, панель) | `tools/product_pack.py` | еженедельно (CI) | artifact прогона |
| `build/bulletin/<date>.md` + `.json` | `tools/weekly_bulletin.py --date <today>` | еженедельно, пятница | artifact прогона |
| `build/shadow/shadow_status.json` + `<date>.*` | `tools/shadow_track.py --date <today>` | еженедельно, пятница | artifact прогона |
| `build/maintenance/status.json` | `tools/maintenance_check.py` | еженедельно + вручную | artifact прогона |

Журнал `registry/forecasts.jsonl` заполняется **не CI**: строки пишет человек/Lead через
`tools/forward_forecast.py` (append-only, docs/110, docs/117). CI только читает журнал.

## 2. CI: workflow `Weekly bulletin (support mode)`

Триггеры: расписание `0 7 * * 5` (каждая пятница, 07:00 UTC) и `workflow_dispatch` (ручной запуск).
Права — только `contents: read`; `concurrency: weekly-bulletin` с `cancel-in-progress: false`;
секреты и приватные данные не нужны: все входы (протоколы, отчёты, журнал) закоммичены.

Шаги: checkout → Python 3.11 → `pip install numpy` → `python tools/product_pack.py` →
`python tools/weekly_bulletin.py --date "$(date -u +%F)"` →
`python tools/shadow_track.py --date "$(date -u +%F)"` → `python tools/maintenance_check.py --date
"$(date -u +%F)"` → загрузка артефактов `build/product/`, `build/bulletin/`, `build/shadow/`,
`build/maintenance/` (`actions/upload-artifact@v4`, retention 90 дней).

Workflow **никогда не коммитит, не пушит, не тегирует и не деплоит**: в нём нет `git commit`,
`git push`, `gh pr create` и deploy-шагов. Он не переписывает журнал и не меняет протоколы. Если
`maintenance_check` вернул ALERT (код 2), шаг падает — прогон виден красным, артефакты всё равно
загружаются (`if: always()`).

**Как запустить:**

```powershell
# локально (то же, что делает CI; дата — текущая UTC)
python tools/product_pack.py
python tools/weekly_bulletin.py --date "$(Get-Date -AsUTC -Format yyyy-MM-dd)"
python tools/shadow_track.py   --date "$(Get-Date -AsUTC -Format yyyy-MM-dd)"
python tools/maintenance_check.py --date "$(Get-Date -AsUTC -Format yyyy-MM-dd)"
```

**Без `gh`-аутентификации / без секретов:** workflow запускается кнопкой в UI GitHub
(Actions → «Weekly bulletin (support mode)» → Run workflow), результат и артефакты скачиваются со
страницы прогона; `gh` CLI, токены и приватные data-artifacts не требуются. Локально без gh —
выполнить четыре команды выше: они читают только репозиторий и пишут только `build/`. Проверить
workflow-файл локально можно парсером YAML (`python -c "import yaml; yaml.safe_load(open(...))"`), но
сам запуск GitHub Actions локально без `act`/`gh` не воспроизводится — это ограничение среды.

## 3. Maintenance-guard: `tools/maintenance_check.py`

Пять проверок (все — блокирующие):

| id | Что проверяет | Порог | На что опирается |
|---|---|---|---|
| `journal.valid` | журнал парсится и проходит append-only валидацию (`tools/registry.py`) | проблем 0 | `registry/forecasts.jsonl` |
| `shadow.fresh` | свежесть теневого трека | **≤ 10 дней** | `build/shadow/shadow_status.json` (`generated_at`) |
| `product.fresh` | свежесть продуктового фида | **≤ 14 дней** | `build/product/forecast_latest.json` (`generated_at`) |
| `bulletin.fresh` | свежесть последнего выпуска | **≤ 14 дней** | `build/bulletin/*.json` (самый свежий `date`/`generated_at`) |
| `track.alert` | трек не в `ALERT` и в `alerts` нет severity `ALERT` | нет | `shadow_status.json` (docs/119) |

Свежесть считается по **собственным датам артефактов**, а не по mtime файлов: артефакты в git не
лежат, mtime после checkout/копирования недостоверен. Поэтому документ детерминирован: одинаковые
входы и одинаковая `--date` дают байт-идентичный `status.json` (кроме `generated_at`).

Коды выхода:

| Код | Статус | Значение |
|---|---|---|
| `0` | `OK` | всё свежее, журнал валиден, трек не в ALERT |
| `2` | `ALERT` | протух артефакт, журнал невалиден или трек в ALERT — **нужно действие человека** |
| `1` | `ERROR` | нет/битый обязательный вход: здоровье не подтверждается (fail-closed, PASS не выставляется) |

Пишет `build/maintenance/status.json` (в том числе при `ERROR`): `schema`, `generated_at`, `date`,
`status`, `exit_code`, `checks[]`, `counts`, `findings[]`, `track`, `sources`, `rules`. Только чтение
входов; журнал, протоколы, `src/` и продуктовые артефакты не меняются.

```powershell
python tools/maintenance_check.py --date 2026-11-14
python tools/maintenance_check.py --date 2026-11-14 --generated-at 2026-11-14T12:00:00Z
python -m unittest tests.test_maintenance_check -v      # 11 тестов
```

## 4. Еженедельный чек-лист (пятница, ~10 минут)

1. Запустить workflow (по расписанию или вручную) либо четыре локальные команды из §2.
2. Прогон зелёный; если `maintenance_check` упал — см. §6 (ALERT) или §7 (ERROR).
3. `build/maintenance/status.json`: `status = OK`, `counts.failed = 0`; `track.status` —
   `STARTING`/`ON_TRACK`/`WARN`/`GATE_PASS`, но не `ALERT`.
4. Скачать артефакты (`build/product`, `build/bulletin`, `build/shadow`, `build/maintenance`) со
   страницы прогона.
5. Просмотреть `build/bulletin/<date>.md`: статус `CANDIDATE`, `conditional_data_class=true`,
   C4 FAIL по RMSE, C6-счётчик, near-miss `ENSEMBLE_REGIME`; ничего не редактировать «для красоты».
6. Убедиться, что версии/хеши в бюллетене не изменились (v5 `41d6823e…`, R3 1.0.1, NF-SIM,
   composition 2026-11-11). Изменение хеша = событие, а не рутина: остановиться и сообщить Lead.
7. Ничего не коммитить: артефакты `build/` не входят в git; коммит журнала — отдельное действие
   человека/Lead после релиза данных.

## 5. Ежемесячный чек-лист (после релиза CPI, 10–15-е число)

1. Проверить, что новая строка журнала появилась (`python tools/registry.py --validate`,
   `python tools/registry_resolve.py --status`); при необходимости — человек/Lead пишет строку
   `tools/forward_forecast.py`, CI этого не делает.
2. Пересобрать контур (`python tools/product_pack.py`, `python tools/weekly_bulletin.py`,
   `python tools/shadow_track.py`) и прогнать `tools/maintenance_check.py`.
3. Сверить прогресс C6: 12 разрешённых прогнозов, ≥4 различных целевых периода; счётчики
   отражены в бюллетене и `shadow_status.json`. C6 идёт своим ходом — ускорять его нельзя.
4. Проверить отсутствие дрейфа цепочки хешей и отсутствие изменений в `protocols/**`/`src/**`.
5. Зафиксировать в недельном бюллетене/заметке, что ALERT/WARN не было или какие были; решения по
   треку — только по docs/119, не «на глаз».

## 6. Действия при ALERT (код 2)

1. Не менять протокол, критерии и статусы: ALERT — это сигнал, а не основание для ревизии.
2. Прочитать `build/maintenance/status.json` → `checks[]`/`findings[]`:
   - `shadow.fresh`/`product.fresh`/`bulletin.fresh` — пересобрать артефакты (§2), проверить, что
     запись в CI не падает; если артефакты не пересобираются — искать поломку в `tools/**`;
   - `journal.valid` — **не править журнал вручную**: append-only, коррекции только отдельной
     correction-строкой по правилам `registry/README.md`; при сомнении эскалировать Lead;
   - `track.alert` — открыть `build/shadow/<date>.md` и docs/119: коды `SUSPEND_LOSS`,
     `SUSPEND_COVERAGE`, `SUSPEND_CADENCE`. Решение о приостановке/продолжении трека принимает
     человек (Lead), фиксирует причину; CI ничего не останавливает автоматически.
3. После устранения причины перезапустить workflow и убедиться, что `status = OK`.
4. Если ALERT не устраняется в тот же день — сообщить Lead с кодом проверки и путём к артефакту.

## 7. Действия при ERROR (код 1)

Означает «здоровье не подтверждается»: нет журнала, нет `build/shadow/shadow_status.json`, нет
`build/product/forecast_latest.json`, нет ни одного `build/bulletin/*.json` или они битые. Это
fail-closed: ни одна проверка не помечается PASS. Действия: пересобрать контур (§2); если вход
обязан быть в репозитории (журнал, протоколы) — проверить, не сломан ли checkout/файл, и
эскалировать Lead. Не «заглушать» ошибку пустым `status.json` вручную.

## 8. Границы поддерживающего режима

- Статусы кандидатов **не меняются**: ни CI, ни maintenance-guard не присваивают SHADOW_TEST /
  LIMITED_DEPLOYMENT / ACTIVE.
- C6 **идёт** по мере накопления журнала (12 разрешённых прогнозов, ≥4 периода; ориентир — 2027 год,
  docs/119); ускорять/подменять его нельзя.
- Frozen-цепочка, `protocols/**`, `registry/**`, `src/**`, существующие `tools/**` — не меняются;
  новые файлы волны: workflow, `tools/maintenance_check.py`, тест и этот документ.
- CI **не коммитит**; внешней публикации, рассылки и деплоя нет.
- `build/` не в git: артефакты живут 90 дней в artifacts прогона и локально.
