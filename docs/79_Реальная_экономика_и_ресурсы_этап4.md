## 1. Назначение и границы

Этап 4 вводит **физическую** сторону модели: межотраслевые потоки, транспортные задержки и запасы,
первичные ресурсы (энергия, сырьё), трудовой ресурсный потенциал и материальные балансы. Модуль
независим от учётного ядра (этап 2) и двустранового прототипа (этап 3) и обменивается с ними только
векторами физических величин; деньги, цены, налоги и финансовые требования остаются в этих треках.

Что **не** делается намеренно (чтобы не подменить ограничения их имитацией):

- нет денежной оценки физического предела (docs/38 E03) — все величины в физических единицах;
- нет трудовой теории стоимости: часы ограничивают активность, но не определяют стоимость выпуска
  (docs/35, «Важное теоретическое различение»); цены в модуле не задаются вообще;
- нет утверждения о неизменности коэффициентов (docs/38 E07): один экземпляр модели = один снимок
  технологии; сравнение снимков — задача вызывающего кода;
- нет оптимизации выпуска при замещении ресурсов: реализовано явное правило пропорционального
  рационирования, а оптимальное распределение и эластичности замещения — гипотезы этапа 5.

## 3. Input-output Леонтьева

Модель: `A` — неотрицательная матрица прямых затрат (единицы продукта i на единицу валового выпуска
сектора j), баланс `x = A x + d`, решение `x = (I − A)⁻¹ d`.

- **Продуктивность** (`is_productive`): `ρ(A) < 1` (радиус Перрона–Фробениуса оценивается степенной
  итерацией), что эквивалентно существованию неотрицательной обратной `(I − A)⁻¹ = Σ Aᵏ`. Сингулярная
  или непродуктивная матрица **не решается**: `gross_output`/`inverse` поднимают `LeontiefError`, а не
  возвращают отрицательный выпуск. Граница `ρ = 1` считается непродуктивной.
- **Добавленная стоимость**: `VAⱼ = xⱼ − Σᵢ Aᵢⱼxⱼ` — остаток баланса, не трудовая стоимость.
- **Нет двойного счёта** (docs/38 E01): валовой выпуск и промежуточное потребление не складываются;
  для закрытой экономики `ΣVA = Σd` — проверяется `check_no_double_counting`.
- **Мультипликаторы**: суммы столбцов `(I−A)⁻¹` (обратные связи) и суммы строк (прямые связи);
  для продуктивной технологии все ≥ 1.

Контрольный пример (2 сектора, `A = [[0.2, 0.3],[0.1, 0.4]]`, `d = (10, 20)`):

```
ρ(A)                       = 0.5                       → productive
x = (I−A)⁻¹d               = (26.6667, 37.7778)
VA = x − Ax                = (10.0, 20.0), ΣVA = 30 = Σd
мультипликаторы            = (1.5556, 2.4444)
max |A x + d − x|          = 3.6e-15
Σx = 64.4444, ΣAx = 34.4444, ΣVA = 30.0, Σd = 30.0
```

## 4. Логистика и цепочки поставок

Дискретная модель материальных потоков: узел = склад/переработка с запасом на начало периода и
ограничением пропускной способности; ребро = перевозка с мощностью, **задержкой ≥ 1 периода** и долей
потерь (0 ≤ loss < 1). За период:

1. приходы = отправки, у которых наступил срок (задержка = полное число периодов);
2. доступно = запас на начало + приходы + экзогенная поставка;
3. отправка = min(спрос, мощность ребра, доступный запас, пропускная способность узла) — по рёбрам в
   порядке объявления; неудовлетворённый спрос попадает в `unmet` **и не превращается в отрицательный
   запас**;
4. запас на конец периода = доступно − отправлено (тождество физического запаса, docs/38 I04).
   Потери вычитаются на ребре до прибытия.

Две проверки сохранения: `check_node_conservation` (по каждому узлу за весь прогон) и
`check_mass_conservation` (по цепи: `начальный запас + поставки = запасы + в пути + потери`).

Сценарий шока: `supply_shock(chain, horizon, shock_periods, edge_factor)` и `disruptions` по периодам
(множители мощности рёбер/узлов). Агрегированный результат — недопоставки по периодам; задержка
транспорта сдвигает эффект вниз по цепи на срок перевозки.

Контрольный пример (port→factory→market, задержка 1, мощность 10, спрос 10):

```
базовая линия:                  суммарный unmet = 0.0, сохранение массы 0.0
шок: все рёбра закрыты в 3–4:   суммарный unmet = 40.0
недопоставки по периодам:       [0, 0, 20, 20, 0, 0, 0, 0]
приходы на factory:             период 4 = 0, период 5 = 0 (заблокированы отправки 3 и 4),
                                период 6 = 10 (восстановление)
```

## 5. Энергия и сырьё

`ResourceBalance` — баланс одного первичного ресурса за период и территорию:

```
добыча + импорт + изъятие из запасов
    = промежуточное потребление + конечное потребление + экспорт + потери + накопление запасов
```

Накопление/изъятие запасов учитывается ровно один раз (docs/38 I04): одновременно `stock_draw > 0` и
`stock_build > 0` для одного однородного ресурса отклоняется. Небаланс → `ResourceBalanceError`
(`supply_total != use_total` не «закрывается» молча).

`InputConstraint` — физический предел выпуска `Σₛ eₛxₛ ≤ E` (`eₛ` — ресурс на единицу валового
выпуска). Предел линеен, поэтому допустимый пропорциональный масштаб `s = min(1, E / потребность)`
вычисляется точно; `apply_input_limit` возвращает масштаб, выпуск, добавленную стоимость, `binding`
и остаток. Сценарий сокращения доступности действует через `energy_factor`.

Контрольный пример: `E = 50 МВт·ч`, потребность при полном выпуске `2·26.6667 + 37.7778 = 91.1111`:

```
scale = 0.548780, binding = True
потребность после рационирования = 50.0 (ровно доступность)
VA = 30 · 0.548780 = 16.4634
```

## 6. Труд: три состояния и B0/B1/B2

`LabourStates` хранит часы по квалификационным группам в трёх состояниях:
POTENTIAL ≥ ACCESSIBLE ≥ UTILIZED (проверяется по каждой группе). Группы — квалификации, а не
«универсальное качество человека» (docs/37 R03); единицы — человеко-часы, не смешиваются с людьми,
деньгами или единицами продукции.

Три конкурирующих варианта ограничения (docs/37), сравниваемые на одном и том же векторе выпуска,
каждый со своими независимыми параметрами:

- **B0** `NoLabourConstraint` — труд не входит в производственное ограничение; только описательные
  часы. Это обязательный baseline (R05) и случай автоматизации (R04): сектор с нулевыми затратами
  труда производит.
- **B1** `AggregateLabourConstraint` — минимальные трудовые индикаторы: один агрегированный пул часов
  и коэффициент часов на единицу выпуска по секторам. Сектора взаимозаменяемы в пуле.
- **B2** `TaskLabourConstraint` — задачная структура: часы по задачам на единицу выпуска, задача
  привязана к квалификационной группе, доступные часы по группам **не переливаются** между группами.
  Возможна ситуация, когда агрегированных часов достаточно, а одна группа — узкое место; полное
  замещение не постулируется (оно сделало бы B2 эквивалентом B1), частичное замещение — гипотеза
  следующего этапа.

`compare_labour_variants` возвращает строки без ранжирования: docs/37 R06 запрещает объявлять вариант
лучшим до вневыборочного теста; функция не содержит полей «best/winner».

Контрольный пример (выпуск контрольного IO-примера; требуемые часы B1: `26.6667 + 2·37.7778 = 102.222`):

```
B1, доступно 100:  scale = 0.978261, binding = aggregate_hours
B1, доступно  50:  scale = 0.489130
B2, manual 90:     scale = 0.880435, binding = manual
B2, cognitive 5 при manual 1000: binding = cognitive, scale < 1 (агрегат B1 этого не видит)
```

Дополнительно: `employment_from_hours` (часы → эквивалент работников) и `unemployment_rate`
(определение должно быть задано явно, docs/35) — только пересчёт, не оценка.

## 7. Материальные балансы и отсутствие двойного счёта

`ProductBalance` реализует I01 для одного продукта в одной базе оценки:

```
внутренний выпуск + импорт + прочие поступления (+ изъятие из запасов)
    = промежуточное использование + конечное потребление + накопление капитала
      + экспорт + прочие использования (+ накопление запасов)
```

`MaterialBalances` проверяет набор продуктов; отрицательная величина отклоняется (у физической
поставки нет отрицательного знака). `balances_from_io` строит балансы из решения IO; при закрытой
экономике все невязки равны нулю тождественно, при открытой — импорт/экспорт включаются как отдельные
компоненты, и несогласованный торговый вектор даёт ненулевую невязку, а не «молчаливое» закрытие.
`check_no_double_counting` возвращает валовой выпуск, промежуточное потребление, добавленную стоимость
и конечные использования вместе с невязкой — тест проверяет и тождество, и то, что валовой выпуск
больше добавленной стоимости (иначе промежуточный продукт был бы посчитан дважды).

## 8. Сценарии шока

`Scenario` — набор независимых мультипликаторов: `demand_factors` (по секторам конечного спроса),
`energy_factor` (доля доступной первичной ресурсной мощности), `labour_factor` (доля доступных часов).
`run_scenario` решает IO при шокированном спросе, затем берёт минимальный масштаб из физических
пределов, возвращает выпуск, конечный спрос, добавленную стоимость, связывающие ограничения и невязку
материального баланса (баланс сохраняется после рационирования благодаря линейности системы).

Стандартный набор `standard_shock_set`: baseline, demand_shock (−20% спроса одного сектора),
energy_shock (−30% доступной энергии), labour_shock (−25% доступных часов), combined_shock.
Результаты контрольного прогона (энергия 50, труд B1 50):

| сценарий | scale | binding | VA |
|---|---|---|---|
| baseline | 0.489130 | energy, labour | 14.6739 |
| demand_shock | 0.506757 | energy, labour | 14.1892 |
| energy_shock (−30%) | 0.384146 | energy, labour | 11.5244 |
| labour_shock (−25%) | 0.366848 | energy, labour | 11.0054 |
| combined_shock | 0.380068 | energy, labour | 10.6419 |

Сценарии не ранжируют исходы и не присваивают «оптимальность»: это физически допустимые варианты при
заданных допущениях; правило пропорционального рационирования — явное сценарное допущение.

## 9. Связь с этапами 2 и 3

- **Этап 2 (учётное ядро)**: модуль отдаёт физические величины — валовой выпуск по секторам,
  промежуточное потребление, добавленную стоимость как остаток баланса, объёмы запасов и поставок.
  Денежное распределение добавленной стоимости (оплата труда, прибыль, налоги) не моделируется здесь:
  это счета этапа 2, и связь должна идти через явную карту «сектор IO → типизированный счёт». Обратная
  связь (издержки, цены) в прототипе отсутствует — поэтому нет и претензии на полный круг «производство
  → доход → спрос».
- **Этап 3 (две страны/валюты)**: `ProductBalance.supply/use` содержит метки `imports`/`exports`,
  поэтому торговые потоки двустранового прототипа подключаются как отдельные компоненты баланса, со
  своими единицами и без зеркалирования внутри модуля. Требование одинаковых границ и оценки
  (docs/38 I05) остаётся за этапом 3; модуль лишь фиксирует, что несогласованный торговый вектор даёт
  ненулевую невязку.
- **Этап 6 (данные)**: коэффициенты `A`, интенсивности энергии и часов в прототипе заданы сценарием;
  калибровка на реальных IO-таблицах, энергобалансах и трудовых обследованиях не выполнялась и
  требует point-in-time источников и лицензионных записей (см. docs/63, 75).

## 11. Ограничения и что осталось

1. **Нет калибровки на данных**: все коэффициенты сценарные. Нужны point-in-time IO-таблицы, энерго-
   балансы, трудовые обследования и лицензионные записи к ним (этап 6, docs/63/75).
2. **Нет замещения ресурсов и оптимального распределения**: реализовано пропорциональное рационирование;
   замещение, эластичности, резервные мощности и приоритеты — гипотезы этапа 5.
3. **Логистика без маршрутной оптимизации**: один товар на цепь, фиксированная топология, задержки
   детерминированы; нет перенаправления потоков, мультипродуктовых загрузок и стохастических задержек.
4. **Труд**: нет замещения квалификаций (частичного тоже), миграции, эндогенного участия и обучения;
   B2 — только жёсткие группы. Сравнение B0/B1/B2 структурное, не прогностическое (R06).
5. **Энергия**: нет цен, разных энергоносителей и замещения между ними; баланс одного ресурса за
   период, без межпериодной динамики запасов и добывающих мощностей.
6. **Связь с учётным ядром и двустрановым треком** — только через документированные интерфейсы
   (векторы выпуска/промежуточного потребления/VA; метки imports/exports); типизированные счета и
   валютные пересчёты не реализованы.
7. **CI**: тест-файл пока не добавлен в `.github/workflows/accounting-regression.yml` (это вне границ
   трека; Lead добавляет шаг и запускает полную регрессию).
8. **Нет отчёта экономической адекватности (V2)**: без реальных данных сравнение сценариев не может
   быть объявлено «правильным»; это честно помечено как NOT_APPLICABLE, а не PASS.
