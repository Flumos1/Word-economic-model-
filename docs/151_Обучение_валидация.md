## 1. Архитектура контура (уровень L6 docs/145)

```
walkforward.py ──► метрики (MAE/RMSE/CRPS, наивный бенчмарк, запрет будущих данных)
      │
      ▼
quality.py ─────► Q = f(E, C, S, R) + жёсткие ограничения (fail-closed)
      │
      ▼
registry.py ────► append-only JSONL: CANDIDATE → SHADOW → LIMITED → ACTIVE
                  (ACTIVE только с preregistered критериями и независимой проверкой)
                  REJECT / REVERT (откат к предыдущей ACTIVE версии)
```

Автоматизируется **обучение параметров и сбор доказательств**; смена архитектуры и перевод в
ACTIVE — только человек (docs/145, критерий F). Реестр — единственный источник версий; удаление
строк невозможно (append-only), откат — отдельное событие.

## 2. Q = f(E, C, S, R)

| Компонент | Формула | Смысл |
|---|---|---|
| E ошибка | `rel = error/benchmark_error`; `E = clip((2.0 - rel)/(2.0-0.5), 0, 1)` | модель вдвое лучше naive → 1; равно naive → 2/3; вдвое хуже → 0 |
| C согласованность | `C = clip(1 - violations/3, 0, 1)` | нарушения балансов/протокола из валидаторов |
| S устойчивость | `cv = std(fold MAE)/mean(fold MAE)`; `S = clip((1.0-cv)/(1.0-0.25),0,1)` | стабильность по фолдам |
| R риск | `R = clip(1 - |coverage-0.80|/0.20, 0, 1)` | покрытие 80% интервала / калибровка |

Веса по умолчанию: **E 0.40, C 0.20, S 0.20, R 0.20** (если S или R недоступны, веса
перенормируются по использованным компонентам). Грейды: **A ≥ 0.75, B ≥ 0.60, C ≥ 0.45, иначе D.**
Сравнение версий: `IMPROVED` при `ΔQ ≥ 0.01`, `DEGRADED` при `ΔQ ≤ −0.01`, иначе `TIE`; сравнение
невозможно, если хотя бы у одной версии не пройдены жёсткие ограничения.

**Жёсткие ограничения (Q не присваивается, fail-closed):**
1. `balance_residual_max ≤ 1e-6` (масштабируется через `balance_scale`);
2. `future_leakage = false` (проверка walk-forward/PIT);
3. `n_oos ≥ 12` (минимум вневыборочных наблюдений);
4. `benchmark_error > 0` (нужен наивный бенчмарк);
5. все входы конечны, ошибки/счётчики неотрицательны.

## 3. Реестр моделей (`registry.py`)

Одно событие = одна строка канонического JSON в append-only JSONL; `event_id` — SHA-256 канонического
события, поэтому одинаковые входы дают одинаковые байты.

**Статусы:** `CANDIDATE → SHADOW → LIMITED → ACTIVE`; `REJECTED` — терминальный для версии.
`REJECT` разрешён из CANDIDATE/SHADOW/LIMITED; **ACTIVE нельзя отклонить напрямую — только
`REVERT`** (откат к ранее ACTIVE версии, которая снова становится ACTIVE, а откатываемая — REJECTED).

**Допуск в ACTIVE — три проверки, все обязательны:**
1. **Preregistered критерии**: `criteria.registered_at ≤ evaluated_at` (записаны до оценки; SHA-256
   критериев фиксируется в событии);
2. **Независимая проверка**: `independent_review = {reviewer, independent: true, pass: true,
   reviewed_at, report_sha256}`; ревьюер ≠ автор; дата ревью не позже даты повышения;
3. **Качество**: `Q ≥ 0.60` и жёсткие ограничения пройдены; версия должна быть LIMITED; вторая
   ACTIVE-версия в модели запрещена (сначала revert).

`validate_registry()` переигрывает журнал и возвращает отчёт (valid/errors/models); битая строка или
нарушение инвариантов — `valid: false`, при записи — `RegistryError` и **ничего не добавляется**.

## 4. Walk-forward (`walkforward.py`)

Расширяющееся окно: фолд `k` — обучение `[0, origin]`, тест `[origin+1, origin+h]`;
`assert_no_leakage` требует `test_start > train_end` для каждого фолда, прогнозная функция получает
**только копию обучающего окна** (tuple) и обязана вернуть ровно `h` значений. Метрики: MAE, RMSE по
шагам и пул-агрегат; **CRPS** при квантилях: `CRPS = 2·mean pinball loss` по переданным уровням
(конвенция harness). Бенчмарк по умолчанию — random walk (последнее наблюдение), сравнение
`relative_mae/relative_rmse`, `beats_naive`; бенчмарк можно заменить. Ошибки, неверная длина
прогноза, слишком короткий ряд, нулевая ошибка naive, NaN/Inf — `WalkForwardError` (fail-closed).

Результат содержит `quality_inputs` (`error`, `benchmark_error`, `n_oos`, `balance_residual_max`,
`future_leakage: false`, `interval_coverage`), которые напрямую передаются в `evaluate_quality`.

## 5. Демо (`tools/learning_demo.py`, офлайн, детерминированное)

Синтетический ряд (120 наблюдений, mean-reverting + сезонность, без случайности), `min_train=60`,
h=1, 60 OOS-точек; три версии:

| Версия | Q | Грейд | MAE | MAE naive | rel | beats naive | Решение |
|---|---:|---|---:|---:|---:|---|---|
| v0 `RW_BASELINE` | **0.6774** | B | 0.3942 | 0.3942 | 1.000 | нет | ACTIVE (ревью **симулировано** в демо) |
| v1 `AR1_IMPROVED` | **0.7280** | B | 0.3791 | 0.3942 | 0.962 | да | SHADOW → LIMITED; **ACTIVE отказан** дважды |
| v2 `AR1_BIASED_DEGRADED` | **0.4000** | D | 5.0040 | 0.3942 | 12.695 | нет | REJECTED |

`v1_vs_v0: IMPROVED (+0.0506)`, `v2_vs_v0: DEGRADED (−0.2774)`. Порядок демо проверяет именно
ворота ревью: сначала **v0 и v1 обе доводятся до LIMITED**, затем выполняются две попытки
`v1 → ACTIVE` — **без review** (`ACTIVE requires an independent review (independent_review mapping)`)
и **с non-independent review** (`ACTIVE requires independent_review.independent = true`); в этот
момент ACTIVE-версии ещё нет, поэтому отказ не может быть замаскирован сообщением «already has an
ACTIVE version». Только после этого `v0` повышается до ACTIVE (с симулированным ревью), и выполняется
откат `v1` (LIMITED) → `v0` (ACTIVE, `REVERT`), `v1`→REJECTED; журнал 10 событий,
`validate_registry`: **valid=true**. Тест `test_demo_refusals_are_review_gate` требует, чтобы каждая
причина содержала `review` и не содержала `already has an ACTIVE`.
Выход демо явно помечает: *независимое ревью в демо симулировано, реальный ACTIVE требует человека.*

## 6. Связь с протоколом v5 / C6

* C6 — это **живой** forward-journal кандидата (12 разрешённых прогнозов, ≥4 периода, loss/coverage);
  learning-контур даёт **исторический** walk-forward и Q для версий/моделей, не заменяя C6 и не
  присваивая допуск.
* Правило «ни одна версия не попадает в прод без предрегистрированных критериев» (docs/145)
  реализовано в реестре как жёсткая проверка; отчёт независимой проверки хранится по SHA-256.
* Откат версии (REVERT) — операционный аналог rollback при деградации; C6-календарь и shadow-трек
  не затрагиваются.

## 7. Что автоматизировано, что требует человека

**Автоматически:** расчёт Q и компонентов, проверка жёстких ограничений, walk-forward метрики и
сравнение с naive, append-only запись событий реестра, отказ ACTIVE при отсутствии preregistered
критериев/независимого ревью, откат по событию REVERT, детерминированные демо и тесты.
**Только человек:** независимое ревью (reviewer ≠ author, реальный отчёт), решение о повышении до
ACTIVE/LIMITED в проде, изменение архитектуры модели (автоматически — только параметры),
предрегистрация критериев (до оценки), интерпретация результатов и продуктовые решения.

## 8. Ограничения

1. **Демо синтетическое**; числа показывают работу контура, а не качество реальной модели.
2. **Веса Q (0.4/0.2/0.2/0.2), пороги E (0.5–2.0), грейды и ACTIVE_MIN_Q=0.60 — документированные
   конвенции**, а не доказанные оптимумы; менять их можно только версией инструмента и записью в
   журнале решений.
3. **Walk-forward не PIT**: ряд берётся как есть (без винтажей), поэтому возможна переоценка
   точности на пересмотрах; для реальных рядов нужен слой винтажей (ср. D-147).
4. **CRPS только при квантилях**; без них Q считается по доступным компонентам (R перенормируется),
   и это фиксируется в документе качества.
5. **Реестр локальный** (JSONL в каталоге проекта), без распределённой блокировки/подписей; для
   мультипользовательского режима нужен серверный журнал и криптографические подписи.
6. Реестр не проверяет содержательную корректность метрик/хешей (доверяет вызывающему коду);
   независимость ревью проверяется по формальным полям, а не по личности.
7. Никакой автоматической смены архитектуры: контур меняет только параметры/версии в рамках
   зарегистрированной архитектуры.
8. ACTIVE в демо достигнут с **симулированным** ревью — это иллюстрация механики, а не допуск.
