## 1. Зачем

REAL_TIME-прогон заново считает одни и те же прогнозы на одних и тех же началах: кандидат и каждый
член компаратора — это регрессии/ансамбли по скользящему окну, ~1,3 с на начало в T2 h=0. Повторные
прогоны (отладка, бенчмарки, прогон другой цели/горизонта, повторная проверка после правки
отчётов) пересчитывают неизменные предсказания. Кэш мемоизирует **только прогнозы** и отдаёт их по
контентному ключу, не меняя ни результаты, ни PIT-гарантии.

Кэшируются:

- прогноз кандидата (`kind="candidate"`, id кандидата из `protocols/candidates_2026-11-11.json`);
- прогноз каждого члена компаратора (`kind="model"`, id модели R3).

**Не** кэшируются: сырые данные, PIT-срезы, реализации/факты (`actual_pair`), маска рецессий и
итоговый admission-отчёт. Факты и маска каждый прогон пересчитываются из архива, поэтому кэш не
может «подменить» PIT-истину и не хранит третьих значений (licence_policy, docs/84) — только
собственные прогнозы проекта в приватном каталоге.

## 2. Ключ кэша: identity + версионный fingerprint

`tools/eval_cache.py` строит ключ как SHA-256 канонического JSON из двух частей:

1. **identity прогноза**: `kind` (candidate/model), `name` (id кандидата/модели), `target`,
   `horizon`, `origin` (ISO), `series_id` (может быть null), `mode` (`auto`/`latest`/`vintage`);
2. **fingerprint окружения**:
   - `versions` — LF-нормализованные SHA-256 замороженных артефактов: `evaluation_protocol_v4.json`,
     `r3_specification.json`, `nf_sim_thresholds.json`,
     `comparator_composition_2026-11-11.json`, `nber_dates.json`, `spf_metadata.json`;
   - `source_sha256` — дайджест кода прогнозирования: 12 файлов из `src/amfe/forecast`,
     `src/amfe/candidates`, `src/amfe/ensemble`;
   - `data_sha256` — дайджест приватного архива `data/raw/**.csv|zip|json` (путь + LF-SHA-256
     содержимого; на локальном архиве — 33 файла);
   - `cache_schema = eval-cache/1.0.0`.

Свойства:

- **PIT-безопасность:** `origin` входит в ключ, а ключ строится только из входов, от которых
  зависит детерминированный прогноз. Один и тот же origin всегда даёт тот же ключ; другой origin —
  другой ключ. Кэш физически не может отдать значение, посчитанное с данными после origin, потому
  что это был бы другой ключ (другие данные/версии/начало).
- **Инвалидация:** любое изменение данных, кода прогнозирования, frozen-версий или NBER/SPF-метаданных
  меняет fingerprint → все прежние ключи перестают использоваться (остаются «сиротами» до `prune`).
- **Детерминизм:** одинаковые входы → одинаковый ключ и одинаковый payload; payload
  нормализуется в JSON (numpy → list/float), при чтении возвращается точное значение, совпадающее с
  посчитанным (идентичность проверена тестами, см. §6).

Хранение: `cache_dir/<первые 2 hex>/<ключ>.json`; одна запись — identity, fingerprint, `created_at`,
payload. Запись атомарная (временный файл + `replace`). Битые/чужие файлы считаются промахом
(`corrupt`), падения не вызывают.

## 3. Интеграция в прогон

`tools/run_real_evaluation.py`:

- `--cache-dir PATH` — включает кэш (по умолчанию выключен; поведение без флага не изменилось);
- `--max-origins N` — ограничение числа начал на окно (бенчмарк/отладка; по умолчанию все);
- в `build_window` каждый вызов кандидата и члена компаратора проходит через
  `ForecastCache.forecast(...)`: промах → расчёт + запись, попадание → готовый payload;
- итоговый отчёт **не меняется**: в JSON отчёта нет полей кэша, в stdout-сводку добавлен блок
  `cache` (entries/hits/misses/writes/bytes/fingerprint) только при включённом кэше.

Пример:

```
python tools/run_real_evaluation.py --target T1_CPI_YOY --horizon 1 \
  --cache-dir build/eval_cache --out build/first_real_evaluation_report.json
```

Обслуживание:

```
python tools/eval_cache.py stats --dir build/eval_cache     # entries/bytes/hits/misses/fingerprint
python tools/eval_cache.py prune --dir build/eval_cache     # удалить записи другого fingerprint
python tools/eval_cache.py clear --dir build/eval_cache     # очистить каталог
```

Рекомендация: каталог кэша — вне git (например, `build/eval_cache`); после `data-refresh` с новыми
данными и после правок модельного кода выполнять `prune` (или просто дать ключам смениться — старые
записи не будут использоваться).

## 5. Benchmark: T2 h=0, 20 начал

Методика (повторяемая): окно W2, `target=T2_GDP_GROWTH`, `horizon=0`, кандидат `ENSEMBLE_EQUAL`
(применим к T2; `ENSEMBLE_RW_AR`, на котором построена первая реальная оценка T1, для T2 не
применим — RW не поддерживает T2; новые T2-кандидаты волны, `ENSEMBLE_T2_SPF`/`ENSEMBLE_T2_NOT_SPF`,
появились позже и на механизм кэша не влияют — ключ строится по id кандидата), члены компаратора
`AO`, `AR_BIC`, `BVAR_MINNESOTA`, `OWN_NOWCAST_BRIDGE`;
`max_origins=20` (20 использованных REAL_TIME-начал, `data_class=REAL_TIME`). Фазы: (A) без кэша;
(B) холодный кэш (100 промахов, 100 записей); (C) тёплый кэш (100 попаданий).

| фаза | секунды | per-origin | cache |
|---|---|---|---|
| A. без кэша | **25.49** | 1274.5 ms | — |
| B. холодный кэш (заполнение) | 17.42 | 871.0 ms | 100 промахов, 100 записей, 305 690 B |
| C. тёплый кэш (повтор) | **0.75** | **37.5 ms** | 100 попаданий |

- **Ускорение повтора: 34.0×** (25.49 → 0.75 с); на начало — 1274.5 → 37.5 ms.
- Идентичность: окна из фаз A, B и C совпадают поэлементно (`identity_baseline_vs_cold=true`,
  `identity_baseline_vs_warm=true`); admission-отчёт детерминированно строится из тех же массивов,
  поэтому отчёт совпадает с точностью до `generated_at`.
- Фаза B быстрее A, хотя включает запись: первый запуск платит за импорт/прогрев интерпретатора и
  чтение архива, поэтому «до/после» корректно сравнивать как A → C; B показывает цену заполнения.
- В кэше 100 записей (20 начал × (1 кандидат + 4 члена)), 305 690 байт (~3.0 КБ на запись).

Воспроизведение (скрипт — фрагмент; он же использован для чисел выше):

```python
import sys, time, json
from pathlib import Path
sys.path[:0] = ["tools", "src"]
import run_real_evaluation as runner, eval_cache

cache = eval_cache.ForecastCache(Path("build/eval_cache"))
def window(c=None):
    return runner.build_window("T2_GDP_GROWTH", 0, "W2", "ENSEMBLE_EQUAL", None, "auto",
                               max_origins=20, cache=c)
t = time.perf_counter(); plain = window(); a = time.perf_counter() - t
t = time.perf_counter(); cold = window(cache); b = time.perf_counter() - t
t = time.perf_counter(); warm = window(cache); c = time.perf_counter() - t
print({"no_cache_s": round(a, 2), "cold_s": round(b, 2), "warm_s": round(c, 2),
       "speedup": round(a / c, 2), "cache": cache.stats()})
```

Ограничение методики: для T2 h=0 окно W1 начинается с REAL_TIME только с 1996-12 (винтажи
GS10/TB3MS/CPILFESL; docs/88), поэтому для чистого 20-начального REAL_TIME-среза используется W2;
полный прогон W1+W2 через `run_real_evaluation.py --cache-dir` ускоряется тем же механизмом (кэш
работает внутри `build_window`).

## 6. Идентичность результатов с кэшем и без

Требование «кэш не меняет результаты» проверено на двух уровнях:

1. **Окно (`build_window`)**: без кэша, холодный и тёплый кэш дают поэлементно равные массивы
   `actual_primary`, `actual_secondary`, `candidate.point/quantiles/probability`,
   `comparator.point/quantiles`, `recession`, а также равные `origins`, `vintage_dates`,
   `data_class` (тесты + benchmark).
2. **Слой отчёта (`_sanitized_window`)**: диджесты/счётчики/метаданные окна совпадают, то есть
   опубликованный отчёт 1-в-1 идентичен; единственное отличие отчёта с кэшем и без — поле
   `generated_at` (время прогона), оно и раньше менялось между прогонами.

## 7. Ограничения

- Кэш **opt-in**: по умолчанию и во всех существующих CI-workflow он не используется; включение —
  `--cache-dir`. Существующие workflow не менялись (границы задачи), кэш не коммитится.
- Кэш не имеет TTL: инвалидация контентная (ключ), устаревшие записи удаляет `prune`; размер растёт
  пропорционально числу прогонённых started (≈3 КБ на прогноз; 100 записей ≈0.3 МБ, полный T2-прогон
  в сотни начал — единицы МБ).
- Нет блокировок на конкурентную запись: один каталог кэша рассчитан на один процесс-писатель;
  атомарная замена исключает битые файлы, но два параллельных процесса могут посчитать один ключ
  дважды.
- `data_sha256` покрывает `data/raw` (33 файла); если появится внешний источник вне этого каталога,
  влияющий на прогноз, его нужно добавить в fingerprint (иначе возможен ложный hit).
- Кэшируются только прогнозы; факты, маски и admission пересчитываются каждый прогон — это
  сознательный выбор в пользу PIT-прозрачности (стоимость `actual_pair` мала, ~0.03 с на начало).
- Идентичность отчёта доказана для детерминированных моделей/данных; недетерминированный источник
  (например, случайная инициализация в будущих моделях) потребует явного seed в ключе.

## 9. Дополнение task-68: ключ включает фактический data root и канал прогона

Дефект (разбор — docs/172 §4.2): ключ хешировал только `data/raw`, а `AMFE_DATA_ROOT`/`--data-root`
в fingerprint не входил. Поэтому standard-прогон по `data/raw` получал из `build/eval_cache`
reconstructed-прогнозы primary-прогона по `data/reconstructed` (498 начал до 1996-12 с
`data_class=REAL_TIME`), и REAL_TIME-only срез выходил 204 начала / 16 рецессий / FAIL вместо
121 / 8 / INCONCLUSIVE.

Исправлено в `tools/eval_cache.py` (схема `eval-cache/1.1.0`):

- fingerprint и ключ включают `data_root` (метка фактического root: `AMFE_DATA_ROOT`/`--data-root`,
  иначе `data/raw`), `channel` (`primary` — extended/W1_EXT на reconstructed-root, `standard` —
  REAL_TIME-only) и `data_class` (`REAL_TIME`/`REAL_TIME_RECONSTRUCTED`); `data_sha256` считается
  по файлам фактического root, а не по жёстко заданному `data/raw`;
- `ForecastCache(..., data_root=..., channel=..., data_class=...)`; если явный `data_root`
  противоречит `AMFE_DATA_ROOT`, конструктор падает (fail-closed), чтобы ключ не разошёлся с
  данными, которые реально читает код прогноза;
- primary- и standard-прогоны не делят записи даже на одном root, а replay не может подменить
  `data_class` (ключ разный → пересчёт, старый payload остаётся нетронутым);
- запись другой схемы/fingerprint — явный `stale`/промах, а не тихое использование: `strict=True`
  (в раннере `--cache-strict`) даёт `CacheProvenanceError`, `python tools/eval_cache.py audit
  --dir build/eval_cache` печатает разбивку current/legacy/foreign/corrupt и выходит с кодом 3 при
  несовпадении; `prune` удаляет такие записи.

Старые записи `eval-cache/1.0.0` (в т.ч. 2160 файлов в `build/eval_cache`) больше не используются —
они «сироты» до `prune`. Тесты: `python tests/test_eval_cache.py` — 31 OK (разные data-root → разные
ключи; primary/standard не смешиваются; replay не подменяет `data_class`; явный stale/strict-fail;
чистый прогон == повторный с кэшем, в т.ч. на reconstructed-root и на реальном архиве).

## 10. Дополнение task-69: каноническая запись отчёта и SHA-256 файла
