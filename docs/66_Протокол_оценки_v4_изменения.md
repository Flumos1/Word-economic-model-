## Зачем v4: два решения владельца
1. **D-131 — окно T3.** Винтажи ALFRED по GS10 и TB3MS начинаются 1996-12-03 (docs/65). До этой даты `PROBIT_SPREAD` — `PSEUDO_REAL_TIME`, и у T3 остаётся один REAL_TIME-член (правило Сам) — ниже минимума компаратора, поэтому C1 на W1 для T3 был бы не определён. **W1 для T3 начинается с 1996-12**; начало задано данными, а не результатами.
2. **D-132 — автоматическая загрузка.** Любой ручной шаг загрузки исключён из конвейера. Данные забирает инструмент проекта в CI: по одному ряду за запрос, с ограничением частоты, без FRED API и без кэша API; если величину нельзя получить автоматически в рамках опубликованных условий — она **заменяется собственной моделью или отбрасывается**, и это записывается. Сырые чужие файлы в репозиторий не попадают.

## Как работает автоматическая загрузка
- `tools/fetch_data.py` читает `protocols/data_plan.json` (только ряды со статусом OPEN в реестре), качает последние значения по публичному CSV-эндпоинту и **винтажные наборы** через форму ALFRED download-data (GET страницы с фактическими винтажными датами + POST формы; 6 рядов × 10 фактических дат = 60 пар, из них 24 до 2000 года), с User-Agent проекта, таймаутом, повторами и паузой между запросами; пишет файлы в игнорируемый `data/raw/` и журнал `protocols/data_log.json` (URL, дата, размер, SHA-256, число строк, последнее наблюдение).
- `.github/workflows/data-refresh.yml` запускается по расписанию (1-е число месяца) и вручную; выполняет тот же скрипт на раннере GitHub и выгружает сырые файлы и журнал как **приватный артефакт** (90 дней), ничего не коммитя.
- FRED API не используется (нет ключа, нет API-кэша). Ограничение частоты и поштучная выборка выбраны потому, что квалифицированный запрет условий FRED касается disruptive/bulk-сбора; это прочтение зафиксировано в реестре и является решением владельца, а не юридической консультацией.
- Если источник нельзя получить автоматически: по протоколу v4 величина заменяется собственной моделью (`licence_policy.substitute`) или не используется; ручной обход конвейера не допускается.
- **Первый запуск** (2026-11-11, run `43063461880`) — 7 последних рядов, 0 ошибок. **Винтажный запуск** (run `43070255701`) — success: 13 записей, 0 ошибок; 6 рядов × 10 **фактических** винтажных дат ALFRED (CPIAUCSL 1996-12-12…2020-12-10; GS10/TB3MS с 1996-12-03), `vintage_check: true` у всех — ни одно наблюдение не позже даты винтажа; строки 887/767/295/875/812/1043; USREC (NBER-хронология) загружается последним файлом. Журнал — [protocols/data_log.json](../protocols/data_log.json); сырые файлы остались вне репозитория (игнорируемый `data/raw/` + приватный артефакт).

## Правки после независимой проверки (docs/67)

docs/67 нашёл три блокирующих остатка в первой редакции v4 и один остаток (Б-4) после правок, все исправлены в этой редакции: (Б-1) `PROBIT_SPREAD` больше не зависит от T10Y3M — иначе он оставался PSEUDO_REAL_TIME на всём W1 и сужение окна не давало двух REAL_TIME-членов; (Б-2) инструмент и план реально качают винтажные наборы через форму ALFRED download-data, а не только последние ряды; (Б-3) автоматизация покрывает все используемые источники — NBER-хронология берётся из `USREC` (`data_depth.nber_source_id`), а правило «неавтоматизированный источник не используется» записано в `data_depth.automation_coverage`; (Б-4) `SPF_MEDIAN` исключён из компаратора и контрольных групп до R2 (его файлы не автоматизированы, помесячного y/y в SPF нет), условие `not used` у `ALFRED:USREC` снято, соответствие `NBER_CYCLE_DATES` ↔ `USREC` записано явно.
