# 117. Протокол v5.0.1 (D-156): исправление идентичности еженедельных строк журнала

Дата: 2026-11-14. Автор: Lead. Статус: **FROZEN** (5.0.1; D-156).
Файлы: [protocols/evaluation_protocol_v5.json](../protocols/evaluation_protocol_v5.json) (5.0.1, SHA
`48c2f6a1…`), пин `protocols/evaluation_protocol_v5.sha256`, [tools/registry.py](../tools/registry.py),
[tools/forward_forecast.py](../tools/forward_forecast.py), [registry/README.md](../registry/README.md),
тесты [tests/test_protocol_v5.py](../tests/test_protocol_v5.py), [tests/test_registry.py](../tests/test_registry.py).

## 1. Проблема

В v5 5.0.0 (`docs/107`, D-151) была объявлена еженедельная cadence forward-журнала, чтобы набрать
12 разрешённых прогнозов T1 h=1 примерно за 4–6 месяцев вместо 12. Но identity журнала в
`tools/registry.py` — `(candidate_id, target, horizon, origin)`, где `origin` — месяц `YYYY-MM`.
Вторая строка того же кандидата/горизонта/месяца отклоняется как дубликат. То есть **еженедельная
cadence 5.0.0 была неисполнима**, и оценка C6 «~3–4 месяца» была ошибочной: фактически оставался
12-месячный календарь (12 разных origin). Это обнаружено при подготовке первого еженедельного
выпуска 2026-11-14.

## 2. Исправление (5.0.1)

- Строка журнала получает необязательное поле **`vintage_week`** (`YYYY-Www`, ISO-неделя). У месячной
  якорной строки его нет (`null`).
- **Identity** расширена до `(candidate_id, target, horizon, origin, vintage_week)`: еженедельная
  строка того же месяца — отдельная строка; повтор той же недели — по-прежнему дубликат.
- Валидация: `vintage_week` проверяется по формату; строка не может быть датирована будущим или
  после публикации целевого факта (механизм `forward_forecast.py` сохраняет прежние гварды).
- Протокол: `forward_registry.vintage_week` (field/format/identity/rule/disclosure),
  `meta_gate.amendments`, `decision_ids += D-156`, версия 5.0.1, статус FROZEN, новый пин.
- Критерии оценки, окна, C4-правила, пороги C6 и состав компаратора **не менялись**.

## 3. Что это значит для C6 (честно)

- C6: ≥12 разрешённых прогнозов на пару, кумулятивная относительная потеря ≤1,0, покрытие ±10 п.п.;
  плюс минимум **4 различных целевых периода** (v5).
- При еженедельных строках 12 разрешённых T1 h=1 набираются примерно за **4–6 месяцев** (12 строк при
  4+ разных месяцах), а не за 12.
- **Но** строки одного целевого месяца коррелированы: мощность проверки покрытия низкая, это
  публикуется в каждом C6-отчёте (`registry_resolve.py`). Требование **8 независимых исходов для
  ACTIVE не подменяется** — ACTIVE для T1/T3 всё равно недостижим по потолку протокола, а для T2 h=4
  остаётся многолетним.
- C6 по-прежнему не является «доказательством превосходства»: это негейтящий по существу тест
  живого трека, и он не отменяет C4.

## 4. Практика

- Первая еженедельная строка: origin `2026-11`, `vintage_week=2026-W46`, `registered_at`
  2026-11-14T09:00:00Z; кандидаты `ENSEMBLE_INVERSE_MSE`, `ENSEMBLE_ADAPTIVE` + контроли
  RW/EQUAL_WEIGHT_POINT/EQUAL_WEIGHT_DENSITY. Журнал: 10 строк (5 якорных + 5 недельных),
  `--validate` — valid.
- Дальше: еженедельно `python tools/forward_forecast.py --origin <YYYY-MM> --vintage-week <YYYY-Www> ...`
  (или workflow `forward-registry.yml`), до публикации факта; месячный якорь — после последнего
  релиза данных месяца.
- Проверка: `python tools/registry.py --validate`, `python tools/registry_resolve.py --status`.

## 5. Ограничения

- 5.0.1 — исправление в том же файле v5 (не новый файл): хеш 5.0.0 (`41d6823e…`) остаётся в истории
  git и docs/107; решения о допуске по 5.0.0 не принимались, поэтому пересмотр хеша не затрагивает
  принятых статусов.
- Еженедельные строки не являются независимыми наблюдениями; это раскрыто в протоколе и в каждом
  отчёте C6.
- Внешней публикации/деплоя нет.
