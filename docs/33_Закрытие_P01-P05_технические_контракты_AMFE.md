# AMFE — закрытие P01–P05: технические контракты методологии
Версия 1.1.1 · 2026-11-11. Статус: проектные решения с критериями приёмки; программная реализация, доказательство полноты и эмпирическая проверка ещё не выполнены.

## Область
Устраняются пять пробелов, выявленных в docs/32. Решения распространяются на научные утверждения и их применение, но не заменяют экономико-математическую модель. Сохраняются docs/12, 20, 21, 29, 31, 32 и вся история решений.

## P01 — типизация ограничений, измерений и ошибок

### Контракт Constraint
{constraint_id, kind, expression, variables, units, accounting_scope, time_window, population_scope, currency_basis, measurement_model, tolerance_rule, provenance, assumptions, validity_conditions, severity, version}.

kind:
- DEFINITIONAL_IDENTITY — тождество, верное при согласованных определениях (например, бухгалтерская сумма компонентов); не произвольный статистический закон.
- PHYSICAL_BOUND — физическая/ресурсная граница с условиями применимости.
- INSTITUTIONAL_RULE — юридическое/институциональное правило с юрисдикцией и датами действия.
- MEASUREMENT_RELATION — модель наблюдения, пересмотра статистики, округления и погрешности.
- EMPIRICAL_REGULARITY — наблюдаемая статистическая связь, не обязательная вне области оценки.
- BEHAVIORAL_HYPOTHESIS — проверяемое поведенческое/причинное предположение.
- SCENARIO_ASSUMPTION — условие сценария, не утверждение об истинности.

Валидация: размерность и единицы; время и период; запасы/потоки; номинальные/реальные величины; валюты и конвертация; границы системы; определение агрегатов; источник статистических расхождений. Для DEFINITIONAL_IDENTITY допускается ненулевая невязка **наблюдаемых данных** из-за статистического расхождения, округления или ошибок измерения, но нельзя подменять ею истинность тождества в согласованных определениях. tolerance_rule фиксируется до проверки и обосновывается measurement_model, а не подгоняется под модель.

Реакция: нарушение строгого ограничения в корректно определённом пространстве → BLOCK соответствующей структурной интерпретации; нарушение эмпирического/поведенческого ограничения → REVIEW, а не автоматическое «логически невозможно». Неопределённая классификация → DEFER.

Приёмка P01: модель с неверными единицами отклоняется; бухгалтерская невязка данных не объявляется автоматически нарушением математического тождества; статистическая корреляция не становится обязательным законом.

## P02 — происхождение и независимость доказательств

### Контракт EvidenceLineage
{evidence_id, origin_ids, dataset_ids, dataset_vintages, publication_ids, code_ids, model_ids, transformation_ids, agent_ids, shared_assumptions, funding_or_conflict_flags, independence_assessment, assessment_basis, version}.

Граф происхождения ориентирован от производного результата к первичным данным/публикациям и преобразованиям. Виды связей: DERIVED_FROM, COPIES, REANALYZES, USES_DATA, USES_CODE, SHARES_MODEL, CITES, INDEPENDENTLY_REPLICATES (последняя только после проверки независимости). Несколько обзоров одной работы не считаются независимыми подтверждениями; разные агенты, использующие общий датасет, также не считаются независимыми данными.

Оценка independence_assessment ∈ {INDEPENDENT_WITH_SCOPE, PARTIALLY_DEPENDENT, DEPENDENT, UNKNOWN}; UNKNOWN не интерпретируется как INDEPENDENT. Для вероятностного объединения доказательств требуется явная модель зависимости; простое умножение вероятностей при зависимости запрещено. Скрытые общие источники остаются риском, неустранимым одной декларацией.

Приёмка P02: три пересказа одной работы дают один кластер происхождения; две статьи на общем датасете не объявляются независимой репликацией данных; отсутствие lineage приводит к UNKNOWN и запросу проверки.

## P03 — пересмотр зависимых утверждений

### Контракт DependencyGraph
Узлы: CLAIM, ASSUMPTION, EVIDENCE, MODEL, RESULT. Типы рёбер: REQUIRES, DERIVED_FROM, SUPPORTED_BY, CONTRADICTS, ALTERNATIVE_SUPPORT. Для каждого вывода хранить **наборы достаточных оснований** justification_sets = [{support_ids, rule_id, scope}], а не только одно ребро «зависит от».

### Алгоритм INVALIDATE_AND_REVIEW(changed_node)
1. Сохранить событие и его provenance; проверить подлинность изменения.
2. Найти все downstream-узлы по REQUIRES/DERIVED_FROM/SUPPORTED_BY с ограничением по области.
3. Для каждого затронутого justification_set пересчитать, остаётся ли полный действительный набор оснований; альтернативные независимые пути сохранять.
4. Если нет ни одного действительного обоснования → epistemic_status=UNDER_REVIEW/INCONCLUSIVE (по типу), use_permission=DEFER либо SUSPEND по риску; не объявлять автоматически ложным.
5. Если хотя бы одно достаточное независимое основание осталось → сохранить статус только после проверки его области и достаточности; отметить IMPACT_REVIEWED.
6. При циклах использовать SCC (strongly connected components), проверять внешние основания, не допускать циклического самообоснования.
7. Записать аудит: affected_nodes, justifications_removed, justifications_retained, decisions, reviewer, rule_version; предусмотреть идемпотентность и повторное исполнение.

Приёмка P03: цепочка A→B→C помечается; B с альтернативным независимым основанием не теряет поддержку автоматически; цикл A↔B без внешнего основания не считается доказательством.

## P04 — версионирование критериев и регрессионные испытания

### Контракт RuleSet
{ruleset_id, semver, effective_from, author, change_reason, formal_diff, affected_gates, affected_claim_types, test_suite_version, approval_record, rollback_target, audit_hash}.

Изменение критериев проходит отдельный meta-gate: PROPOSE → DIFF → IMPACT_ANALYSIS → REPLAY → INDEPENDENT_REVIEW → APPROVE/REJECT → DEPLOY → MONITOR. Нельзя задним числом изменять критерии успешности уже завершённого теста: исторический вердикт остаётся с исходной версией правил; новый вердикт — отдельная запись. Для изменения, влияющего на допуски, обязателен replay ранее рассмотренных кейсов и объяснение расхождений. Автоматический rollback возможен лишь по заранее определённым безопасным условиям, без стирания истории.

Приёмка P04: смена порога не переписывает старый отчёт; выявленные изменения статусов перечислены; не прошедшее регрессию правило не допускается к эксплуатации.

## P05 — разделение научного допуска и эксплуатации прогноза

### Два независимых решения
ScientificAdmit(H,E,c,purpose) ∈ {YES,NO,DEFER}: качество утверждения для конкретной научной цели.
OperationalDeploy(model, environment, horizon, risk_policy) ∈ {YES,NO,DEFER}: разрешение модели в действующем прогнозном ядре.

OperationalDeploy=YES требует: (a) согласованные данные и винтажи, (b) воспроизводимый pipeline и тесты, (c) сравнение с сильными baseline, (d) оценка калибровки/ошибок и неопределённости, (e) проверка ограничений P01, (f) безопасность и мониторинг drift, (g) план отката и версионирование, (h) независимая проверка, (i) разрешённая область/горизонт и цена ошибки. Научно интересная гипотеза может быть RESEARCH_ONLY. Предиктор может быть разрешён для прогнозирования без права делать причинные заявления. Научное открытие не следует из OperationalDeploy=YES.

### Статусы развёртывания
CANDIDATE → SHADOW_TEST → LIMITED_DEPLOYMENT → ACTIVE; возможны SUSPENDED, ROLLED_BACK, RETIRED. Переходы обусловлены записанными испытаниями и risk_policy; нет универсального числового порога.

Приёмка P05: «новая причинная гипотеза» не развёртывается без прогностической валидации; успешный предиктор не получает причинного статуса; drift запускает пересмотр или rollback без удаления научной истории.

## Контрактная матрица контрольных примеров
| ID | Случай | Ожидаемый результат |
|---|---|---|
| A01 | Сумма EUR и USD без конвертации | P01 BLOCK |
| A02 | Статистическое расхождение в измеренном балансе | P01 REVIEW measurement_model, не автоматическое логическое опровержение |
| A03 | Три агента цитируют один исходный датасет | P02 DEPENDENT |
| A04 | Неизвестно происхождение результата | P02 UNKNOWN |
| A05 | A→B→C, A признано ошибочным | P03 REVIEW B,C |
| A06 | B имеет независимое альтернативное основание | P03 сохранить возможный допуск только после проверки |
| A07 | A↔B без внешних оснований | P03 NO self-support |
| A08 | Критерий изменён после результата | P04 сохранить старый вердикт, создать новый replay |
| A09 | Новое правило не проходит регрессию | P04 REJECT |
| A10 | Предиктор точен, но причинность не доказана | P05 прогнозный допуск возможен, причинный нет |
| A11 | Научно перспективная модель без OOS проверки | P05 RESEARCH_ONLY |
| A12 | Drift активной модели | P05 REVIEW/SUSPEND/ROLLBACK по risk_policy |

## Что означает «закрыто»
P01–P05 закрыты **как пробелы в архитектурной спецификации**, потому что для каждого есть схема, правило обработки ошибок и проверяемые примеры. Не закрыты как реализованные, формально доказанные или эмпирически подтверждённые механизмы. Реализационные тесты A01–A12 и независимая критика — обязательные задачи следующего этапа.
