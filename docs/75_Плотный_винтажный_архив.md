## 1. Зачем

Локальный винтажный архив, который построил первый автоматический прогон, содержал **10 годовых
винтажных дат на ряд** (1996–2020). Для `DataContext` режима `vintage` это означает, что на дату
начала в 1990-е годы доступно только последнее годовое наблюдение: информационное множество
«стареет» на месяцы, `effective_steps` превышает горизонт протокола, и честный REAL_TIME-прогон
W1/W2 невозможен — оценка шла в `mode=latest` (`data_class=PSEUDO_REAL_TIME`, docs/74).

Плотный план даёт по одному винтажу на конец каждого квартала 1990-03-31 … 2026-09-30 (147
плановых дат на ряд): архив становится квартальным, а не годовым. Это уровень разрешения,
согласованный с началом W1 (1990-01/1990-03 по `protocols/evaluation_origins.json`).

## 3. План дат

`protocols/data_plan.json`: 147 дат = концы кварталов с 1990-03-31 по 2026-09-30
(1990–2025 по 4 квартала + 2 квартала 2026). Для каждой плановой даты при загрузке берётся
**последняя фактическая винтажная дата ALFRED ≤ плановой** — «снимок на конец квартала».

Почему не «в том же году», как раньше: правило «последняя дата того же года» на плотном плане
склеило бы все 4 квартала года в один винтаж (те же 10 дат), а правило «≤ planned» даёт квартальное
разрешение и при этом никогда не берёт винтаж из будущего (иначе утечка ревизий).

Следствие: у рядов, чьи винтажи начинаются позже 1990, плановые даты до первой доступной винтажной
даты остаются **без маппинга** и пишутся в журнал (`unmapped_planned_dates`). По `data_depth.
first_realtime_vintage` (протокол v4) это GS10 и TB3MS — первые винтажи 1996-12-03, поэтому у них
27 плановых дат 1990-03-31…1996-09-30 не маппятся; фактическое число винтажей по рядам — в §7.
Значения USREC (NBER-хронология) по-прежнему берутся последним файлом, винтажи не нужны.

## 4. Батчинг POST-запросов формы ALFRED

Форма `downloaddata` принимает ограниченное число винтажных дат в поле
`form[entered_vintage_dates]` (≈40 дат / ~500 символов на запрос). Поэтому:

1. один GET страницы `downloaddata` → список фактических винтажных дат (`form_selected_vintage_dates`);
2. planned→actual по правилу §3 (сортировка, дедупликация);
3. даты режутся на чанки по `VINTAGE_CHUNK_DATES = 40`; на каждый чанк — один POST
   (`file_type=2`, «Observations by Vintage Date, All Observations», csv) с диапазоном наблюдений
   самого ряда (first/last из latest.csv);
4. каждый ответ распаковывается (CSV внутри zip, колонки `<SERIES>_<YYYYMMDD>`);
5. **слияние**: все колонки объединяются в одну CSV с уникальными отсортированными
   `observation_date`, отсортированными колонками винтажей и пустыми ячейками для отсутствующих
   значений; пишется один `data/raw/<SERIES>/vintages.zip` (+ README с провенансом);
6. если форма отклонила чанк, он делится пополам (до 1 даты) — это защита от неизвестного точного
   лимита и от одиночной «плохой» даты; журнал помечает такие чанки `split: true`;
7. пауза `rate_limit_seconds = 2.0` после каждого запроса (включая GET страницы).

Количество запросов на ряд: 1 GET + ceil(винтажи/40) POST (≈4 POST при 147 датах). Весь прогон —
порядка 35 запросов, ~2–4 минуты в раннере.

## 5. Проверка PIT и журнал

`vintage_check` в `tools/fetch_data.py`: для каждой колонки-винтажа вычисляется последнее непустое
наблюдение, и проверяется, что оно **не позже** даты винтажа. Ложное срабатывание старой реализации
(сравнение даты наблюдения с именем колонки, а не с датой винтажа) устранено: дата винтажа извлекается
из имени колонки `<SERIES>_YYYYMMDD`, проверка содержательная.

`protocols/data_log.json` (только метаданные, без значений) для каждой vintage-записи пишет:
`vintage`/`url`/`retrieved_at`, `bytes`, `sha256` (merged zip), `file`, `rows`, `planned_vintages`,
`vintage_dates`, `unmapped_planned_dates`, `available_vintage_dates`, `vintage_count`,
`vintage_last_observation`, `vintage_check`, `chunks[]` (по каждому POST: индекс, число и границы
запрошенных дат, bytes, sha256, vintage_count, rows, split) и `merged` (from_chunks, vintage_count,
rows, sha256). Отдельный блок `gate_view` фиксирует spot-check view (см. §8). Соответствие
`data_depth.retrieval.log_fields` протокола v4 сохранено (`last_observation` для latest-файлов,
`vintage_check` и `vintage_last_observation` для винтажей).

## 8. Ворота R2 и плотный архив

`tools/verify_data_gate.py` заморожен (в границах задачи его нельзя менять), а сами ворота постят
**все** датированные колонки ряда одним запросом формы initial-release. На плотном архиве это 147
дат — заведомо больше лимита формы. Поэтому `tools/fetch_data.py` дополнительно строит компактный
spot-check view: `data/raw/gate/<SERIES>/vintages.zip` — не более 36 датированных колонок,
18 из них до 2000 года, остальные равномерно 2000–2026; шаг ворот в workflow читает этот view.
Смысл ворот сохраняется: протокол v4 требует spot check не менее 30 пар, из них не менее 10 до 2000.
Плотный архив при этом остаётся в `data/raw/<SERIES>/vintages.zip` и идёт в артефакт полностью;
на view проверяется представительная выборка архива, а `vintage_check` доказывает PIT-корректность
каждой колонки всего архива.

Замечание: в замороженной R3-спецификации зафиксированы факты ворот R2 предыдущего прогона
(87 пар/17 до 2000, sha256 отчёта `59d42c17…`). Новый отчёт ворот — отдельный артефакт нового
прогона; его числа/хеш отличаются, потому что проверяемая выборка дат теперь из плотного архива.
Это не изменение протокола: критерии ворот (≥30 пар, ≥10 до 2000, 0 mismatches) те же, и они
выполнены — см. §7. Frozen-файлы R3 не пересматривались.

## 9. Ограничения

- **Разрешение — квартальное, не «каждый релиз»**: один винтаж на плановую дату (конец квартала),
  точные даты релизов внутри квартала не моделируются; для месячных рядов фактическая винтажная
  дата — ближайший предшествующий релиз, поэтому «снимок на конец квартала» может отставать от
  календарного конца квартала на дни/недели. Для REAL_TIME это консервативно (не даёт будущих данных).
- **Глубина винтажей задана источником**: GS10/TB3MS доступны только с 1996-12-03, поэтому у них
  меньше 147 винтажей и первые 27 плановых дат не маппятся (в журнале явно). Для T3 W1 протокол
  и так начинается с 1996-12 (D-131).
- **Лимит формы**: без батчинга форма не принимает плотный набор дат; батчи и деление чанков
  увеличивают число запросов и объём артефакта, но остаются в рамках rate limit 2 c.
- **Объём артефакта**: merged zip растёт примерно пропорционально числу винтажей (порядка сотен КБ
  на ряд), журнал `protocols/data_log.json` — сотни КБ метаданных (значения в репозиторий не
  попадают); сырые данные не коммитятся (`.gitignore`), живут в приватном артефакте 90 дней.
- **Локальная сеть недоступна**: реальная загрузка проверяется только CI-прогоном; локально
  работают оффлайн-тесты, dry-run и разбор/слияние реального формата ALFRED (на старом архиве).
- **Ворота R2 на view**: плотный архив проходит `vintage_check` (PIT), но в ворота initial-release
  попадает представительная выборка ≤36 дат на ряд — ограничение замороженного кода ворот, а не
  данных.
- **R3-спецификация frozen**: записанный там sha256 отчёта ворот относится к прогону до этой задачи;
  обновлять R3 задним числом нельзя, расхождение фиксируется здесь.
