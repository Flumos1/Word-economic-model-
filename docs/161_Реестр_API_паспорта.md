## 1. Задача и короткий ответ

До G3 реестр модулей и продукты жили отдельно: API отдавал сценарии, клиентский пакет —
отчёт, а паспорт модуля (версия, статус, ограничения, хеши кода/данных) существовал только в
`build/registry/modules.jsonl`. Покупатель/аудитор не мог проверить, **какая версия** модуля
породила числа.

Сделано:

1. **API v2** (`amfe.forecast_api.v2`): новый endpoint `GET /v1/modules` с паспортами **5 модулей**
   (G3-снимок; реестр с 2026-11-18 содержит 7 паспортов — §10);
   у каждого сценария и forecast-конверта появилось поле `module_ref`
   (`module_id`, `version`, `kind`, `status`, `code_sha256`).
2. **Клиентский пакет**: новый файл `10_Module_Passports.json`
   (`amfe.market_client_pack.passports.v1`) — паспорт конкретного модуля + список всех модулей
   реестра (на момент G3 — пять; с 2026-11-18 — семь, §10), SHA-256 реестра, `policy` и
   `numbers_source = MarketResult`.
3. **Совместимость v1**: `--api-version v1` воспроизводит контракт `amfe.forecast_api.v1` **без
   реестра**; v1-файлы лежат в `build/api_v1/` и не ломают старых клиентов.
4. **Fail-closed**: нет/битый реестр → `ForecastApiError`/`MarketPackError`, exit 2, ничего не
   пишется; числа по-прежнему берутся только из `MarketResult`.

## 3. API v2: `/v1/modules` и `module_ref`

Новый endpoint (файл `modules.json`): массив паспортов, у каждого —
`module_id`, `version`, `status`, `kind`, `limitations`, `code_sha256`, `code_files`,
`data_status`, `data_sha256`, `owner`, `display_name`, `created_at`, `docs`, `tests`,
`entrypoints`, `components`, `summary`, и `disclaimer`. Это **ровно** поля реестра; API ничего не
добавляет от себя и не интерпретирует статусы.

Сценарий (`/v1/scenarios/{id}`) и forecast-конверт (`/v1/forecast/{target}`) несут `module_ref`:

```json
"module_ref": {"module_id": "oil.brent", "version": "0.1.0", "kind": "market",
               "status": "RESEARCH_ONLY", "code_sha256": "0bbe243ca6098359…"}
```

Так клиент может однозначно связать числа с версией кода; сами числа остаются из `MarketResult`
(не из паспорта). `index.json` в v2 перечисляет `api_versions = [v1, v2]`,
`backward_compatible_with = amfe.forecast_api.v1`, а `counts` разделяет `modules: 5` (паспорта) и
`market_modules: 1` (модуль-источник сценариев) — это разные сущности, и раньше они смешивались.

**v1-режим.** `python tools/forecast_api.py --api-version v1 --out build/api_v1` создаёт контракт
`schema = amfe.forecast_api.v1`, `api_version = v1`, `counts = {modules: 1, scenarios: 3,
forecasts: 1}`, **без** `/v1/modules` и без `module_ref`, **без чтения реестра**. Тесты проверяют,
что v1-документы не содержат новых полей, а v2 сохраняет все поля v1.

## 4. Клиентский пакет: `10_Module_Passports.json`

Схема `amfe.market_client_pack.passports.v1`, детерминированный артефакт (входит в
`07_Reproducibility.deterministic_artifacts`):

| Поле | Содержимое |
|---|---|
| `schema`, `kind`, `status`, `generated_at`, `client` | метаданные документа; `status = RESEARCH_ONLY` |
| `registry` | путь `build/registry/modules.jsonl` и его SHA-256 (`ab16c5410b351a07…` на G3; с 2026-11-18 — `0373dc8cf005a9ae…`) |
| `module` | паспорт **использованного** модуля (`oil.brent@0.1.0`) |
| `module_ref` | краткая ссылка `module_id@version` + `code_sha256` |
| `all_modules` | все паспорта реестра (5 на G3, 7 с 2026-11-18 — §10), чтобы клиент видел состав платформы |
| `numbers_source` | `MarketResult` (числа не из паспорта) |
| `policy` | `research_only`, `no_admission`, `no_point_forecast`, `no_raw_third_party_data` |
| `disclaimer` | research-only, не прогноз, не инвестсовет |

Паспорт также попадает в `04_Machine_Readable.json` (как `module_ref`) и в `README.md` пакета;
README/executive-summary показывают версию модуля. DOCX/PDF/XLSX остаются презентационными
контейнерами — их содержимое не меняет чисел.

## 5. Fail-closed и детерминизм

- **Реестр обязателен**: `load_registry()`/`load_module_passports()` бросают ошибку, если
  `build/registry/modules.jsonl` отсутствует или пуст; CLI → exit 2, ничего не пишется.
- **Ошибка реестра не маскируется**: битый JSONL/невалидный паспорт → ошибка, а не «пропуск модуля».
- **Детерминизм**: при одинаковом `--generated-at` `modules.json`, паспорта модулей и
  `10_Module_Passports.json` байт-стабильны; реестр читается как снимок (append-only, но без времени
  в экспорте API, кроме полей самих паспортов).
- **Числа не подменяются**: ни API, ни пакет не берут числа из паспорта; тесты сверяют ключевые
  числа с `MarketResult` (пик 168.85584, диапазон 139.04178/268.523395, средняя 130.098032).

## 7. Ограничения

1. **Паспорт — метаданные, не допуск**: `RESEARCH_ONLY` в паспорте не означает ни CANDIDATE, ни
   «проверено внешним ревью»; статус меняется только через реестр с критериями (docs/157).
2. **`code_sha256` — хеш перечисленных файлов**, а не всего репозитория/коммита: файл,
   не попавший в `code_files`, не защищён хешем.
3. **Реестр — ручные записи**: `register_modules.py` строит паспорта из манифестов модулей, но
   проверка «код действительно такой» ограничена хешами файлов; git-коммит не фиксируется.
4. **v1 и v2 поддерживаются параллельно**: это дублирование кода контракта; при изменении полей
   нужно обновлять оба режима и тесты, иначе клиенты v1 разъедутся с v2.
5. **API статический**: `/v1/modules` — файл, а не живой endpoint; нет авторизации, версий во
   времени (только снимок).
6. **Паспорт содержит ограничения, но не оценку качества**: «у модели 3 ограничения» не значит
   «модель плохая/хорошая»; это честный список.
7. **Сырые данные не передаются**: паспорт хранит `data_status`/`data_sha256`, но не сами ряды;
   `LOCAL_ONLY`/`ASSUMPTION_BASED` — прямой запрет на цитирование как наблюдений.

## 8. Воспроизведение

```powershell
python tools/register_modules.py --registry build/registry/modules.jsonl
python tools/forecast_api.py --out build/api --generated-at 2026-11-16T10:00:00Z
python tools/forecast_api.py --api-version v1 --out build/api_v1 --generated-at 2026-11-16T10:00:00Z
python tools/market_client_pack.py --scenario hormuz_closed_6m --generated-at 2026-11-16T10:00:00Z `
    --out build/client_pack/market_hormuz_6m

```

Коды возврата: `0` — артефакты записаны; `2` — fail-closed (нет реестра/пакета модуля, неизвестный
сценарий/таргет). Внешняя проверка после регенерации: `python tools/external_review_g2.py`
(должна снова дать `PASS`; при расхождении docs/156 с новыми артефактами — замечание, а не тихий
пропуск).

## 9. Следующий шаг (не обещание)

1. Добавить в паспорт **git-коммит/дату регистрации** и проверку «файлы не изменились с момента
   регистрации» (CI-шаг, а не только хеши в JSON).
2. Ввести **историю версий** в API (`/v1/modules/{id}/versions`) и правило «продукт ссылается на
   зарегистрированную версию»; сейчас API отдаёт только текущий снимок.
3. Связать `source_id` паспорта с реестром источников (docs/162): для `ASSUMPTION_BASED`-модулей
   показать, какие источники заменят допущения.
4. Убрать дублирование v1/v2: генерировать v1-представление из v2-контракта, а не поддерживать
   два набора полей руками.
5. Проверять паспорт внешним ревьюером (docs/160): сейчас ревьюер проверяет API, но не сверяет
   `code_sha256` паспорта с фактическими файлами модуля — это следующий шаг.
6. Перегенерировать `build/api`, `build/api_v1` и клиентский пакет под 7 паспортов (§10) и вместе с
   этим обновить docs/156 + прогон `tools/external_review_g2.py`: сейчас продукты — G3-снимок.
7. Ввести **таргеты прогноза по модулю**: `build_forecast` сейчас собирает нефтяной конверт
   (`price_peak`/`price_mean`/`brent_range_*`) для любого зарегистрированного `MarketModule`, поэтому
   в процессе, где импортирован газ, `/v1/forecast` падает `KeyError: 'price_peak'`. Для газа нужен
   свой конверт (TTF/JKM), а пока — явный список модулей с прогнозным контрактом и fail-closed
   ошибка вместо `KeyError` (docs/157 §4.1, docs/161 §10 п. 2). **Выполнено в §11.**

   `secondary` (JKM, Henry Hub reference, арбитражная полоса/добор СПГ, storage end). Статус
   `RESEARCH_ONLY`, без raw-рядов, без `assumptions`/`meta` в конверте.
3. **Газ в v2 по умолчанию**: `get_modules()` импортирует `amfe.markets.gas` (саморегистрация), v1
   остаётся нефтяным — явный фильтр `oil.brent`, `counts = {modules: 1, scenarios: 3, forecasts: 1}`.
4. **Индекс/OpenAPI**: `policy.no_point_forecast = false` (у газа есть central point),
   `policy.no_probability_forecast = true`, `no_raw_third_party_data = true`; у `forecasts[]` —
   `kind`, `default_scenario`, `point_estimate`, `interval`; `x-forecast-targets` описывает
   алиасы и семантику; в `Forecast` добавлены `point`/`interval`/`secondary`.
5. **Live-шлюз**: `forecast_api_server` отдаёт `gas_ttf` из того же `build/api` (алиасы
   `gas.lng_eu`/`gas_lng_eu`/`ttf`), провижининг газа не ломает `oil_brent`.
6. **Fail-closed без `KeyError`**: неизвестный target → `ForecastApiError`; нет реестра → exit 2,
   ничего не пишется. Тесты: `test_forecast_api` — **17** (газовый конверт, oil back-compat,
   7 паспортов, generic `storage` kind, no raw, fail-closed, CLI, детерминизм);
   `test_forecast_api_server` — **39** (газовый endpoint/алиасы/no raw).
