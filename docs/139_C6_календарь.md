# 139. C6-календарь и автоматизация гейта

Дата: 2026-11-14. Статус: **операционный инструмент; календарь — оценка, не обещание даты и не
допуск.** Файлы: [tools/c6_calendar.py](../tools/c6_calendar.py),
[tests/test_c6_calendar.py](../tests/test_c6_calendar.py) (16 тестов),
минимальная правка [tools/shadow_track.py](../tools/shadow_track.py) (`--with-calendar`).
Вход: `build/shadow/shadow_status.json` (производный артефакт `tools/shadow_track.py`); журнал
`registry/forecasts.jsonl` не изменяется, строки не создаются.

## 1. Правила регистрации (docs/119, протокол v5 C6)

1. **Только релизные недели.** Строка кандидата регистрируется лишь на неделе, в которую вышел
   первый релиз данных по цели (CPI ~10–15 число, payrolls ~первая пятница, иногда GDP/claims).
   В недели без релиза строк нет — «добирать» строки нельзя.
2. **Point-in-time.** Строка фиксирует origin и target period в момент регистрации; значения
   прогноза и факта не добавляются задним числом и не пересчитываются под результат.
3. **C6 = ≥12 разрешённых прогнозов и ≥4 различных целевых периодов** (плюс loss ≤ 1.00 и покрытие
   в допуске по разрешённой выборке). Счётчики берутся из статуса теневого трека, календарь их не
   пересчитывает.
4. Один целевой месяц даёт одну строку (недельные строки одного месяца коррелированы), поэтому
   4 разных периода — это не менее 4 календарных месяцев наблюдений.
5. Остановка/предупреждения по cadence: нет новых строк > 35 дней — `SUSPEND_CADENCE` (> 25 —
   WARN), loss > 1.10 после ≥6 разрешённых — стоп, > 1.00 — WARN.

## 3. Календарь до гейта (оценка)

Модель: средняя частота релизных недель **2,5/мес** (шаг ≈12 дней), лаг разрешения **30 дней**
(допущение статуса), даты привязаны к понедельникам ISO-недель. Начало — дата статуса
2026-11-14. Строки помечены `PROJECTED_NOT_REGISTERED` — это окна регистрации, а не записи журнала.

| 1 | 2026-W48 | 2026-11-23 | 2026-12 | 2026-12-23 |
| 2 | 2026-W50 | 2026-12-07 | 2027-01 | 2027-01-06 |

Ключевые даты:

* **12-й разрешённый прогноз: 2027-04-21** (через ~23 недели от статуса; 1 строка уже
  зарегистрирована и разрешится первой).
* **4-й различный целевой период: 2027-02-01** (период считается по зарегистрированной строке,
  поэтому дата — неделя регистрации, без лага).
* **Ориентир гейта C6: 2027-04-21** (≈5,3 мес. от статуса) — максимум из двух дат; loss/coverage
  проверяются на разрешённой выборке после 12-го прогноза.
* Статус даёт ориентир 2027-05-07; календарь на 16 дней раньше, потому что статус считает «12 строк
  к разрешению» без учёта уже зарегистрированной pending-строки. Разница помечена INFO
  (`PROJECTION_SHIFT`) с объяснением, а не скрыта.

## 4. Что автоматизировано

* `tools/shadow_track.py` — еженедельный статус (журнал → разрешённые строки → алерты/проекция),
  пишет `build/shadow/shadow_status.json|md`; с `--with-calendar` добавляет блок `calendar`
  (обратная совместимость: без флага документ прежней формы).
* `tools/c6_calendar.py` — календарь из статуса: прогресс, недели регистрации, даты 12-го прогноза
  и 4-го периода, ориентир гейта, предупреждения (`MISSED_RELEASE_WARN/ALERT`, `PROJECTION_SHIFT`,
  `PENDING_RESOLUTION`, `NO_ROWS`, `PERIODS_AFTER_COUNT`, `GATE_REACHED`); CLI `--json`,
  `--out` (каталог или `.json`/`.md`), `--date` (детерминированный якорь), `--resolution-lag-days`.
* Детерминизм: нет чтения системных часов и меток времени; один и тот же статус/дата дают
  байт-идентичные JSON/MD (проверяется тестом). Fail-closed: отсутствие/битый статус, отсутствие
  ключей, отрицательные счётчики, `rows_candidate > rows_total`, `distinct > rows`,
  нулевая частота релизов → ошибка и exit 1, а не «примерный» календарь.

## 5. Что требует человека

* Подтвердить **реальные релизные недели** по календарю BLS/BEA (CPI, payrolls, GDP/claims) и
  зарегистрировать строку вручную через `tools/registry.py`; календарь — только окна.
* Проверить, что origin/target period корректны и PIT-правило соблюдено (нет задним числом).
* После 12 разрешённых: проверить loss ≤ 1.00 и покрытие по каждому loss (это делают факты, не
  календарь), затем принять решение по LIMITED_DEPLOYMENT.
* Обновить статус (`tools/shadow_track.py`) в неделю без релиза, если пропуск/сдвиг — запись в
  журнале решений.

## 6. Ограничения

1. **Дата — оценка, не обещание.** Календарь построен по средней частоте 2,5 релизных недель/мес;
   реальные недели зависят от календаря статистики и могут сдвинуть даты. Пересчитывать при каждом
   обновлении статуса.
2. **Лаг разрешения 30 дней** — допущение статуса; фактическая публикация факта может быть позже
   (пересмотры, задержки) — тогда 12-й прогноз разрешится позже.
3. **Целевой период projected-недель — оценка** (месяц после origin); это не журнальное значение.
4. Счётчики (0/12, 1/4) берутся из статуса теневого трека; календарь не пересчитывает C6 и не
   подменяет loss/coverage-проверки. 4 разных периода считаются по зарегистрированным строкам
   (правило журнала), а не по разрешённым.
5. Строки не фабрикуются: projected-недели помечены `PROJECTED_NOT_REGISTERED`; инструмент не
   пишет журнал, не меняет протоколы и не содержит сторонних наблюдений.
6. Статус может устареть: при `--date` позже статуса и пропущенном cadence выдаётся
   `MISSED_RELEASE_*`/`STALE_STATUS`; обновление статуса — задача еженедельного CI.

## 7. Воспроизведение

```
python tools/shadow_track.py --root . --date 2026-11-14 --with-calendar
python tools/c6_calendar.py                              # сводка
python tools/c6_calendar.py --json                       # документ на stdout
python tools/c6_calendar.py --out build/shadow           # c6_calendar.json + c6_calendar.md
python tests/test_c6_calendar.py                         # 16 тестов
```

Источник SHA-256 и дата статуса записываются в `source` документа календаря; выходные файлы —
производные артефакты (`build/`), в git не коммитятся.
