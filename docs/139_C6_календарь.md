# 139. C6-календарь и операционный процесс

Дата: 2026-11-18 (обновление; впервые 2026-11-14). Статус: **операционный инструмент; календарь —
оценка, не обещание даты и не допуск; C6 не пройден.** Файлы:
[tools/c6_calendar.py](../tools/c6_calendar.py), [tests/test_c6_calendar.py](../tests/test_c6_calendar.py)
(37 тестов: 16 календарных + 21 процессных), минимальная правка
[tools/shadow_track.py](../tools/shadow_track.py) (`--with-calendar`),
[.github/workflows/forward-registry.yml](../.github/workflows/forward-registry.yml).
Вход: `registry/forecasts.jsonl` (append-only журнал) и `build/shadow/shadow_status.json`
(производный артефакт `tools/shadow_track.py`); аудит процесса —
`build/c6/c6_audit.jsonl` (производный, в git не коммитится).

## 1. Правила регистрации (docs/119, протокол v5 C6)

1. **Только релизные недели.** Строка кандидата регистрируется лишь на неделе, в которую вышел
   первый релиз данных по цели (CPI ~10–15 число, payrolls ~первая пятница, иногда GDP/claims).
   В недели без релиза строк нет — «добирать» строки нельзя. Инструмент проверяет формат недели,
   но **факт релиза подтверждает человек** по календарю BLS/BEA.
2. **Point-in-time.** Строка фиксирует origin и target period в момент регистрации; значения
   прогноза и факта не добавляются задним числом и не пересчитываются под результат. Регистрация
   разрешена только в текущей ISO-неделе (`vintage_week` = неделя `--date` и `registered_at`);
   прошлые и будущие недели отвергаются.
3. **Контрольная группа.** Строка кандидата без компараторов не регистрируется: для T1/T2 в том же
   батче или в журнале должны быть `EQUAL_WEIGHT_POINT` (RMSE) и `EQUAL_WEIGHT_DENSITY` (CRPS),
   для T3 — `EQUAL_WEIGHT_DENSITY` (Brier). Это те плечи, с которыми `tools/registry_resolve.py`
   считает относительные потери C6.
4. **Без look-ahead.** Если первая публикация факта целевого периода уже существует, регистрация
   отвергается; при разрешении факт учитывается только если дата его первой публикации ≤ отчётной
   даты. Значение факта не выводится и не пишется — только идентификаторы, даты и счётчики.
5. **C6 = ≥12 разрешённых прогнозов и ≥4 различных целевых периодов** (плюс loss ≤ 1.00 и покрытие
   в допуске по разрешённой выборке). Счётчики берутся из журнала и фактов; loss/coverage считает
   `tools/registry_resolve.py`, календарь их не пересчитывает.
6. Один целевой месяц даёт одну строку на неделю (недельные строки одного месяца коррелированы),
   поэтому 4 разных периода — это не менее 4 календарных месяцев наблюдений.
7. Остановка/предупреждения по cadence: нет новых строк > 35 дней — `SUSPEND_CADENCE` (> 25 —
   WARN), loss > 1.10 после ≥6 разрешённых — стоп, > 1.00 — WARN.

## 4. Что автоматизировано

* `tools/forward_forecast.py` — строит недельные строки кандидата и контрольных плеч
  (`--vintage-week`, `--dry-run`, `--out`), отказывает при опубликованном факте.
* `tools/c6_calendar.py` — два режима:
  * **календарь** (по умолчанию): прогресс, недели регистрации, даты 12-го прогноза и 4-го периода,
    ориентир гейта, предупреждения (`MISSED_RELEASE_WARN/ALERT`, `PROJECTION_SHIFT`,
    `PENDING_RESOLUTION`, `NO_ROWS`, `PERIODS_AFTER_COUNT`, `GATE_REACHED`); CLI `--json`,
    `--out`, `--date`, `--resolution-lag-days`;
  * **операционный процесс**: `--register` (регистрация недельного батча с контрольной группой),
    `--resolve` (автоматическое разрешение по первой публикации), `--weekly` (один недельный цикл:
    регистрация → разрешение → отчёт → `WEEK_CHECK`), `--report`/`--report-out` (отчёт 12/4).
    Общие флаги: `--journal`, `--audit`, `--records`, `--date`, `--dry-run`, `--strict`,
    `--candidate/--target/--horizon`.
* Аудит-лог `build/c6/c6_audit.jsonl` — append-only JSON Lines: `ROW_REGISTERED`, `ROW_RESOLVED`,
  `WEEK_CHECK`. Повторный запуск идемпотен: те же события не дублируются, разрешённая строка не
  разрешается второй раз.
* Отчёт `build/c6/c6_report.json|md`: 12/4 статус, недели (строка/контроль/проверка), полнота
  контрольной группы, неразрешённые и просроченные строки, алерты, SHA-256 журнала и аудита.
* Детерминизм: функции отчёта не читают системные часы и не пишут меток времени; один и тот же
  журнал/аудит/`--date` дают байт-идентичный JSON (проверяется тестом).
* Fail-closed: битый журнал/аудит, отсутствие файла записей, неполная контрольная группа, прошлая/
  будущая неделя, опубликованный факт, дубликат с другим содержимым, отрицательные счётчики →
  ошибка и exit 1, а не «примерный» отчёт.

## 5. Runbook: что делать еженедельно

**Роль:** `evaluation-harness` (наука) исполняет; `dense-vintages` проверяет артефакты и
публикацию; `Lead` коммитит журнал и принимает решения. Время: **пятница после релиза**
(CPI ~10–15 число, payrolls ~первая пятница).

| Шаг | Действие | Команда / проверка | Результат |
|---|---|---|---|
| 0 | Открыть неделю | `date -u +%G-W%V` | ISO-неделя |
| 1 | Проверить календарь BLS/BEA: был ли первый релиз по цели | календарь/новости | «релизная» / «нет» |
| 2 | Если релизной **нет** — строку не добавлять | — | фиксируется только `WEEK_CHECK` |
| 3 | Если релизная **есть** — собрать батч (кандидат + контрольные плечи) | `python tools/forward_forecast.py --origin <YYYY-MM> --candidates ENSEMBLE_REGIME_V4 --targets T1_CPI_YOY:1 --mode latest --vintage-week <YYYY-Www> --dry-run --out build/forward_week.json` | `rows` без записи в журнал |
| 4 | Зарегистрировать недельный цикл | `python tools/c6_calendar.py --weekly --records build/forward_week.json --date <YYYY-MM-DD> --audit build/c6/c6_audit.jsonl --report-out build/c6` | строки + `WEEK_CHECK` + отчёт |
| 5 | Проверить отчёт | `build/c6/c6_report.md`: 12/4, контрольная группа, алерты | нет `ALERT` |
| 6 | Проверить журнал и C6-потери | `python tools/registry.py --validate`; `python tools/registry_resolve.py --status > build/c6/c6_status.json` | `valid: true`, статус честный |
| 7 | Мониторинг трека | `python tools/shadow_track.py --with-calendar` | `build/shadow/<дата>.md|json` |
| 8 | Запись | при изменении статуса — решение D-…; иначе артефакты + строка журнала | след в журнале решений |

Если релизной недели не было, шаги 3–4 не выполняются; вместо них достаточно:

```powershell
python tools/c6_calendar.py --weekly --date <YYYY-MM-DD> --audit build/c6/c6_audit.jsonl `
  --report-out build/c6
```

Это ставит `WEEK_CHECK` (процесс не пропущен) и пересчитывает отчёт без новых строк.

**Если неделя пропущена:**

1. `MISSED_WEEK` (WARN) — одна завершённая неделя без строки. Проверить, была ли она релизной:
   если да — зафиксировать пропуск в журнале решений; строку задним числом **не добавлять**.
2. `MISSED_WEEK_ALERT` (ALERT, ≥2 недель подряд) — разобрать причину (нет релизов / забыли /
   сломан CI), восстановить cadence в ближайшую релизную неделю, записать решение.
3. `MISSED_CHECK` (ALERT) — не выполнялся еженедельный цикл. Выполнить `--weekly` за текущую
   неделю; прошлые `WEEK_CHECK` не выдумывать (аудит append-only).
4. `UNRESOLVED_LATE` / `UNRESOLVED_OVERDUE` — проверить публикацию факта и винтажный архив;
   если факт опубликован, `--resolve` разрешит строки; если архива нет — `FACTS_UNAVAILABLE`,
   данные не подменять.
5. `CONTROL_GROUP_MISSING` — не регистрировать кандидата без компараторов; добрать недостающее
   плечо в том же батче (это не «доливка» прогноза, а недостающая контрольная строка).
6. `SUSPEND_CADENCE` / `SUSPEND_LOSS` / `SUSPEND_COVERAGE` — по docs/119: остановка, разбор,
   возврат только новым предрегистрированным кандидатом.

## 6. Разрешение и аудит: семантика

* **Первая публикация.** `tools/registry_resolve.py` использует `actual_pair`: primary — первая
  архивная винтажная дата, содержащая целевой период; secondary — винтаж через 12 месяцев.
  В аудит пишется только `first_publication` (дата), без значения.
* **No look-ahead.** Если `first_publication > --date`, строка не разрешается и попадает в
  `FUTURE_FACT_BLOCKED`; если факт уже опубликован на момент регистрации — регистрация отвергается.
* **Аудит.** `build/c6/c6_audit.jsonl` — производный артефакт: журнал прогнозов остаётся
  единственным append-only источником, коммитится человеком. Аудит можно потерять при clean
  checkout; это осознанно: он не заменяет журнал и не содержит значений фактов. Для CI артефакт
  `build/c6/` загружается в run artifact.
* **Повторный запуск.** `--weekly` за ту же дату не дублирует `WEEK_CHECK` и `ROW_RESOLVED`;
  `--register` с байт-идентичным батчем пропускает строки (`skipped`), с другим содержимым —
  ошибка append-only.
* **Границы.** Батч пишется построчно (не транзакция); при сбое посередине часть строк может уже
  быть в журнале — повторный запуск идемпотентен, но факт частичной записи нужно проверить
  `python tools/registry.py --validate`.

## 7. Алерты процесса

| Код | Уровень | Значение |
|---|---|---|
| `MISSED_WEEK` | WARN | завершённая неделя без строки кандидата (проверить, была ли релизной) |
| `MISSED_WEEK_ALERT` | ALERT | ≥2 завершённых недель подряд без строки кандидата |
| `MISSED_CHECK` | ALERT | нет `WEEK_CHECK` за завершённую неделю после старта аудита |
| `CONTROL_GROUP_MISSING` | ALERT | у группы нет обязательных компараторов |
| `UNRESOLVED_LATE` | WARN | строка не разрешена > 30 дней после конца целевого периода |
| `UNRESOLVED_OVERDUE` | ALERT | строка не разрешена > 45 дней после конца целевого периода |
| `FUTURE_FACT_BLOCKED` | INFO | первая публикация позже отчётной даты (no look-ahead) |
| `FACTS_UNAVAILABLE` | WARN | нет локального винтажного архива; разрешение/просрочка не проверяются |
| `NO_AUDIT` | INFO | аудит пуст: истории процесса ещё нет (не выдаётся за «0 пропусков») |
| `NO_ROWS` | WARN | в журнале нет строк кандидата по паре |
| `COUNTS_MET` | INFO | 12/4 по количеству и периодам выполнены; loss/coverage ещё нужны |

`--strict` возвращает exit 2 при любом `ALERT` (для CI-гейта); без `--strict` отчёт печатает
алерты, но не валит сборку.

## 8. CI

`forward-registry.yml`:

* месячный запуск 15-го (как раньше) — строит месячные якорные строки, валидирует журнал;
* **новый недельный запуск (пятница, 15:00 UTC)** — `--weekly --date <сегодня> --audit
  build/c6/c6_audit.jsonl --report-out build/c6`: разрешение + отчёт + `WEEK_CHECK`, без
  автоматической регистрации (релизную неделю подтверждает человек);
* аудит-лог восстанавливается из артефакта последнего успешного прогона этого workflow, поэтому
  `MISSED_CHECK` видит пропуски между неделями; если артефакта ещё нет, история процесса
  начинается с текущей недели и ложных пропусков не выставляет;
* ручной `workflow_dispatch` с `register=true` и `vintage_week=YYYY-Www` — собирает батч
  (`forward_forecast --dry-run --out`) и регистрирует его через `c6_calendar --register`
  (контрольная группа и no-look-ahead проверяются инструментом);
* workflow **не коммитит** журнал: `registry/forecasts.jsonl`, `build/c6/*` и `build/forward_week.json`
  загружаются артефактом; коммит делает Lead после проверки.

## 9. Ограничения

1. **Дата — оценка, не обещание.** Календарь построен по средней частоте 2,5 релизных недель/мес;
   реальные недели зависят от календаря статистики и могут сдвинуть даты.
2. **Лаг разрешения 30 дней** — допущение статуса; фактическая публикация факта может быть позже
   (пересмотры, задержки).
3. **Первая публикация приблизительна.** Архив винтажей квартальный: «первая публикация» — первая
   архивная дата, содержащая наблюдение; это документированное приближение, а не точная дата релиза.
4. **Релизная неделя — человеческое решение.** Инструмент проверяет ISO-неделю, PIT и контрольную
   группу, но не знает календарь BLS/BEA; в неделю без релиза строку добавлять нельзя.
5. **Loss/coverage не в отчёте процесса.** Отчёт даёт 12/4 и алерты; C6-потери и покрытие считает
   `tools/registry_resolve.py` по разрешённой выборке. `gate` не может быть `PASS` без них.
6. **4 периода — по зарегистрированным строкам** (правило журнала); разрешённых периодов может быть
   меньше, это показывается отдельно.
7. **Аудит производный.** `build/` не коммитится; история процесса может быть потеряна. Журнал
   прогнозов — единственный постоянный источник.
8. Счётчики 0/12 и 1/4 взяты из журнала на 2026-11-18; при обновлении журнала отчёт пересчитать.

## 10. Воспроизведение

```powershell
# календарь (оценка)
python tools/shadow_track.py --root . --date 2026-11-18 --with-calendar
python tools/c6_calendar.py --status build/shadow/shadow_status.json
python tools/c6_calendar.py --json
python tools/c6_calendar.py --out build/shadow

# операционный процесс
python tools/c6_calendar.py --weekly --date 2026-11-18 --report-out build/c6
python tools/c6_calendar.py --report --date 2026-11-18
python tools/c6_calendar.py --resolve --date 2026-11-18 --audit build/c6/c6_audit.jsonl
python tools/c6_calendar.py --register --records build/forward_week.json --date 2026-11-20

# проверки
python tests/test_c6_calendar.py            # 37 тестов
python tools/registry.py --validate
python tools/registry_resolve.py --status
```

Источник SHA-256 и дата статуса записываются в `source` документа календаря; выходные файлы —
производные артефакты (`build/`), в git не коммитятся.
