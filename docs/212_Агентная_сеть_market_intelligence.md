## 0. Резюме

- Собрана сеть из **11 узлов: 1 lead (Director) + 10 ролей**: 5 сегментных, 2 сборщика,
  3 контрольных/выходных. Покрытие портфеля — **20/20 аккаунтов**, каждый закреплён ровно за
  одной ролью.
- Процесс зафиксирован как конвейер **вопрос → source plan → collect → grade → analysis → case →
  QA → KB** с владельцем на каждом шаге и пятью воротами.
- Границы вынесены в машиночитаемый блок `boundaries` и в `playbooks/red_lines.md`
  (RL-01…RL-18): только законные источники, «закрытые базы» — только по подписке/разрешению, OSINT
  без взлома и обхода авторизации, без персональных данных, без подкупа, санкционный комплаенс.
- Инструмент `tools/market_intel.py` валидирует схему и генерирует task brief; **сети не касается,
  данных не выдумывает**, fail-closed (exit 2).
- Честное ограничение: **в среде нет сети и внешних БД**, поэтому ни один факт о рынке не
  повышен до `VERIFIED`; адаптеры описаны, вызовы не выполнялись.

## 1. Задача и границы

Задача сети — превращать решение-релевантный вопрос («что будет с бюджетом при шоке цены», «где
TCO хуже», «что меняет логистика») в **проверяемый** материал: источник → grade → статус →
сценарий → кейс → независимая проверка → запись в базу знаний.

Границы (зафиксированы в `org.json` → `boundaries`, продублированы в плейбуках):

| Тема | Правило |
|---|---|
| Источники | открытые публикации, публичная отчётность/раскрытие, регуляторная статистика, лицензированные БД с доступом |
| Закрытые базы | только подписка или письменное разрешение; ключи и доступы не в репозитории |
| OSINT | открытые страницы и публичные реестры; **без** взлома, обхода авторизации/paywall/robots/terms/лимитов |
| Персональные данные | не собираются и не хранятся; только корпоративные роли, контакты — через человека |
| Добросовестность | без подкупа, оплаты за конфиденциальную информацию, недобросовестной конкуренции |
| Санкции | комплаенс до касания; ограничение фиксируется, а не обходится |
| Код | не обходит авторизацию, платный доступ и технические ограничения |
| Сеть в среде | отсутствует: адаптеры описываются, данные не подставляются |
| Выдумывание | нет данных → `NOT_FETCHED`; оценка → `HYPOTHESIS`; цифра без источника запрещена |
| Публикация | агент ничего не отправляет и не публикует |

## 2. Организационная схема

```
director (lead) — вопрос, подвопросы, source plan, evidence ceiling
├── сегменты: upstream · gas-lng · downstream-chemicals · services-equipment · trading-shipping
├── сбор:     osint-scout · licensed-data
└── контроль: evidence-qa · case-writer · kb-librarian
```

| Роль | Слой | Зона | Аккаунты | Evidence ceiling | Ревьюер |
|---|---|---|---:|---|---|
| `director` | lead | вопрос, план, конфликты, передача в QA | — | PARTIAL | `lead` (вне сети) |
| `upstream` | segment | upstream-экономика + интегрированные E&P (владелец континуитета) | 10 | PARTIAL | `evidence-qa` |
| `gas-lng` | segment | газ, СПГ, спреды, фрахт, санкции | 4 | PARTIAL | `evidence-qa` |
| `downstream-chemicals` | segment | переработка, нефтехимия, TCO сырья | 4 | PARTIAL | `evidence-qa` |
| `services-equipment` | segment | сервис/оборудование: watch-list, база для TCO | 0 | PARTIAL | `evidence-qa` |
| `trading-shipping` | segment | трейдинг, маршруты, фрахт, страхование | 2 | PARTIAL | `evidence-qa` |
| `osint-scout` | collection | открытые страницы/реестры, collection log | — | PARTIAL | `evidence-qa` |
| `licensed-data` | collection | подписки, условия, запрет перепродажи | — | VERIFIED | `evidence-qa` |
| `evidence-qa` | control | grade/статус, независимая проверка, подпись `VERIFIED` | — | VERIFIED | `director` |
| `case-writer` | output | кейс/one-pager из проверенного | — | PARTIAL | `evidence-qa` |
| `kb-librarian` | control | inbox → validate → merge → index | — | PARTIAL | `evidence-qa` |

**Почему 11, а не 12.** Портфель `marketing/target_accounts.json` — 20 нефтегазовых аккаунтов;
сегмент «энергетика и промышленные потребители» в нём отсутствует. Роль под него вынесена в
`deferred_roles` с чек-листом активации: выдумывать аккаунты и сегмент запрещено.
Валидатор проверяет, что **каждый** портфельный сегмент покрыт, а каждый аккаунт закреплён ровно
за одной ролью.

**Независимость.** `review_role` не может указывать на себя; цепочка ревью обязана завершаться,
а верхний уровень (`director`) проверяется **внешним** ревьюером `lead`
(`protocols/agent_roles.json`), потому что сеть не может проверять себя сама.
`VERIFIED` подписывают только `evidence-qa` и `licensed-data`; Director — не выше `PARTIAL`.

## 3. Процесс и ворота

| Шаг | Владелец | Выход | Условие перехода |
|---|---|---|---|
| QUESTION | `director` | вопрос + 3–5 подвопросов | вопрос законно закрываем |
| SOURCE_PLAN | `director` | класс источника → grade → доступ | нет запрещённых источников |
| COLLECT | `osint-scout` / `licensed-data` | collection log (URL, дата, цитата) | каждая строка с источником или `NOT_FETCHED` |
| GRADE | `evidence-qa` | grade A/B/C + статус | завышенное понижено |
| ANALYSIS | сегментная роль | сценарии, допущения, диапазоны | только вокруг подтверждённого |
| CASE | `case-writer` | кейс/one-pager | ни одного числа вне evidence |
| QA | `evidence-qa` | CONFIRMED / WITH_NOTES / NOT_CONFIRMED | 0 непроверенных claim без пометки |
| KB | `kb-librarian` | запись + индекс | `tools/kb.py --check` зелёный |

Ворота (`review_gates`): source plan → evidence → independence → lawful → KB. Пока у артефакта нет
статуса и источника, шаг не закрыт.

Шкала: grade — сила источника, статус — что именно утверждаем. `VERIFIED` требует grade A,
`source_id`, `retrieved_at` и подписи `evidence-qa`; `PARTIAL` — частичное подтверждение;
`HYPOTHESIS` — внутренняя оценка/сценарий; `NOT_FETCHED` — источник допустим, данных нет.

## 5. Инструмент `tools/market_intel.py`

```powershell
python tools/market_intel.py --check        # exit 0 / 2
python tools/market_intel.py --org          # схема, процесс, границы
python tools/market_intel.py --json         # amfe.market_intel.check.v1
python tools/market_intel.py --role upstream --question "..." --account TATNEFT
python tools/market_intel.py --role osint-scout --question "..." --out .tmp/brief.md
```

**Что проверяет `--check`** (fail-closed, 30+ кодов): схема и версия; `RESEARCH_ONLY`,
`admission=false`; ровно один lead и 9–11 ролей; kebab-id и уникальность; обязательные поля;
слои; промпт существует, содержит 7 обязательных разделов и не переиспользуется; `memory` в
`agents/memory/*.jsonl`; цепочка `review_role` без самопроверки и циклов; только control-роли
подписывают `VERIFIED`; потолок Director ≤ `PARTIAL`; каталог сегментов, покрытие сегментов и
аккаунтов (20/20, без дублей и выдуманных id); порядок и владельцы процесса; `boundaries` со всеми
ключами; шкала evidence; ≥3 non-goals, ≥4 ворот, KPI; `deferred_roles` с чек-листом; наличие
плейбуков.

**Генератор brief** собирает: роль и мандат, вопрос, блок аккаунта (из
`marketing/target_accounts.json`, всегда `HYPOTHESIS`), что читать, подвопросы, пустой
**source plan** с `NOT_AVAILABLE_IN_ENV`/`NOT_FETCHED`, порядок работы, формат отчёта, критерий
приёмки, передачу, стоп-лист и хеш тела брифа. Защита: бриф не выпускается, если в нём появляется
e-mail/телефон или формулировка о допуске; неизвестная роль, короткий вопрос и неизвестный аккаунт
→ exit 2. Сеть не используется, файл пишется только по `--out`.

## 6. Ограничения (честно)

- **Сети и внешних БД в среде нет.** Валидатор проверяет структуру и честность статусов, а не факты
  о рынке; адаптеры к источникам описаны в плейбуках, но не выполнялись.
- **Нет ни одного `VERIFIED`-факта о компаниях**: внутренняя карточка — `HYPOTHESIS`, публичные
  цифры не выносятся без первоисточника и даты.
- **Нет контактов и каналов**: сеть не отправляет письма, не публикует и не коммитит.
- **Санкционная и правовая оценка** — за человеком; `evidence-qa` не подменяет юридическую проверку.
- Роль `services-equipment` работает без аккаунтов (watch-list) — это отражено в схеме, а не
  замаскировано «нулевыми» аккаунтами.

## 8. Связь с существующим контуром

- [docs/175](175_Агентная_оркестрация_и_обучение.md): те же принципы (write scopes, независимый
  ревьюер, fallback, память), но сеть MI — отдельный контур с собственным org-файлом.
- `agents/memory/*.jsonl`: у каждой роли MI свой файл памяти (`agents/memory/mi-<role>.jsonl`);
  создаётся при первой записи, не обязателен заранее.
- `protocols/source_registry.json` и `protocols/licence_register.json` не дублируются: сеть
  ссылается на них, а `knowledge_base/sources.json` — рабочий реестр с доступом и лицензией.
- Коммит и публикация — только Lead; сеть пишет лишь в свои файлы и в `knowledge_base/`.
