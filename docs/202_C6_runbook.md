# 202. C6 runbook: как вести релизную неделю

Дата: 2026-11-20. Статус: **операционный регламент недели; не допуск и не решение за Lead**.
Файлы: [tools/c6_runbook.py](../tools/c6_runbook.py), [tests/test_c6_runbook.py](../tests/test_c6_runbook.py)
(43 теста), входы — [registry/forecasts.jsonl](../registry/forecasts.jsonl) и
[build/shadow/shadow_status.json](../build/shadow/shadow_status.json); выход — `build/c6/c6_runbook.json|md`
(производный артефакт, в git не коммитится). Основание: [docs/139](139_C6_календарь.md) (календарь и
операционный процесс), [docs/119](119_Регламент_теневого_трека.md) (регламент трека), протокол v5 (C6).

## 1. Зачем нужен runbook

`tools/c6_calendar.py` умеет регистрировать неделю, разрешать строки и считать отчёт 12/4. Runbook —
это **одна страница перед действием**: что уже есть в журнале, что можно делать на этой неделе, чего
не хватает и почему регистрировать нельзя. Он не заменяет календарь и не принимает решений: он
показывает состояние и передаёт решение человеку.

Runbook читает только два входа: журнал прогнозов (append-only, единственный постоянный источник) и
производный статус трека. Аудит `build/c6/c6_audit.jsonl` — необязательный третий вход (по умолчанию
читается, если есть): по нему видно, зафиксирован ли `WEEK_CHECK` текущей недели.

```powershell
python tools/c6_runbook.py                          # неделя по дате статуса (без чтения часов)
python tools/c6_runbook.py --date 2026-11-20        # отчётная дата вручную
python tools/c6_runbook.py --date 2026-11-23 --confirm-release   # человек подтвердил релиз
python tools/c6_runbook.py --json                   # машинный документ
python tools/c6_runbook.py --out build/c6           # c6_runbook.json + c6_runbook.md
python tools/c6_runbook.py --check                  # валидация входов, exit 1 при проблемах
```

Общие флаги: `--journal`, `--status`, `--audit`, `--candidate`, `--target`, `--horizon`,
`--resolution-lag-days`, `--date`, `--json`, `--out`, `--check`, `--confirm-release`.

**Детерминизм.** Runbook не читает системные часы и не пишет меток времени: `--date` по умолчанию
равен `status.date`. Один и тот же журнал/статус/`--date`/флаги дают байт-идентичные JSON и MD.
**Ничего не пишется** в журнал, аудит и статус; `--out` создаёт только `c6_runbook.json|md`.
**Fail-closed:** отсутствующий/битый журнал или статус, невалидный журнал (схема registry,
append-only), строка с `registered_at` позже отчётной даты, факт без даты первой публикации,
неизвестный origin, нецелый horizon, отрицательные лаги → ошибка и exit 1, а не «примерный» отчёт.

## 2. Что показывает runbook

| Блок | Содержание |
|---|---|
| `c6` | счётчики **12/4** по журналу: `n_resolved`, `distinct_target_periods`, `remaining_forecasts`, `remaining_periods`, `registrations_needed`, `status` (`STARTING` / `IN_PROGRESS` / `COUNTS_MET`), `gate` |
| `rows` | каждая строка кандидата: `RESOLVED` (разрешена и считается), `PENDING` (ждёт факта), `BLOCKED` (факт есть, первая публикация позже отчётной даты — no look-ahead), `REJECTED` (нарушение целостности); списки `allowed` / `pending` / `blocked` / `rejected` |
| `control_group` | полная ли контрольная группа по каждой группе (origin + vintage_week), каких плеч не хватает |
| `release_windows` | до 6 ближайших оценочных релизных окон: неделя, начало, оценка origin и целевого периода, дата разрешения, добавляет ли окно новый период; `days_to_next`, `current_week_is_window` |
| `projection` | оценка дат 12-го разрешённого прогноза, 4-го различного периода и гейта; расхождение с ориентиром статуса |
| `missing` | чего не хватает: `FORECASTS`, `PERIODS`, `CONTROL_GROUP`, `WEEK_CHECK`, `LOSS_COVERAGE` |
| `checklist` | 9 шагов недели docs/139 со статусом `DONE` / `TODO` / `NEEDS_HUMAN` / `BLOCKED` и командой |
| `registration` | `can_register`, подтверждён ли релиз человеком, `cannot_register` (блокирующие причины), предупреждения регистрации |
| `alerts` | предупреждения процесса (коды docs/139/119 + `STATUS_*` из статуса) |

Состояние на 2026-11-18: **0/12 прогнозов, 1/4 периодов, `STARTING`**; в журнале 11 строк, из них
1 строка кандидата (`2026-11/2026-W46`, ждёт факта, контрольная группа полная); ближайшее оценочное
окно — 2026-W48 (2026-11-23); оценка 12-го прогноза — 2027-04-21, 4-го периода — 2027-02-01; gate
`NOT_MET`; `can_register = false` с причиной `RELEASE_NOT_CONFIRMED`. Это ожидаемое состояние, а не сбой.

## 3. Релизная неделя: порядок действий

Время — **пятница, после релиза** (CPI ~10–15 число, payrolls ~первая пятница, иногда GDP/claims).
Роль-исполнитель: `evaluation-harness`; проверка артефактов и публикации — `dense-vintages`; коммит
журнала и решения — `Lead`.

| Шаг | Действие | Команда / проверка | Результат |
|---|---|---|---|
| 0 | Открыть неделю | `python tools/c6_runbook.py --date <YYYY-MM-DD>` | ISO-неделя, счётчики, окна, чек-лист |
| 1 | Проверить календарь BLS/BEA: был ли **первый релиз** по цели | календарь/новости | «релизная» / «нет» |
| 2 | Если релизной **нет** — строку не добавлять | `python tools/c6_calendar.py --weekly --date <YYYY-MM-DD> --audit build/c6/c6_audit.jsonl --report-out build/c6` | только `WEEK_CHECK`, процесс не пропущен |
| 3 | Если релизная **есть** — подтвердить её в runbook | `python tools/c6_runbook.py --date <YYYY-MM-DD> --confirm-release` | `can_register = true`, чек-лист разблокирован |
| 4 | Собрать батч (кандидат + контрольные плечи), без записи | `python tools/forward_forecast.py --origin <YYYY-MM> --candidates ENSEMBLE_REGIME_V4 --targets T1_CPI_YOY:1 --mode latest --vintage-week <YYYY-Www> --dry-run --out build/forward_week.json` | `rows` без записи в журнал |
| 5 | Зарегистрировать недельный цикл | `python tools/c6_calendar.py --weekly --records build/forward_week.json --date <YYYY-MM-DD> --audit build/c6/c6_audit.jsonl --report-out build/c6` | строки + `WEEK_CHECK` + отчёт |
| 6 | Проверить отчёт | `python tools/c6_calendar.py --report --date <YYYY-MM-DD>`; `build/c6/c6_report.md` | нет `ALERT` |
| 7 | Проверить журнал | `python tools/registry.py --validate`; `python tools/c6_runbook.py --check` | `valid: true`, `ok: true` |
| 8 | Пересобрать трек | `python tools/shadow_track.py --with-calendar` | `build/shadow/<дата>.md|json` |
| 9 | Запись решения | при изменении статуса — D-… в журнале решений | след в журнале решений |

Шаг 4–5 выполняются только в релизную неделю. В неделю без релиза достаточно шага 2: он ставит
`WEEK_CHECK` и пересчитывает отчёт без новых строк. Задним числом строки не добавляются никогда.

## 4. Кто подтверждает релиз

* **Релизную неделю подтверждает человек** — исполнитель `evaluation-harness`, сверяя первый релиз
  данных по цели с календарём BLS/BEA. Только после этого передаётся `--confirm-release`
  (и только на текущую ISO-неделю: прошлые и будущие недели инструмент отвергает).
* **Артефакты и публикацию проверяет** `dense-vintages`: батч, отчёт 12/4, контрольная группа,
  отсутствие look-ahead, `python tools/registry.py --validate`.
* **Коммит журнала и решения принимает** `Lead`: runbook и отчёт — подготовка; сам runbook ничего не
  коммитит и не повышает статус. Коммит `registry/forecasts.jsonl` — только человек.
* **Инструмент релиз не подтверждает.** Без `--confirm-release` runbook всегда возвращает
  `RELEASE_NOT_CONFIRMED` и `can_register = false`: он не знает календарь статистики и не угадывает.
  Если человек подтвердил релиз в неделю вне оценочного окна, runbook пишет
  `RELEASE_OUTSIDE_CALENDAR` (WARN) — это допустимо, но источник подтверждения фиксируется в решении.

## 5. Что делать при 0/12

`0/12` — нормальное стартовое состояние: ни одна строка ещё не разрешилась, потому что факт по
целевому периоду не опубликован. Действия:

1. **Не «добирать» строки.** Регистрация только в релизные недели; строки одного целевого месяца
   недельными рядами коррелированы и не добавляют мощности.
2. **Каждую неделю ставить `WEEK_CHECK`** (`--weekly` без `--records`), даже если релиза не было:
   иначе появится `MISSED_CHECK` (ALERT) и история процесса будет выглядеть пропущенной.
3. **Следить за разрешением pending-строк.** Как только первая публикация факта появилась,
   `python tools/c6_calendar.py --resolve --date <дата>` разрешит строки (без look-ahead, значение
   факта не выводится). `PENDING_RESOLUTION` — INFO; `UNRESOLVED_LATE` (>30 дн. после конца периода)
   — WARN; `UNRESOLVED_OVERDUE` (>45 дн.) — ALERT: проверить винтажный архив, данные не подменять.
4. **Сверить дату 12-го прогноза.** Runbook даёт оценку (на 2026-11-18 — 2027-04-21); при пропуске
   релизных недель дата сдвигается, `PROJECTION_SHIFT` показывает расхождение с ориентиром статуса.
5. **0/12 при уже опубликованных фактах** — это не «нет данных», а разрыв процесса: проверить
   `FACTS_UNAVAILABLE` (нет локального винтажного архива), `UNRESOLVED_OVERDUE`, `registry.py
   --validate` и аудит; при подтверждённом факте разрешение выполняет `--resolve`, а не ручная правка.
6. **Не менять пороги/критерии под результат.** Остановка по `SUSPEND_*` — разбор и возврат только
   новым предрегистрированным кандидатом (docs/119 §4).

## 6. Почему регистрировать нельзя: коды

Блокирующие (`severity: BLOCK`, `can_register = false`):

| Код | Значение |
|---|---|
| `RELEASE_NOT_CONFIRMED` | релизная неделя не подтверждена человеком (нет `--confirm-release`) |
| `WEEK_ALREADY_REGISTERED` | в текущей неделе уже есть строка кандидата по паре: вторая строка недели не регистрируется |
| `WEEK_ROW_REJECTED` | в текущей неделе есть отклонённая строка: сначала устранить нарушение целостности |
| `FACT_ALREADY_PUBLISHED` | факт за целевой период будущей строки уже опубликован — регистрация была бы look-ahead |
| `STATUS_<CODE>` | статус трека в ALERT (например `SUSPEND_LOSS`, `SUSPEND_COVERAGE`, `SUSPEND_CADENCE`): сначала разбор |

Предупреждения (`registration.warnings`, не блокируют, но требуют действия):

| Код | Значение |
|---|---|
| `CONTROL_ARMS_NOT_BOOKED` | контрольные плечи недели ещё не в журнале: батч должен включать их вместе с кандидатом |
| `STATUS_STALE` | статус старше отчётной даты: счётчики статуса могут отставать (runbook считает по журналу) |
| `FACTS_UNAVAILABLE` | нет локального винтажного архива: публикация факта не подтверждена |
| `RELEASE_OUTSIDE_CALENDAR` | подтверждённый релиз не совпал с оценочным окном |

## 7. Строки журнала: четыре состояния

* **`RESOLVED` (allowed)** — первая публикация факта известна и не позже отчётной даты, контрольная
  группа полная, неделя/дата согласованы. Только такие строки идут в счётчик 12.
* **`PENDING`** — строка корректна, факт ещё не опубликован. Считается зарегистрированной (входит в
  `registrations_needed`), но не в 12.
* **`BLOCKED`** — факт существует, но первая публикация позже отчётной даты: строка не разрешается
  (no look-ahead) и не считается. Это не ошибка журнала.
* **`REJECTED`** — нарушение целостности: `CONTROL_GROUP_MISSING`, `PUBLISHED_BEFORE_REGISTRATION`
  (публикация не позже регистрации), `MISSING_VINTAGE_WEEK` / `VINTAGE_WEEK_MISMATCH` /
  `MISSING_REGISTERED_AT` (неделя PIT не доказуема), `ROW_AFTER_REPORT`, `BAD_ORIGIN`,
  `SUPERSEDED_BY_CORRECTION`. Строка **не удаляется** (журнал append-only) и **не входит** в 12/4;
  разбор — через коррекцию или решение Lead.

## 8. Релизные окна и проекция — это оценка

Модель та же, что в [tools/c6_calendar.py](../tools/c6_calendar.py): средняя частота **2,5 релизных
недели/мес** (шаг ≈12 дней), лаг разрешения **30 дней** (допущение статуса), окна привязаны к
понедельникам ISO-недель и отсчитываются от **последней регистрации** (каденс трека, а не от даты
просмотра). Поэтому даты не «уезжают», если страница открыта позже.

* Строки помечены `PROJECTED_NOT_REGISTERED` — это окна регистрации, а не записи журнала.
* `current_week_is_window` = текущая неделя попадает в оценочное окно; `days_to_next` = сколько дней
  до ближайшего окна. Флаг — подсказка, а не подтверждение релиза.
* Оценка целевого периода окна считается по `protocol_period` от месяца окна (для `T1_CPI_YOY` h=1
  это сам месяц origin; так же считает `tools/registry_resolve.py`). В таблице docs/139 §3 период
  подписан следующим месяцем — это приближение календаря, а журнальное значение периода определяет
  `protocol_period`.
* Сверка с docs/139 на 2026-11-18: 12-й прогноз — **2027-04-21**, 4-й период — **2027-02-01**,
  ориентир гейта — **2027-04-21**; ориентир статуса 2027-05-07, расхождение −16 дней объясняется
  pending-строкой (`PROJECTION_SHIFT`, INFO).

## 9. `--check`: что валидирует

```powershell
python tools/c6_runbook.py --check --date 2026-11-20
python tools/c6_runbook.py --check --json
```

Проверяется: читаемость и валидность журнала (схема registry + append-only), валидность статуса
(структура и внутренняя согласованность), читаемость аудита; совпадение пары и кандидата со
статусом; что строки не зарегистрированы после отчётной даты; `rows_total`, `rows_candidate`,
`n_resolved`, `distinct_target_periods` статуса против пересчёта по журналу; неделя/дата регистрации
каждой строки кандидата; наличие контрольной группы; отсутствие look-ahead.

Exit 1 при любой проблеме (`ok: false`), exit 0 при чистом результате. `--check` ничего не пишет.
Предупреждения (`STATUS_STALE`, `NO_WEEK_CHECK`, `FUTURE_FACT_BLOCKED`, `FACTS_UNAVAILABLE`,
`SUPERSEDED_ROW`) не валят проверку, но должны быть разобраны.

## 10. Ограничения

1. **Календарь — оценка, не обещание даты.** Частота 2,5 релизных недель/мес и лаг 30 дней —
   допущения; реальные недели зависят от календаря статистики.
2. **Релизная неделя — человеческое решение.** Runbook не знает BLS/BEA; без `--confirm-release`
   всегда `RELEASE_NOT_CONFIRMED`. Инструмент проверяет формат недели и PIT, а не факт релиза.
3. **Loss/coverage не считаются.** Их даёт `tools/registry_resolve.py` по разрешённой выборке;
   `gate` не может быть `PASS` без них. Runbook прямо помечает `loss_coverage_checked: false`.
4. **4 периода считаются по зарегистрированным строкам** (правило журнала); разрешённых периодов
   может быть меньше — это показывается отдельно.
5. **Первая публикация приблизительна**: винтажный архив квартальный, «первая публикация» — первая
   архивная дата с наблюдением.
6. **Аудит производный.** `build/` не коммитится; журнал прогнозов — единственный постоянный источник.
7. **Runbook не разрешает и не коммитит.** Решение о регистрации, коммите журнала и статусе
   кандидата принимает Lead; runbook — подготовка недели.
8. Счётчики 0/12 и 1/4 взяты на 2026-11-18; при обновлении журнала runbook пересчитать.

## 11. Воспроизведение

```powershell
# недельная страница
python tools/c6_runbook.py --date 2026-11-18
python tools/c6_runbook.py --date 2026-11-23 --confirm-release
python tools/c6_runbook.py --date 2026-11-18 --json
python tools/c6_runbook.py --date 2026-11-18 --out build/c6

# валидация
python tools/c6_runbook.py --check --date 2026-11-18
python tools/registry.py --validate
python tools/c6_calendar.py --report --date 2026-11-18

# тесты
python tests/test_c6_runbook.py        # 43 теста
python tests/test_c6_calendar.py       # 37 тестов календаря/процесса
```

Выходные файлы (`build/c6/c6_runbook.json|md`) — производные артефакты: в git не коммитятся, журнал
остаётся единственным append-only источником, сырые значения фактов в runbook не выводятся.
