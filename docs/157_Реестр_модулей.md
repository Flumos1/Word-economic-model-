## 1. Зачем и как связано с learning registry

| | Реестр модулей (этот документ) | Learning registry (docs/151) |
|---|---|---|
| Что записывает | паспорт **модуля**: id, kind, версия, код/данные, owner, docs/tests, ограничения | **модель/версию** с метриками, Q и историей статусов |
| Ключ | `module_id + version` | `model_id + version` |
| Статусы | `RESEARCH_ONLY → CANDIDATE → LIMITED → ACTIVE` | `CANDIDATE → SHADOW → LIMITED → ACTIVE` |
| Гейт выше CANDIDATE | preregistered критерии + независимое ревью | то же + `Q ≥ 0.60` и hard constraints |
| Роль в G2/G4 | G4 (walk-forward) и продукты ссылаются на `module_id@version`, не на код | Q/walk-forward-доказательства для версий |

Модульный реестр **не заменяет** learning registry и **не присваивает** допуск: он фиксирует
«что это за модуль, какой версии, каким кодом и какими данными он является, кто владелец и какие у
него ограничения». Обе записи могут ссылаться друг на друга: в паспорте есть `components` (например,
model_id финансовых карт), в learning registry — `model_id`/`version` соответствующей модели.

## 2. Схема паспорта (одно событие = одна строка JSONL)

| Поле | Тип | Обязательно | Смысл |
|---|---|---|---|
| `schema` | str | да | `AMFE-MODULE-REGISTRY/1.0.0` |
| `action` | str | да | `REGISTER` / `STATUS` |
| `module_id` | str | да | стабильный id, напр. `oil.brent`, `AGRI_SOY`, `world.p2` |
| `kind` | enum | да | `market / agri / finance / agentic / world / core / other` |
| `version` | str | да | `MAJOR.MINOR[.PATCH]` (напр. `0.2.0`) |
| `status` | enum | да | при REGISTER: только `RESEARCH_ONLY` или `CANDIDATE` |
| `owner` | str | да | трек/владелец (`track-a`…`track-e`) |
| `display_name`, `summary` | str | да | человекочитаемое имя и краткое описание |
| `code_sha256` | hex64 | да | комбинированный хеш кода (см. `code_hash`) |
| `code_files` | object | нет | `{relative_path: sha256}` — прозрачность состава |
| `data_sha256` | hex64/null | да (ключ) | хеш данных/манифеста; `null`, если данные не закоммичены |
| `data_status` | enum | да | `COMMITTED / LOCAL_ONLY / SYNTHETIC / ASSUMPTION_BASED / NONE` |
| `created_at` | date | да | ISO-дата; передаётся вызывающим (без чтения часов) |
| `docs`, `tests`, `entrypoints` | list[str] | да | ссылки на документацию/тесты и точки входа |
| `limitations` | list[str] | да | непустой список ограничений |
| `components` | list[str] | нет | подобъекты (сценарии, model_id, части модуля) |
| `note` | str | нет | примечание |
| `preregistered_criteria` | object/null | нет | только у STATUS-событий выше CANDIDATE |
| `independent_review` | object/null | нет | только у STATUS-событий выше CANDIDATE |
| `event_id` | hex64 | да | SHA-256 канонического события (детерминизм) |

`code_hash(files)` считает SHA-256 каждого файла и комбинированный SHA-256 от сортированных строк
`relative_path:sha256`, поэтому результат не зависит от порядка аргументов и абсолютных путей.
Каноническая строка: JSON с `sort_keys=True`, `separators=(",", ":")`, UTF-8, LF; существующие
байты никогда не перезаписываются.

## 3. Статусы и гейты

* `RESEARCH_ONLY` — по умолчанию; исследовательский прототип, не допуск.
* `CANDIDATE` — модуль готов к проверке; разрешён при регистрации **без** критериев.
* `LIMITED`, `ACTIVE` — **выше CANDIDATE**: требуют одновременно
  1. **preregistered критериев**: `criteria.registered_at ≤ at` (дата повышения), непустой
     `criteria`-объект, его SHA-256 пишется в событие; если критерии уже были зафиксированы в
     паспорте, повышение допускается только с теми же критериями;
  2. **независимого ревью**: `{reviewer, independent: true, pass: true, reviewed_at, report_sha256}`,
     `reviewer ≠ owner`, `reviewed_at ≤ at`.
* Понижение статуса возможно (`ACTIVE → RESEARCH_ONLY` и т.п.) без критериев; повторная установка
  того же статуса — ошибка.
* Регистрация сразу в `LIMITED`/`ACTIVE` **запрещена** (fail-closed), как и критерии/ревью в
  REGISTER-событии — они принадлежат только повышению.

## 5. Как добавить модуль

1. Собрать паспорт: `build_passport(module_id, kind, version, display_name, summary, owner,
   code_sha256, data_sha256, data_status, created_at, docs, tests, entrypoints, limitations,
   components=..., code_files=...)` — валидация полей и fail-closed на любую ошибку.
2. Убедиться, что единица вообще является модулем: `MarketModule` (scenarios/run) **или** экспортирует
   стабильный `MODULE_ID` и точку сборки (слой вроде `oil.storage_curve`). Инструменты, CLI и
   библиотеки сценариев в реестр не попадают (§4.1, п. 4).
3. Добавить пути кода в `CODE_FILES` в `tools/register_modules.py` (явный манифест; отсутствие файла
   — ошибка, а не тихий пропуск); закоммиченный вход данных, если он есть, — в `DATA_FILES`
   (`data_sha256` = хеш файла, иначе `null` + warning).
4. `register(path, passport)` — append-only; повторная регистрация того же `module_id+version`
   запрещена (нужна новая версия, старые события не редактируются).
5. Добавить тесты и документ модуля; указать `limitations` (непустой) и `data_status`.
6. Добавить `module_id` в `EXPECTED` в `tests/test_module_registry.py`: тест собирает модуль и
   сверяет паспорт с кодом, поэтому неподключённый модуль виден сразу.
7. Для повышения статуса — отдельное STATUS-событие с критериями и независимым ревью.

CLI:

```
python tools/register_modules.py                          # build/registry/modules.jsonl
python tools/register_modules.py --json                   # JSON-отчёт
python tools/register_modules.py --out build/registry/modules_report.json
python tools/register_modules.py --date 2026-11-16 --registry /tmp/modules.jsonl
```

## 6. Экспорт для API

`export_for_api(path)` возвращает детерминированный документ
`schema=AMFE-MODULE-REGISTRY-EXPORT/1.0.0`, `modules` отсортированы по `module_id` (последняя версия
каждого модуля; поля `status_history`/`status_events` не экспортируются), `counts` содержит
`modules`, `by_kind`, `by_status`. Документ не содержит меток времени и путей данных — пригоден для
кэширования и для ссылок продуктами (`module_id@version`).

## 7. Детерминизм и fail-closed

* Нет чтения системных часов: `created_at`/`at` передаёт вызывающий; `event_id` — хеш содержимого,
  поэтому одинаковые входы дают байт-идентичный JSONL (проверяется тестом).
* `load_entries` падает на битой строке/чужой схеме; `validate_registry` даёт отчёт
  (`valid/errors/modules`) без исключения; запись при ошибке не происходит.
* Дубликат `module_id+version` — ошибка; статус выше CANDIDATE без критериев/ревью — ошибка;
  критерии после даты повышения, ревьюер = owner, `independent != true`, `pass != true` — ошибки.
* Инструмент падает (exit 1) при отсутствии кода, невалидной дате, дубликатах, ошибках импорта
  модулей; `--date` меняет дату паспорта (для воспроизводимости фиксируется в записях).

## 8. Ограничения

1. **Статусы реестра — метаданные, не допуск**: RESEARCH_ONLY не означает «проверен», а
   CANDIDATE — не допуск к продукту; допуск по-прежнему только через protocol v5 (C6) и решение
   владельца.
2. **Хеш кода — снимок файлов на дату регистрации**; при изменении любого файла из `CODE_FILES` хеш
   меняется и нужна новая версия/событие. Хеш не проверяет смысл кода.
3. **Данные в основном не закоммичены**: `data_sha256=null` при `ASSUMPTION_BASED`/`SYNTHETIC`;
   у `world.p2` хешируется только релизный манифест, а не сами данные OECD (локальны).
4. **Локальный JSONL** без распределённых блокировок, подписей и прав доступа; для
   мультипользовательского режима нужен серверный журнал и подписи.
5. **Инструмент импортирует модули** (numpy и др.), поэтому зависит от доступности зависимостей;
   при ошибке импорта регистрация падает fail-closed, а не пропускает модуль.
6. **Нет автоматических переходов статусов** и нет связи с CI: повышение — явное событие с
   критериями/ревью; «независимость» ревью проверяется формально (reviewer ≠ owner), а не по
   личности.
7. Повторный запуск инструмента на том же журнале **падает по дубликатам** (append-only): для
   перерегистрации нужен новый журнал/новая версия, редактирование истории запрещено.
8. **Инструмент не поднимает версии.** Пересборка журнала регистрирует текущий снимок кода под тем
   же `module_id@version`; если файлы из `CODE_FILES` изменились (так вышло с `oil.brent` и
   `world.p2`, §4.1 п. 3), это видно по хешу, но семантическое повышение версии — решение владельца
   трека. До него продукт, ссылающийся на `module_id@version`, видит **другой код** под той же
   версией — это осознанная граница, а не гарантия неизменности.
9. **Слой без `MarketModule`**: `oil.storage_curve` регистрируется как `kind=market`, но контракта
   `scenarios()`/`run()` у него нет — продукты обязаны вызывать документированные функции
   (`build_curve`/`build_report`/`cross_check_with_oil`), а не «единый» интерфейс рынка.
10. **Даты паспортов разные**: G2-записи датированы 2026-11-16, газ и запасы — 2026-11-18
    (фактические даты регистрации); `--date` управляет только модулями без закреплённой даты.

## 9. Воспроизведение

```
python tools/register_modules.py            # 7 записей, JSON-отчёт
python tests/test_module_registry.py        # 22 теста (16 G2 + 6 G5)
```

Тесты покрывают: append-only префикс и канонические строки, дубликаты, запрет регистрации выше
CANDIDATE, невалидные паспорта (kind/version/hash/даты/ограничения), гейты LIMITED/ACTIVE
(критерии+ревью, даты, reviewer=owner, non-independent, pass=false), понижение статуса, latest-версию
и поиск, детерминизм байтов, экспорт для API, повреждённый журнал, `code_hash`, а также инструмент:
7 модулей всех RESEARCH_ONLY, порядок G2-записей, детерминизм, дубликаты, exit 1 на невалидной дате,
и сборку каждого модуля с проверкой паспорта (§4.1 п. 6).

G5-обновление не меняет ни код модулей, ни `src/amfe/learning/*`, ни протоколы: только
`tools/register_modules.py`, `tests/test_module_registry.py`, этот документ и docs/161.
