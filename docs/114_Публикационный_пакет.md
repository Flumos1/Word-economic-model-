# 114. Публикационный пакет: недельный бюллетень MD+JSON и дисклеймеры

Версия 1.0.0 · 2026-11-12. Волна 7, трек публикации. Задача: `task-7`. Действующий протокол —
**v5 FROZEN** (`protocols/evaluation_protocol_v5.json`, SHA-256 `41d6823e…`); журнал —
[registry/forecasts.jsonl](../registry/forecasts.jsonl) (5 строк, append-only).

Новые файлы: [tools/weekly_bulletin.py](../tools/weekly_bulletin.py),
[tests/test_weekly_bulletin.py](../tests/test_weekly_bulletin.py), этот документ и генерируемый
каталог `build/bulletin/` (`build/` в `.gitignore` — в git артефакты не добавляются). Существующие
`tools/**`, `protocols/**`, `registry/**`, `src/**` и продуктовый пакет `build/product/` не меняются.

Это **публикационная упаковка** уже полученных результатов, **не допуск и не новая оценка**: статус
ни одного кандидата не меняется, критерии не пересчитываются.

## 1. Что делает инструмент

`python tools/weekly_bulletin.py` читает только артефакты репозитория (без сети, без `data/raw/`):

| Вход | Что берётся |
|---|---|
| `build/product/forecast_latest.json` | статус, `conditional_data_class`, кандидат, цель, горизонт, origin, точка, 19 квантилей, контрольные плечи, C4/C6, хеши источников. Если файла нет — инструмент **один раз** собирает пакет через `tools/product_pack.py` (это можно отключить флагом `--no-build`) |
| `protocols/first_real_evaluation_report_v5.json` | подтверждённые C1/C2/C5 (окна W1/W2, относительные потери, скорректированные p) |
| `protocols/evaluation_protocol_v5.json` + `.sha256`, `r3_specification.json`, `nf_sim_thresholds.json` + `.sha256`, `comparator_composition_2026-11-11.json` | версии и SHA-256 замороженной цепочки; пины и хеши повторно сверяются загрузчиком `product_pack` |
| `registry/forecasts.jsonl` | журнал: проверка, что фид не устарел, и изменение к предыдущей записи |
| `protocols/regime_candidate_evaluation_report.json` | near-miss кандидата `ENSEMBLE_REGIME` (контекст; отсутствие файла не блокирует выпуск) |

Пишет два файла в `build/bulletin/`:

| Файл | Содержание |
|---|---|
| `<YYYY-MM-DD>.md` | бюллетень: статус и замороженная цепочка; последний прогноз с 50/80/90% интервалами и контрольными плечами; «что подтверждено» (C1/C2/C5 PASS на T1 h=1); «что не подтверждено» (C4 RMSE FAIL, C6 ноль) отдельными строками + near-miss `ENSEMBLE_REGIME` отдельной строкой; изменение к предыдущей записи журнала («первый выпуск», если её нет); дисклеймер и ограничения; источники с полными SHA-256 |
| `<YYYY-MM-DD>.json` | машиночитаемый двойник по схеме §2 |

Запуск:

```powershell
python tools/weekly_bulletin.py
python tools/weekly_bulletin.py --date 2026-11-12 --generated-at 2026-11-12T20:00:00Z
python tools/weekly_bulletin.py --no-build        # fail-closed, если build/product отсутствует
python -m unittest tests.test_weekly_bulletin -v
```

`--generated-at` фиксирует момент снимка; без него берётся текущее UTC, дата выпуска — из него же
(или из `--date`). Всё, кроме `generated_at`, — чистая функция входов: одинаковые входы и одинаковая
дата дают байт-идентичные файлы.

**Fail-closed:** отсутствие `build/product/forecast_latest.json` при `--no-build`, невозможность
собрать пакет, устаревший фид (точка/квантили/origin не совпадают с последней строкой журнала),
битый JSON, расхождение хеша протокола/журнала, несовпадение кандидата/цели/горизонта с отчётом,
неизвестный статус — код выхода `2`, файлы бюллетеня не пишутся.

Бюллетень намеренно **плоский и самодостаточный**: каждое число прослеживается до журнала, отчёта или
замороженного протокола, а `confirmed`/`not_confirmed` отделяют подтверждённое от неподтверждённого.
Сырых сторонних значений в нём нет по построению: журнал содержит только собственные прогнозы, отчёт —
только производные метрики и диджесты (`licence_policy`, docs/84).

## 4. Что публиковать можно и что нельзя

**Можно:**

- сам бюллетень (`build/bulletin/<date>.md` и `.json`) как отчёт исследовательского продукта;
- собственные прогнозы AMFE и производные метрики: точки, квантили, относительные потери, p-значения,
  счётчики C6, хеши;
- явно помеченные утверждения о подтверждённом (C1/C2/C5 PASS) и неподтверждённом (C4 FAIL, C6 ноль).

**Нельзя:**

- выдавать `CANDIDATE` за «допущенную модель», скрывать C4 FAIL или C6-ноль, убирать near-miss
  `ENSEMBLE_REGIME` из контекста;
- снимать `conditional_data_class=true` без новой оценки, проходящей C4 без реконструкции;
- публиковать сырые сторонние наборы данных (FRED/ALFRED, FRED-MD/QD, SPF и любые другие) — никогда:
  `licence_policy` разрешает только производные статистики (docs/84); бюллетень их и не содержит;
- публиковать бюллетень как инвестиционную рекомендацию или как прогноз «для сделок»;
- приписывать бюллетеню смену статусов: он их не меняет и не пересчитывает критерии.

## 5. Обязательный дисклеймер

Каждый выпуск содержит блок «Это не допущенная модель и не инвестиционная рекомендация» и фиксирует:
статус `CANDIDATE`; `conditional_data_class = true`; недостигнутые SHADOW_TEST / LIMITED_DEPLOYMENT /
ACTIVE; C4 FAIL по RMSE; C6 = 0/12 и 0/4; pre-origin семантику записи; отсутствие C3; ограничение
пакета парой T1_CPI_YOY h=1 (T2/T3 не входят). Тот же текст продублирован в JSON (`disclaimer`,
`limitations`), поэтому машиночитаемая версия не может быть опубликована без дисклеймера.

## 6. Тесты

`tests/test_weekly_bulletin.py` (21 тест, все зелёные):

- схема JSON: обязательные поля и типы, 19 строго возрастающих квантилей, интервалы 50/80/90 и их
  вложенность, контрольные плечи;
- консистентность: точка, квантили и origin совпадают с `forecast_latest.json` и последней строкой
  журнала; контрольные точки — со строками контрольных плеч; статус/хеши — с фидом и файлами;
  `confirmed` — с отчётом v5 (C1/C2/C5 PASS и числа); `not_confirmed` — с C4/C6 фида; near-miss —
  с отчётом `ENSEMBLE_REGIME`;
- обязательные блоки Markdown и все ключевые числа/токены (CANDIDATE, версии, хеши, 1.0775, 0.9303,
  0/12, 0/4, near-miss);
- отсутствие сырых третьих данных: запрещённые ключи в JSON, маркеры `actual_*`, `data/raw`,
  `data_log.json` в тексте;
- детерминизм: повторная сборка байт-идентична; при другой `generated_at` отличается только эта метка;
- неизменность входов: SHA-256 журнала, протокола и замороженных файлов после запуска те же;
- fail-closed: отсутствие `build/product` при `--no-build` и пустой корень дают код `2`;
- автосборка пакета при отсутствии `build/product`; CLI как отдельный процесс.

## 7. Ограничения

1. **Не допуск и не ACTIVE.** Бюллетень фиксирует `CANDIDATE`; SHADOW_TEST, LIMITED_DEPLOYMENT и
   ACTIVE не достигнуты. C6 физически не может быть пройден до накопления журнала (~12 месяцев после
   первой записи), поэтому потолок статуса — `CANDIDATE`.
2. **Один кандидат и одна пара.** Бюллетень покрывает `T1_CPI_YOY` h=1 и кандидата из продуктового
   фида; T2/T3 и остальные кандидаты в него не входят (near-miss `ENSEMBLE_REGIME` — только контекст).
3. **Снимок, а не поток.** `generated_at` фиксирует момент сборки; автоматического обновления,
   рассылки и внешней публикации нет. Пересборка — ручная/CI и не коммитится инструментом.
4. **Зависимость от формата фида и отчёта.** Поля C4/C6 берутся из `forecast_latest.json`, C1/C2/C5 —
   из `admission.criteria` отчёта; смена формата требует правки инструмента (он упадёт fail-closed).
5. **Устаревший фид не публикуется.** Если журнал ушёл вперёд `build/product`, бюллетень падает с
   кодом `2`: нужно пересобрать `python tools/product_pack.py`.
6. **Файлы в git.** `build/` в `.gitignore`; добавлять ли артефакты в git — отдельное решение Lead
   (задача говорит не коммитить).
