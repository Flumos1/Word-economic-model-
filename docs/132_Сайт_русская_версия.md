# 132. Сайт: русская и английская версии (static, из реальных артефактов)

Версия 1.1.0 · 2026-11-14. Волна P2, задачи `task-23` (RU) и `task-27` (EN). Инструмент —
[tools/site_build.py](../tools/site_build.py), тесты — [tests/test_site_build.py](../tests/test_site_build.py).
Выход — двуязычный каталог `site/` (в git **не коммитится**: это генерируемый артефакт, решение о
публикации — отдельное действие Lead).

Сайт — публичная **витрина уже зарегистрированных результатов**, а не допуск и не новая оценка.
Статусы кандидатов он не меняет, критерии не пересчитывает, внешней сети не требует, JavaScript и
фреймворков не использует.

## 1a. Двуязычность (RU ↔ EN)

- Русские страницы лежат в `site/*.html`, английские — в `site/en/*.html`; CSS общий
  (`site/assets/style.css`, из EN подключается как `../assets/style.css`).
- `<html lang="ru">` для русских страниц и `<html lang="en">` для английских. На каждой странице
  есть переключатель языка (`class="lang-switch"`): с RU-страницы — ссылка `en/<page>.html`
  (`hreflang="en"`), с EN-страницы — ссылка `../<page>.html` (`hreflang="ru"`).
- Числа, статусы и дисклеймеры идентичны: EN-версия переводит текст, но берёт те же данные из
  артефактов. EN-дисклеймер — «Research only — not admission, not investment advice», статусы
  CANDIDATE/SHADOW_TEST, C4 FAIL и C6 показаны так же честно.
- Локальные ссылки: RU `../docs/<файл>.md`, EN `../../docs/<файл>.md` — обе версии работают при
  открытии файла напрямую и не зависят от сервера.
- Как добавить третий язык: добавить словари в `NAV_LABELS`/`BRAND_LABELS`/`FOOTER`, набор
  render-функций (`render_*_xx`), запись в `RENDERERS_*` и пару в `LANGUAGES`; `page()` проставит
  `lang`, CSS-путь и переключатель (для нового языка нужна ветка в `page()`). Тесты: новые страницы
  добавить в `REQUIRED_FILES`, проверить `lang`, дисклеймер и числа.
- Русская версия не меняется по смыслу: RU-тесты остаются зелёными, EN-страницы — дополнительные
  файлы.

## 3. Как собрать и открыть

```powershell
python tools/site_build.py                       # site/ с текущим generated_at
python tools/site_build.py --generated-at 2026-11-14T12:00:00Z --out-dir site
python -m unittest tests.test_site_build -v      # 20 тестов (RU + EN)
```

Проверка локально:

```powershell
start site/index.html                            # просто открыть файл в браузере
# или, если нужен http-контекст:
python -m http.server 8000 --directory site      # затем http://127.0.0.1:8000/index.html
```

Сервер не обязателен: сайт полностью статический, все ссылки относительные. Внешняя сеть не нужна
ни для сборки, ни для просмотра.

Всё, кроме `generated_at` в подвале, — чистая функция входов: повторная сборка с той же датой даёт
байт-идентичные файлы. **Fail-closed:** если нет обязательного входа (продуктовый фид, мировой
индекс/отчёты, отчёты v4/v5, `shadow_status.json`, манifestы FIGARO/WIOD, `blocked.json`, документы
из списка) или вход битый — код выхода `2`, `site/` не пишется.

## 4. Что публиковать можно и что нельзя

**Можно:** сам сайт как витрину исследования; собственные прогнозы и производные метрики (точки,
квантили, относительные потери, покрытие ВВП, доли, топ-списки); явно помеченные статусы
CANDIDATE/SHADOW_TEST/RESEARCH_ONLY.

**Нельзя:**

- выдавать CANDIDATE/SHADOW_TEST за «допущенную модель» или ACTIVE; скрывать C4 FAIL и C6-ноль;
- публиковать сырые сторонние наборы (FIGARO/WIOD/OECD/Eora/Comtrade) и их значения — только
  производные агрегаты по лицензии источника;
- добавлять внешние URL, JS, аналитику, шрифты или CDN: сайт должен оставаться офлайн-статическим;
- публиковать сценарии как прогноз или инвестиционную рекомендацию — это сравнительная статика;
- менять статусы «на сайте»: сайт их только отображает.

Дисклеймер «не допуск / не инвестиционная рекомендация» стоит на каждой странице в шапке-выноске и
в подвале; JSON-фиды и отчёты он не заменяет.

## 5. Как обновлять

1. Пересобрать источники: `python tools/product_pack.py`, `python tools/weekly_bulletin.py`,
   `python tools/shadow_track.py`, при необходимости — `tools/world_reports.py` (сценарии).
2. Пересобрать сайт: `python tools/site_build.py` (при публикации — с фиксированным
   `--generated-at`, чтобы артефакт был воспроизводим).
3. Прогнать `python -m unittest tests.test_site_build -v`.
4. Проверить вручную: статусы, C4/C6, отсутствие внешних URL и JS, суммы сценариев.
5. Публикация (если решит Lead) — отдельным шагом; коммит `site/` в git не автоматизируется.

## 6. Ограничения

1. **Снимок, а не поток.** Сайт отражает состояние `build/product`, `build/world`, `build/shadow` на
   момент сборки; автодеплоя, обновления в реальном времени и внешней аналитики нет.
2. **Зависимость от артефактов.** Если `build/product`/`build/world`/`build/shadow` устарели, сайт
   покажет устаревшие числа; сборка сайта не пересчитывает прогнозы и сценарии.
3. **Не допуск.** Страницы фиксируют CANDIDATE и SHADOW_TEST; C4 FAIL и C6 не скрываются; C6 идёт
   своим ходом (12 разрешённых прогнозов, ≥4 периода) и ускорять его нельзя.
4. **Двуязычность, но не локализация.** Есть RU и EN; третьего языка, перевода документов и
   автоопределения языка нет. EN-версия — перевод витрины, а не отдельный контент.
5. **Офлайн-дизайн.** Никакого JS/интерактива, графиков и фильтров нет by design; вёрстка
   адаптивная, темы светлая/тёмная — через `prefers-color-scheme`.
6. **Сырые данные вне git.** `site/` и `build/` — генерируемые артефакты; сырые MRIO-данные лежат в
   `data/mrio/` (вне git) и на сайт не попадают.
