## 1. Назначение и границы

Этап 2 дорожной карты — [docs/42](42_Дорожная_карта_реализации_AMFE17_и_контрольные_ворота.md), N2:
«превратить прототип четырёх секторов в типизированные счета с полным
отображением изменений чистой стоимости и финансовых позиций».

Модуль закрывает:

1. типизированные секторы, счета и инструменты вместо «словарей без типов»
   прототипов v01–v07;
2. подписанные финансовые позиции (актив `+`, обязательство `−`), товарные
   запасы и основной капитал как реальные активы, чистую стоимость;
3. атомарные проводки двойной записи с полным откатом при любой ошибке;
4. независимый слой инвариантов: зеркальность финансовых позиций,
   `ΔNW = сбережения + переоценка` (в общем виде — с капитальными трансфертами
   и прочими изменениями объёма), бюджетное ограничение государства, закрытая
   экономика без невязок, три метода ВВП игрушечного ядра;
5. обратную совместимость: те же сценарии, что v01/v02/v04–v07, воспроизводятся
   с точностью до `Decimal` и сверяются в тестах с оригинальными прототипами;
6. воспроизводимую сетку 10 000 допустимых комбинаций параметров (продолжение
   `tests/test_government_parameter_grid_v03.py`);
7. интерфейс расширения для этапа 3 (две страны, две валюты).

Вне модуля и вне этапа 2: полноценные счета производства/образования/распределения
и использования доходов по SNA, промежуточное потребление, капитальные трансферты
в полном объёме, рынок облигаций и центральный банк, поведение секторов,
калибровка, эмпирические данные. См. §9.

## 2. Архитектура

```
src/amfe/accounts/
├── __init__.py      публичный API
├── model.py         типы: Sector, Dimension, CurrentFlow, CapitalFlow,
│                    RealAsset, FinancialInstrument, TransactionKind,
│                    Posting, Transaction, AccountSpec, ChartOfAccounts,
│                    BalanceSheet, Snapshot, JournalEntry, NonTransactionEntry,
│                    PeriodReport, ошибки, Decimal-конвертация
├── accounts.py      AccountSystem: атомарное применение проводок, период,
│                    переоценки/прочие изменения объёма, отчёты, экспорт
├── invariants.py    независимые проверки (snapshot/report), GovernmentBudget,
│                    проверка двухкнижной зеркальности для этапа 3
└── scenario.py      эталонные сценарии docs/39/40/44/47, сетка 10 000
```

Принципы слоения:

* `model.py` — чистые данные и хартия счетов, без периода и без инвариантов;
  проверяется быстро и может использоваться другими слоями.
* `accounts.py` — состояние и жизненный цикл периода; перед фиксацией проводки
  валидирует целиком *кандидатное* состояние, затем фиксирует атомарно.
* `invariants.py` — чистые функции от `Snapshot`/`PeriodReport`; специально
  не зашиты в `apply`, чтобы их можно было проверять на испорченных отчётах
  (негативные тесты) и переиспользовать в этапе 3.
* `scenario.py` — ссылочные сценарии; никакой бизнес-логики в тестах.

Денежная единица: одна номинальная единица страны, цена конечного продукта = 1;
все суммы — точный `Decimal` (стандартный контекст, без двоичных дробей).
`float` принимается только через `str`, `bool`/`NaN`/`Infinity` отвергаются.
Внешние пакеты не используются (stdlib).

## 3. Типы счетов и знаки

### 3.1 Измерения и потоки

| Измерение | Смысл | Знак |
|---|---|---|
| `CURRENT` | текущий счёт: сберегающий поток | получение `+`, расход `−` |
| `CAPITAL` | капитальный счёт: капитальный трансферт | получение `+`, выплата `−` |
| `REAL` | изменение реального актива в сделке | приобретение `+`, выбытие `−` |
| `FINANCIAL` | финансовый инструмент (запас) | актив `+`, обязательство `−` |

`CurrentFlow`: `output` (выпуск, только фирма), `wages`, `direct_tax`,
`transfer`, `interest`, `household_consumption`, `government_consumption`,
`depreciation`. `CapitalFlow`: `capital_transfer`.
`RealAsset`: `inventory`, `fixed_capital`.
`FinancialInstrument`: `deposit`, `loan`, `bond`, `receivable` (начисленная
зарплата: актив домохозяйства / обязательство фирмы).

### 3.2 Роли счетов (`AccountSpec`)

У каждого счёта в `ChartOfAccounts` явно заданы:

* `posting_sectors` — кто вправе делать проводки;
* `positive_sectors` / `negative_sectors` — допустимый знак проводки
  (для текущих/капитальных/реальных счетов);
* `mirrored` — сумма проводок одной транзакции по этому счёту обязана быть
  нулевой (все финансовые инструменты, зарплаты, налоги, трансферты, проценты,
  капитальные трансферты);
* `asset_sectors` / `liability_sectors` — допустимая ориентация *остатка*
  финансового счёта (для инструмента);
* `allow_negative_balance` — только для реальных активов (по умолчанию запрещено).

Роли проверяются и на уровне отдельной проводки, и на уровне итоговых остатков —
поэтому, например, переплата кредита (`bank: loan < 0`) и отрицательный депозит
домохозяйства отвергаются, а отрицательная чистая стоимость фирмы разрешена.

### 3.3 Правило атомарности транзакции

Для каждой транзакции и каждого затронутого сектора `s`:

```
Σ CURRENT(s) + Σ CAPITAL(s) = Σ REAL(s) + Σ FINANCIAL(s)
```

плюс `Σ` по всем секторам для каждого `mirrored`-счёта равен нулю.
Из этого одного правила следуют и двойная запись, и связность счетов:
выпуск ⇒ текущий доход и запас; зарплата ⇒ зеркальные текущие записи и
зеркальные депозиты; покупка ⇒ расход домохозяйства и превращение запаса
фирмы в депозит; кредит ⇒ четыре зеркальные финансовые позиции и т.д.
Проводка с дисбалансом по счёту, сектору или знаку отвергается целиком:
балансы, журнал и состояние периода не меняются.

### 3.4 Чистая стоимость и счета сектора

Для сектора `s`:

```
NW_s = Σ_i F_(s,i) + Σ_a I_(s,a)          (F — финансовые позиции, I — реальные активы)
S_s  = Σ CURRENT(s)                        (сбережения, net saving)
CFC_s = −CURRENT_depreciation(s)          (потребление основного капитала)
GS_s  = S_s + CFC_s                        (валовые сбережения)
CF_s  = ΔInventory(s) + GFCF(s)            (валовое накопление)
NLB_s = GS_s + CapitalTransfers_s − CF_s   (чистое кредитование/заимствование)
ΔF_s  = Σ FINANCIAL(s)                     (изменение чистых финансовых активов)
```

Капитальный счёт представлен накоплением и капитальными трансфертами,
балансирующая статья `NLB_s` выводится; финансовый счёт — `ΔF_s`.
Требуется `NLB_s = ΔF_s` для каждого сектора.

## 4. Инварианты

| Код | Инвариант | Где проверяется |
|---|---|---|
| F01 | Для каждого финансового инструмента `Σ_s F_(s,i) = 0` (зеркальность) | `apply` (транзакция), `check_financial_mirror`, `check_snapshot` |
| F02 | Ориентация остатков: актив `>0` только у `asset_sectors`, обязательство `<0` только у `liability_sectors`; реальные активы неотрицательны | `check_stock_signs` (вызывается из `apply`) |
| F03 | `Σ_s NW_s = Σ_s real_s` (агрегатное богатство = реальные активы закрытой экономики) | `check_snapshot` |
| P01 | `NW_close − NW_open = S_s + CapitalTransfers_s + Revaluation_s + OVC_s`; без трансфертов/переоценки — требуемое `ΔNW = сбережения` | `check_period_identity` |
| P02 | `GS_s = S_s + CFC_s`; `NLB_s = GS_s + CapitalTransfers_s − CF_s`; `Δ_real(s) = CF_s − CFC_s` | `check_period_identity` |
| P03 | `NLB_s = ΔF_s`; по каждому инструменту `Σ_s ΔF_(s,i) = 0` | `check_financial_accounts` |
| C01 | Закрытая экономика без невязок: `Σ_s NLB_s = 0`, `Σ_s GS_s = Σ_s CF_s`, `Σ_s ΔF_s = 0`, `Σ_s S_s = Σ_s CF_s − Σ_s CFC_s` | `check_closed_economy` |
| G01 | Бюджетное ограничение государства: `revenue − expenditure = S_gov`; дефицит финансируется чистым заимствованием: `net_borrowing = deficit − CFC_gov − CapitalTransfers_gov + CF_gov`; `net_borrowing = Δобязательств − Δактивов` | `check_government_budget` |
| G02 | ВВП тремя методами в игрушечном ядре: `Y = C + G + ΔInventory + GFCF` и `Y = wages_received + gross_operating_surplus`, `Y_prod = Y_exp = Y_inc` | `check_gdp_identity` |

Все проверки вызываются в `close_period`; `AccountSystem.assert_invariants()`
перепроверяет текущий снимок и последний отчёт. Соответствие старым
формулировкам [docs/40](40_Государственный_сектор_и_проверка_балансов_v02.md):
F01 (нулевая сумма подписанных изменений) — правило атомарности §3.3;
F02–F04 (зеркала кредита, облигации и депозитов) — F01 настоящего ядра;
F05 (баланс банка с процентным результатом) — P03; G01 docs/40 (ВВП по
расходам) — G02; G02 docs/40 (кассовый бюджет государства) — G01; G03 docs/40
(нельзя потратить/продать больше доступного) — F02 плюс негативные тесты §10.

Соглашения, важные для чтения инвариантов:

* выпуск фиксируется как текущий доход фирмы и одновременный прирост запаса;
  продажа — превращение запаса в депозит, а не новый доход (доход уже признан
  при выпуске). Это учебная конвенция docs/39/45, а не полный SNA;
* процент — перераспределение дохода (property income), не выпуск;
* прямой сбор — экзогенный текущий трансферт фирмы, не налог на прибыль и не
  налог на продукты; в ВВП по доходам не входит;
* амортизация — `CFC`, не уменьшает ВВП (gross measures), уменьшает
  сбережения и основной капитал;
* `G02` действует только при допущениях ядра: одно государство и одна страна,
  нет промежуточного потребления, налогов на продукты, смешанного дохода,
  зарплаты государства и производства вне фирмы. При расширении хартии эти
  допущения нужно пересмотреть явно.

## 5. Жизненный цикл периода и неоперационные изменения

* `AccountSystem(chart, period, opening=None)` открывает первый период;
  `OpeningBalances` задаёт стартовые остатки (проводки не создаются),
  проверяется зеркальность и ориентация.
* `close_period()` строит `PeriodReport` (начальная/конечная чистая стоимость,
  текущие потоки по кодам, сбережения, CFC, накопление, `NLB`, финансовые
  изменения, переоценки, OVC, ВВП, журнал периода, снимок) и проверяет все
  инварианты; при нарушении период остаётся открытым и состояние не меняется.
* `begin_period(label)` открывает следующий период; остатки переходят в
  начальные; дубликат метки запрещён.
* `revalue_real(asset, delta)` — переоценка реального актива (holding gain),
  `other_volume_change_real(asset, delta)` — прочее изменение объёма,
  `revalue_financial(instrument, {sector: delta})` — переоценка финансового
  инструмента, сумма изменений по инструменту обязана быть нулевой.
  Эти изменения не попадают в журнал транзакций, но входят в `P01`.
* Ошибочная переоценка (отрицательный реальный актив, незеркальная
  финансовая переоценка) откатывается полностью.

## 9. Интерфейс для этапа 3 (две страны, две валюты) и что осталось

### 9.1 Точка расширения

`ChartOfAccounts.extend(sectors=..., specs=[AccountSpec...], kinds=...)`
возвращает новую хартию; повторная спецификация существующего счёта объединяет
роли (например, добавляет новый сектор в `posting_sectors`/`asset_sectors`).
Ничего в `AccountSystem` менять не требуется: проверки читают роли из хартии.
Пример (исполняется в тесте `test_chart_extension_keeps_global_mirroring`):
добавлен сектор `row` (остальной мир) и инструмент `external_claim`;
транзакция «домохозяйство покупает внешний актив, расплачиваясь депозитом»
проходит все инварианты.

### 9.2 Контракт двух стран

1. Каждая страна ведёт свой `AccountSystem` (своя валюта, свои цены) с
   дополнительным сектором `row`, отражающим остальной мир **в книгах этой страны**.
2. Для каждой пары зеркальных инструментов `(i_A, i_B)`:
   * позиции резидентов двух книг в сумме дают ноль (у мира нет чистого
     требования к самому себе);
   * `balance(ROW_A, i_A) = Σ позиций резидентов B`, `balance(ROW_B, i_B) = Σ
     позиций резидентов A` (с согласованным знаком).
   Проверка: `invariants.check_external_mirroring(left, right, instrument_pairs=...)`.
3. Переоценка из-за курса — отдельные `revalue_financial`-записи после
   пересчёта в общую расчётную единицу; они отделены от потоков и входят в
   `ΔNW = сбережения + переоценка`.
4. Потоки экспорта/импорта, факторных доходов и трансфертов добавляются как
   новые `current`-коды в расширенной хартии (обязательно `mirrored` там, где
   есть контрагент), внешние позиции — как новые инструменты с явными ролями.
5. Согласование ВВП и торговли между странами уже прототипировано отдельно:
