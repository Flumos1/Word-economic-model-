# CRM: какие стадии и даты ставить (инструкция, CSV не изменён)

**Статус:** только инструкция. `marketing/crm_pipeline.csv.tmpl` в этом батче **не изменён**: 20
аккаунтов, все стадии `NEW`, владелец `lead` — как было. Правки вносит человек с правами на CRM по
этой инструкции; перед сохранением — валидация `tools/marketing_crm.py --check`.

## 1. Правила, которые нельзя нарушать

- Стадии — только `NEW`, `CONTACTED`, `DISCOVERY`, `PILOT`, `PROPOSAL`, `WON`, `LOST` (в верхнем
  регистре); `next_date` — реальная дата `YYYY-MM-DD`; `next_action` — конкретное действие (≥ 10
  символов).
- В CRM **не пишем адреса электронной почты, телефоны, имена и должности людей**: валидатор
  отклоняет строку с такими значениями. Для этого есть `owner = lead` как роль, а контакты живут у
  человека с каналом.
- `owner` меняется с роли `lead` на человека только после назначения Lead; до этого не трогаем.
- Ровно 20 аккаунтов из `target_accounts.json`. LEGAT в этот CSV не добавляем — см. §6.

`next_action` выше — готовые строки для колонки; они не содержат контактов и проходят валидатор.

## 3. Когда письмо реально отправлено

Стадия → `CONTACTED`, `next_date` = дата отправки + 7 дней, `next_action` = «Follow-up: короткое
письмо, вложение по запросу». Пример для плановых дат из `send_plan.md`:

| ID | Если отправлено | Стадия | next_date |
|---|---|---|---|
| `TATNEFT` | 2026-11-24 | `CONTACTED` | 2026-12-01 |
| `TANECO` | 2026-11-25 | `CONTACTED` | 2026-12-02 |
| `GAZPROMNEFT` | 2026-11-27 | `CONTACTED` | 2026-12-04 |
| `NOVATEK` | 2026-11-30 | `CONTACTED` | 2026-12-07 |
| `IRKUTSK_OIL` | 2026-12-02 | `CONTACTED` | 2026-12-09 |

Дата отправки ставится фактическая, а не плановая. Если письмо не ушло — стадия остаётся `NEW`, а
`next_date` переносится на следующий рабочий день поиска контакта.

## 4. Дальше по воронке

| Событие | Стадия | next_date | next_action (пример) |
|---|---|---|---|
| Ответ, договорились о созвоне | `DISCOVERY` | +2–3 дня | 20-мин созвон: 4 вопроса, один экран, границы, next step |
| Созвон состоялся, есть задача | `PILOT` | +3 дня | NDA + 2 шаблона данных; согласовать категорию/решение |
| Пилот согласован по объёму/цене | `PROPOSAL` | +5 дней | Отправить оффер и критерии успеха; зафиксировать дату старта |
| Оплата получена | `WON` | дата закрытия | Передать в доставку; зафиксировать критерии успеха |
| Отказ или стоп после 2 писем | `LOST` | дата решения | Причина отказа в `notes`; вернуться в 2027-Q1 при новом поводе |

Дедлайны критериев успеха: Татнефть — 2026-12-05, ТАНЕКО — 2026-12-08, Газпром нефть — 2026-12-11,
НОВАТЭК — 2026-12-15, ИНК — 2026-12-18. Если к этой дате нет ответа — `LOST` с причиной
«нет ответа» либо `NEW` с датой возврата, но без новых писем в том же цикле.

## 5. Проверка после правок

```powershell
python tools/marketing_crm.py --check     # exit 0: схема, стадии, tier, даты, нет контактов
python tools/marketing_crm.py --summary   # что делать на этой неделе
python -m unittest tests.test_marketing_crm
```

Если `--check` вернул exit 2 — строку не сохранять: причина в выводе (стадия, дата, tier, контакт).

## 6. LEGAT — отдельный трек

ТПО «ЛЕГАТ» нет в `crm_pipeline.csv.tmpl` и в `target_accounts.json`; добавление сломает валидатор
(ровно 20 аккаунтов). Учёт LEGAT ведётся в `outreach/legat/`:

- follow-up запланирован на 2026-11-27 (`followup_legat_2026-11-27.md`), пока **не отправлен**;
- после отправки — запись `outreach/legat/SENT_v3.md`; стадия в LEGAT-треке `CONTACTED`,
  `next_date` = 2026-12-04;
- ответ до 2026-12-04 — `DISCOVERY` и 20-минутный созвон; иначе пауза до 2027-Q1.

## 7. Чего не делать

- не менять CSV-шаблон в этом батче и не добавлять LEGAT;
- не ставить `WON` без оплаты и `LOST` без причины в `notes`;
- не писать в CRM имена, адреса, телефоны — только роли и задачи;
- не ставить `next_date` в прошлом: просроченная дата у `TATNEFT` (2026-11-20) — как раз то, что
  исправляет §2.
